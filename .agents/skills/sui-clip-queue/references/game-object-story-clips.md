# 游戏目标物精切：从“看见”到“漏掉”的完整故事

这套流程适合“画面里有醒目目标物（红点、宝箱、钥匙、机关等），主播看见或被提醒后仍然漏掉”的游戏片段。目标是保留观众能理解的因果链，而不是把几个检测到目标物的帧拼成蒙太奇。

## 先找完整事件链

先用主播 SRT 和观众 XML 找叙事锚点，再回到原视频确认画面：

1. **第一次出现或第一次被观众指出**：观众说“看到了”“在一层”“在右边”等。
2. **主播意识到目标**：主播说“我看到了”“红色”“去找路”等。
3. **接近和找路**：保留转身、找桥、找楼梯、尝试跳跃等必要过程。若这一步解释了为什么后面没拿到，不能删掉。
4. **第一次结果**：开箱、捡到一个、触发机关或确认目标已经在视野内。
5. **遗漏或误认**：第二个目标仍在画面中，主播离开、继续找，或把目标看成火苗、灯光等。
6. **回看与收尾**：主播回去寻找，观众重复提醒，最后形成明确笑点或反应。

用源视频绝对秒记录每个节点。窗口通常从第一次有效提醒前几秒开始，到主播说完收尾、动作完成后再结束。边界应落在完整语句、动作结果或自然停顿之后；字幕结束不等于说话结束，动作画面也不能只保留结果帧。

## 视觉候选只负责召回

可以用 OpenCV 的 HSV 红色掩膜、亮度和连通区域扫描找候选帧，再人工复核。红色场景灯、火焰、伤害特效和 UI 都会产生假阳性，所以：

- 扫描结果写成候选帧和分数，不直接宣称“这里一定有目标物”；
- 每个候选至少看开始、中间、结束三帧，确认目标物的位置和持续时间；
- 通用 YOLO 没有游戏专属目标物类别时，不要把“红色物体”当成 YOLO 已识别的道具；
- 画面证据与 SRT/XML 时间证据要能互相对齐，不能用弹幕文字替代画面确认。

## 剪辑和声音

连续故事优先于固定时长。找路、过桥和开箱过程可以较长，但必须服务于目标物的因果链；毒区、重复战斗和无关支线可以在不破坏因果的前提下删掉。

每次反馈后重新检查出点和入点附近的原音。不要在主播最后一个字、笑声尾部、操作音或结果显现前硬切。若两个保留区间之间有无关的长空档，切掉空档时应落在自然停顿；若中间的对话解释了“为什么又回去找”，就把桥接对话一起保留。

## 弹幕层

需要全量观众反应时，使用现有 `radioDanmaku` 路径读取同名 XML，并只投影到保留时间段：

- 不手挑少量弹幕冒充全量；
- 传统弹幕从右向左滚动，白字黑边等样式由运营要求决定；
- 同一版本使用统一 `scrollSeconds`，不要按文字长度随意改变飞行时长；
- 不能把弹幕结束时间截在视频尾点，否则片尾弹幕会被压缩成“瞬移”；允许事件结束时间超出视频尾点，让视频自然截断动画；
- XML 缺失或解析失败时应阻止请求的弹幕层，不要静默生成无弹幕成片。

实现入口：`src/workflows/clipping/radioDanmaku.ts`。它负责 XML 解析、保留区间投影、车道分配和 ASS 生成；精切脚本只需要提供源窗口、保留区间和样式设置。

## 审核清单

- 第一处目标物出现、主播意识到目标、找路、第一次结果、遗漏、回看和收尾是否按原顺序存在？
- 是否能仅凭成片听懂“为什么继续找、为什么漏掉第二个”？
- 每个出点和入点的对白、操作声、结果画面是否完整？
- OpenCV 候选是否经过三帧人工复核？是否排除了火焰、红色场景和 UI？
- 弹幕是否来自同名 XML，时间是否投影到当前时间轴，滚动速度是否统一？
- 片尾最后一条弹幕是否仍按完整时长移动，而不是一闪而过？
- 精切版本是否独立于原候选和已投稿视频，状态仍为 `pending_review`，直到用户明确要求投稿？
