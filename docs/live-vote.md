# 直播弹幕投票机器人

**推荐使用 [Yuiffy 的改版 mikufans / BililiveRecorder](https://github.com/Yuiffy/BililiveRecorder) 转发弹幕。**需要使用包含 `LocalDanmakuRelay` 和多房间转发功能的构建；官方原版和 fork 的旧安装包不一定提供这个接口。

如果不依赖改版 mikufans，独立运行需要使用 B 站直连来源。每个被独立监听的房间都会增加一条弹幕连接；与录播软件重复监听、多房间同时连接或频繁重连，都可能增加风控风险。推荐让 mikufans 维护已有连接，投票机器人仅通过一条本机 WebSocket 接收转发；这不会替录播姬新增 B 站连接。模式由配置显式选择，不会在转发断开后自动改为直连。

## 多房间模式（推荐）

录播姬 EXE 同目录的 `local-danmaku-relay.json` 使用 `"roomSelection": "auto-record"`（替代单房间 `roomId`），并设置 `enabled`、`port`、`token`。范围跟随录播姬有效的 `AutoRecord` 设置：勾选自动录制的房间纳入，取消勾选或删除房间立即移除，不替用户勾选其他房间。

投票机器人配置参考 `src/services/live-vote/config.recorder.example.json`：

```json
{
  "source": "recorder",
  "rooms": "auto-record",
  "recorderSocketUrl": "ws://127.0.0.1:17896/api/local/danmaku",
  "globalAdminUids": ["14279"],
  "botUid": "412141275",
  "maxMessageChars": 40
}
```

`14279` 为带鱼 UID，`412141275` 为鹿饼 UID；其他部署请改成自己的账号。无需手工维护各主播名单：本房间的主播 UID 来自录播姬已获取的房间信息，仅能发起/取消自己房间的投票；`globalAdminUids` 中的带鱼可在所有已纳入房间操作。房管和其他房间的主播不自动获得权限。主播 UID 尚未确定或弹幕断开时，不启动该房间投票。

各房间计时、选项和投票人去重互相独立；同一个观众可在不同房间各投一票。房间被移除、取消自动录制、主播身份变化或连接中断，会取消该房间投票并丢弃其待发公告；本机 WebSocket 断开会取消所有投票。所有房间共用发送队列，账号发言间隔至少 3 秒，多房间同时投票时播报可能排队延后，计票仍按各自截止时间结束。

认证可通过环境变量配置，也可显式提供绝对路径 `recorderSettingsFile` 读取录播姬转发配置的 token；真实发送可显式提供 `credentialConfigPath`，读取其中的 `bilibili.cookie`，环境变量 `BILIBILI_VOTE_COOKIE` 优先。发送前会重新读取显式配置的凭据文件，Cookie 更新后无需重启投票机器人；每次读取都验证账号与 `botUid` 一致。环境变量由进程管理器注入时，更新后仍需重启进程并更新环境。程序不会自动寻找生产凭据。`statePath` 可设为绝对路径，输出当前房间列表和连接状态，不含凭据。配置文件路径和凭据属于本机配置，不提交 Git。

多房间协议：`/api/local/danmaku` 首先发送 `rooms` 完整快照（`version: 1`，每房间含 `roomId`、`ownerUid` 字符串、`connected`），随后发送带 `roomId` 的 `danmaku` 帧；房间增删、自动录制开关、主播 UID 或连接状态变化会推送新快照。单房间端点 `/api/local/danmaku/{roomId}` 仍可使用，但只能连接当前纳入范围内的房间。

## 设计与边界

- 默认独立监听一个 B 站长房间号 (`source` 省略或设为 `bilibili`)。这是只读的直播弹幕连接，和录播姬各占一条连接；不自动改用录播姬或 XML。依赖 `blive-message-listener` 的 UID、文本与连接事件，不自行实现弹幕协议。
- 直连投票需要登录监听：设置 `BILIBILI_VOTE_LISTEN_COOKIE`，或复用显式设置的 `BILIBILI_VOTE_COOKIE`。监听 Cookie 须含 `SESSDATA`、`DedeUserID`、`buvid3`，HTTP 与弹幕握手使用同一个账号及已有设备标识。匿名连接虽然能收到文本，观众 UID 可能全部为 0，不能用于授权或每人一票，因此 CLI 缺少监听凭据时直接报错；dry-run 同样需要监听凭据，但不会发言。
- `source: "recorder"` 连接本机 BililiveRecorder WPF 转发，复用该进程已有的弹幕连接。服务只绑定 `127.0.0.1`，需要房间匹配和至少 16 位的随机字母数字 token；转发 UID、文本与收到时间，不包含 Cookie。这个模式需要部署并重启**改过源码的** WPF 录播姬；当前运行进程不会因为源码编译自动获得转发功能。
- `source: "xml"` 追踪录播姬弹幕 XML，仅适用于本机落盘且时间戳/UID 可用的场景。首次从文件末尾读，切换文件后从新文件开头读；来源停止更新时它无法识别断线，不推荐无人值守发言。
- 直连显式传入 User-Agent、Referer、Origin 和 Accept，避免 `tiny-bilibili-ws 1.1.0` 请求头合并时丢失默认 User-Agent。`getDanmuInfo` 返回 `-352` 只说明该次接口请求被拒绝，不能单凭它判断账号被封、整个 IP 被限制或需要验证码；应先核对请求头、签名和登录/设备状态。启动握手失败后机器人停止自动重试并以非零状态退出；录播姬自身的连接也受 B 站策略约束，复用不能绕过平台限制。
- 默认 **dry-run**：只打印拟发送文字。真实发弹幕必须加 `--send` 且提供独立 `BILIBILI_VOTE_COOKIE`，其中 `DedeUserID` 必须与配置 `botUid` 一致；切勿提交 Cookie。发送走 B 站直播发送接口，可能因账号资格、字数、频率或接口策略失败；失败就停止机器人，不补发或无限重试。

## 运行

需要 Node.js 22+；依赖用本项目的 pnpm lockfile 安装。先复制 `src/services/live-vote/config.example.json` 为本地 JSON 配置，换成实际**长房间号**和授权发起人的 UID，`botUid` 是鹿饼账号 UID。`source` 默认 `bilibili`，不需要录播姬端口。

启动前将监听 Cookie 注入 `BILIBILI_VOTE_LISTEN_COOKIE`（仅接收），或将同一账号 Cookie 注入 `BILIBILI_VOTE_COOKIE`（接收；加 `--send` 后才发送）。凭据不写进示例配置，也不会自动从本项目生产配置读取。

```powershell
pnpm install --frozen-lockfile
npm run build
npm run vote:run -- --config temp/live-vote.json
```

确认来源、UID 和输出后，才配置 `BILIBILI_VOTE_COOKIE` 并在命令末尾加 `--send`。生产运行请设置进程管理器和独立日志；不要在日志中输出 Cookie。不要拿现有录播/投稿 Cookie 当默认发言凭证。

本机转发模式的配置示例：

```json
{
  "roomId": "628684",
  "authorizedUids": ["123456789", "987654321"],
  "botUid": "1122334455",
  "source": "recorder",
  "recorderSocketUrl": "ws://127.0.0.1:17896/api/local/danmaku/628684",
  "maxMessageChars": 40
}
```

推荐在改版 WPF 录播姬 EXE 同目录放置 `local-danmaku-relay.json`，这样手工或守护程序重启均可启用：

```json
{
  "enabled": true,
  "roomId": 628684,
  "port": 17896,
  "token": "替换为至少16位随机英文字母或数字"
}
```

这是兼容的单房间配置，房间必须已配置在录播姬中；多房间部署使用前文的 `roomSelection`。token 属于本机凭据，不要提交 Git。启动投票机器人前，将文件的 `token` 读入 `BILILIVE_LOCAL_DANMAKU_TOKEN`，或显式配置 `recorderSettingsFile`；单房间的 `roomId` 和 URL 中的房间号须与文件一致。环境变量 `BILILIVE_LOCAL_DANMAKU_ROOM_ID`、`BILILIVE_LOCAL_DANMAKU_TOKEN` 和可选 `BILILIVE_LOCAL_DANMAKU_PORT` 仍可覆盖文件配置。文件配置在进程启动时读取，修改后需重启录播姬；多房间模式下在 UI 增删房间和切换自动录制会即时更新，无需重启。

转发器只订阅已有房间的弹幕和连接状态事件，不主动开启录制、额外连接 B 站或回放历史消息。未开播且录播姬没有监听时，WebSocket 握手仍可成功，但状态帧会是 `connected: false`；不能将本机端口已连接当成 B 站弹幕已连接。

WebSocket 以 token 作为子协议认证。连接后先发 `{"type":"status","roomId":628684,"connected":false}`；普通弹幕格式为 `{"type":"danmaku","roomId":628684,"uid":"123","text":"1","sentAt":1790259000000}`，时间是录播姬接收时的毫秒时间戳。每个客户端队列最多 256 条，积压溢出时断开该客户端，避免丢票后继续输出结果。

XML 回退示例：`"source": "xml", "recorderRoot": "D:\\recordings"`，目录必须是绝对路径。

## 弹幕规则

- 授权 UID 发 `#投票 1.复联2 2.法环`，默认 30 秒；`#投票60 1复联2 2法环` 或 `#投票 60 1、复联2 2、法环` 设置 60 秒。支持 2～9 个选项，编号可以是 1～9 或 A～I，同一场不能混用数字和字母。无需从 1/A 开始，也无需连续；时长 30-120 秒，选项名不超过 16 个 Unicode 字符。单独 `#投票60` 不会启动，因为没有选项。
- 三选项示例：`#投票 1复联2 2老头环 3美队3`。选项以“空格 + 编号”分隔，片名内数字直接跟随名称（如 `复联2`）；数字开头的名字可写成 `1.2048`。空选项、重复编号、混用编号类型、编号越界或超出 9 项会被拒绝。
- 字母示例：`#投票 A复联2 B法环 C美队3 D第三集`；只投 B/C 可发 `#投票60 B法环 C美队3`，跳号也可写 `#投票 A甲 C乙`。大小写、全角字母均可，播报统一显示大写，保留实际编号及命令顺序，不自动重编号。英文开头的选项名须用标点或空格分开，例如 `A.Apple Pie B.Banana`；单独的字母或数字出现在名称内且前面有空格时可能被识别为编号，应避免这种歧义写法。
- 默认每条最多 **40 字**，开始说明、票型、结果会尽量合并；超过上限才按选项拆分，保留名称和票数。可通过 `maxMessageChars` 配置为 20～40，具体上限取决于发送账号权限。每 10 秒更新一次票型，到点后留 3 秒接收时间戳在截止前的延迟消息，最后公布票数和胜者。
- 上述三选项会播报 `投票30秒，发序号：1.复联2 2.老头环 3.美队3`；中途例如 `剩余20秒~1.复联2:0票 2.老头环:1票 3.美队3:0票`；结束例如 `结束：1.复联2:0票 2.老头环:1票 3.美队3:0票 【老头环】胜~`。平票会列出并列选项，例如 `【复联2和美队3平票】`；若并列名称合起来超过单条字数上限，就分别用 `【】` 标出名称并附上 `平票`。无人投票会明确标注。
- 中途票型在完整消息能放进单条字数上限时，加上 `剩余N秒~`。剩余秒数按生成票型时距截止时间计算并向上取整；若加上倒计时会超长，则保留 `票型：` 前缀并沿用原有拆分，优先保留选项名称和票数，不为了倒计时增加弹幕条数。跨房间发送排队仍可能带来延迟。
- 观众的 `1`、`1111`、全角 `１１１` 都算 1；字母票的 `b`、`BBB`、`bBb`、`ＢＢＢ` 都算 B。只接受本次明确列出的编号：B/C 场次里 A、D、1、2 均不计票，数字场次也不接受字母。每 UID 只计**第一张**有效票，不接受 `BC`、`B B` 或夹杂其他文字，鹿饼自己的 UID 不参与。先发 `B` 再发 `C` 不会改票。断线时取消当前投票且不宣布不完整结果；重连后须重新发起。授权 UID 可发 `#取消投票`。
- 发弹幕节流至少 3 秒。文字在排队期间若断线/取消，会跳过尚未发送的旧公告；已经发到 B 站的消息无法撤回。票数只保留内存，重启或断线后不恢复。
- `#结束投票`：由本房间主播或全局管理员（带鱼）提前结束本房间投票，立即按已收到的有效票数结算，公布带选项名称的结果，不再等待原倒计时或 3 秒延迟窗口；后续票不再计入，原定到点也不会重复公布。待发的旧票型会跳过，结果仍遵守发送间隔。没有进行中的投票时不回应。
- `#取消投票`：同样需要管理权限，但只宣布取消，不公布统计结果。两种操作都只影响命令所在房间。

## 岁己直播提醒

提醒是可选模块，初版只支持 `source: "recorder"`、`rooms: "auto-record"` 的多房间来源，
只在配置的目标房间工作。把以下字段合入本机配置；示例文件默认关闭，已有机器人配置
不会自动启用。本机配置和状态文件不要提交 Git。

```json
{
  "reminders": {
    "enabled": true,
    "roomId": "25788785",
    "statePath": "D:/workspace/myrepo/danmaku-to-summary-ts/data/runtime/live-reminders.json",
    "notificationConfigPath": "D:/workspace/myrepo/danmaku-to-summary-ts/config/production.json",
    "startMinutes": 15,
    "endMinutes": 60,
    "minGapMinutes": 10,
    "quietMaxPerMinute": 12,
    "quietRatio": 0.5
  }
}
```

默认项目是 `medicine`（吃药）和 `lotion`（身体乳），各有三句短模板，每条仅提醒一件事。
吃药模板仅提醒按医嘱服用反流药，不判断当天是否需要服药或给出剂量。当前使用预制
模板，不调用 luna。配置需显式指定企微配置绝对路径，沿用主配置、secrets 和环境变量
的覆盖规则读取 `wechatWork.webhookUrl`；缺失企微地址或状态损坏会拒绝启动提醒。

每 30 秒通过 B 站房间信息接口读取直播状态和真实开播时间，不新增弹幕连接，也不
以机器人启动或弹幕连接时间充当开播时间。只有录播姬确认目标房间已连接并取得可信
主播 UID，才开始观察。开播后 **15 分钟（含）至 60 分钟（不含）** 才允许提醒。
不根据标题或分区判断内容，即使标题含 OP、游戏或同步视听，或分区为空，也不会因此
阻止提醒。内容阶段只采用上述时间窗口，不分析直播音视频。无法确认开播时间、下播、
断线或超过 45 秒未更新的直播状态仍会跳过。带鱼可用本场停止指令补充控制。

接通后至少观察一分钟弹幕。最近一分钟观众弹幕不超过 12 条，或不超过此前最多四
分钟平均频率的一半，才认为适合发送；机器人自己的弹幕不计入。阈值可配置，始终
没有低频窗口则本场跳过，不在一小时后补发。两个项目至少间隔 10 分钟；仍共用投票、
问答的发送队列和账号至少 3 秒发言间隔。排队至发送前会再次检查窗口、弹幕频率、
房间连接和关闭指令，过期公告不会发出。

仅配置的 `globalAdminUids`（带鱼）可在目标房间发以下单行指令，弹幕需在 10 秒内收到。
其他观众、其他房间、匿名 UID、机器人和过期指令不会改变提醒状态。

| 指令 | 行为 |
| --- | --- |
| `#关闭提醒` | 永久关闭上一条开始发送的提醒；没有上一项时提示指定 ID |
| `#关闭提醒 medicine` / `#关闭提醒 吃药` | 永久关闭指定事项，身体乳可用 `lotion` 或 `身体乳` |
| `#关闭提醒 全部` | 关闭所有自动提醒的总开关，后续直播保持关闭 |
| `#开启提醒 medicine` / `#开启提醒 全部` | 开启指定事项或总开关；总开关不会重置单项开关或当天发送记录 |
| `#停止提醒` | 停止本场剩余提醒，下次真实开播时间变化后自动恢复 |
| `#新增提醒 喝水` | 新增每天一次的事项，模板为“岁岁，记得喝水哦～”，返回 `custom-1` 等 ID |
| `#提醒列表` | 显示项目 ID、名称和开关，可分条发送 |

最多 10 个项目，新增项目成句需符合 `maxMessageChars`（20–40），重复名称不新增。
新增/关闭/本场停止均原子写入状态，重启后保留。每项目按上海自然日最多尝试一次，
同日断线、重新开播或重启不重复。发送前先持久化 `attempted`，明确成功后更新 `sent`；
网络超时或中途退出不能确认发送结果时，保留尝试记录并不自动重发。只支持一个机器人
进程拥有该状态文件，不要给多个实例共用同一路径。

发送成功后立即发一条企微文本记录，包含房间、事项、时间和原句；未确认的发送尝试
标明“发送未确认，不自动重发”。被取消的排队消息没有发送记录。企微失败留在本地
`notified: false` 和错误日志，不重发弹幕，也不自动重试通知。默认 dry-run 只打印弹幕
和企微拟发送文本，状态独立写到 `<statePath>.dry-run`，不消耗真实每天名额或改真实开关。
完成验证后需单独部署并重启 `live-vote` 才生效，验证构建不会启用提醒或更新生产产物。

## @鹿饼 录像问答

在已启用问答的房间发送 `@鹿饼 以前玩过法环吗？`，初版只接受本房间主播和配置的全局
管理员（带鱼），与投票权限一致。其他观众及其他房间的主播不会启动查询，也不会收到
确认或忙碌提示。单房间模式沿用 `authorizedUids`，多房间模式使用可信主播 UID 和
`globalAdminUids`，不自动授予房管权限。支持全角 `＠`，问题最多 120 个 Unicode 字符；仅接受以提及开头的
单行问题，拒绝控制字符、过期弹幕、匿名 UID 和机器人自己的消息。
授权用户只发 `@鹿饼`（含全角提及或末尾冒号）时，空闲回复一条提问格式提示，
忙碌则提示当前在查的问题；不调用模型，也不消耗查询名额。提示仍遵守全局提示频控。
问答与投票共用现有发送队列及账号至少 3 秒的发言间隔；取消/结束投票不会取消问答。

问答是独立可选项，旧配置行为不变。设置本机投票配置中的 `questions.enabled: true`，
填写 `providerConfigPath` 绝对路径和按房间号划分的 `recordingRoots`，例如：

```json
{
  "questions": {
    "enabled": true,
    "providerConfigPath": "D:/workspace/myrepo/danmaku-to-summary-ts/config/production.json",
    "recordingRoots": {
      "25788785": [
        "D:/files/videos/DDTV录播/25788785_岁己SUI",
        "E:/EFiles/Evideo/DDTV录播-E/25788785_岁己SUI"
      ]
    },
    "globalCooldownMs": 30000,
    "userCooldownMs": 120000,
    "noticeCooldownMs": 15000,
    "timeoutMs": 90000,
    "maxQuestionsPerHour": 20
  }
}
```

这里只展示要合入原配置的问答部分，连接来源、投票 UID 和发送凭据仍按前文设置。
`recordingRoots` 必须指向各房间的录像目录，不能使用磁盘根目录；未列出的房间不启用问答。
缺失或离线的归档目录会跳过。主配置通过共享配置加载器读取，沿用 secrets 和环境变量
的覆盖顺序，只使用 `ai.text.daiYu` / `ai.providers.daiYu` 的 endpoint、API key 和 proxy。
模型固定为 **daiYu 的 `gpt-6-luna`**，不受其他文本任务的模型配置影响，不自动切换 provider。
适配器接受 daiYu 仅含 `tool_calls`、省略 `content` 的工具调用消息，将其正文规范为 `null`；
缺少正文又没有工具调用的响应仍按无效响应拒绝，工具名称和参数继续经过原白名单校验。
同一个主配置还必须启用 `bilibili.delayedReply.summaryDynamic` 并填写鹿饼的汇总动态 ID。
`botUid` 必须明确配置，动态归属与发送 Cookie 均须匹配这个账号。
示例默认关闭；启用后即使是 dry-run 也会调用模型，dry-run 阻止所有真实弹幕和评论发送。
启动日志会明确显示问答是否启用；启用时仅记录固定 provider、模型和配置房间数量。
修改本机配置或 TS 源码后，需要部署编译产物并重启 `live-vote` 才会生效。
验收用 `build/service` 不会更新正在运行的 `dist/services/live-vote/runVoteBot.js`。
仅更新独立投票机时，先完成 `verify:all`，备份本机配置及原产物，再部署候选中的
`services/live-vote` 和 `services/bilibili/question-records`。共享配置模块须与已验证版本
兼容；不要混入其他服务的产物更新。保持现有入口及启动参数，只重启 `live-vote`，
确认新的问答启动日志和录播姬房间连接状态；不需要激活 workflow 或部署 webhook。

接受问题后只发一条确认弹幕：
`鹿饼收到，正在直播记录中查询“以前玩过法环吗?”问题的答案。`
问题太长时保留开头并加省略号。40 字账号使用完整句式；20 字账号缩短为
`鹿饼收到，正在查“……”的答案。`，保持单条确认，不拆成多条。

所有房间全局只允许 **1 个在途查询**，不积压待办问题。忙碌时回复
`正忙着查「玩过法环吗?」问题，请稍后再问`，较长问题仅显示开头。
默认查询启动间隔 30 秒、同 UID 跨房间间隔 120 秒、全局每小时最多 20 次；
忙碌/频控/拒绝提示共用 15 秒间隔，防止刷屏。可调整上述参数，但启动间隔不能低于
10 秒、同用户间隔不能低于 30 秒、提示间隔不能低于 10 秒，每小时上限不能超过 60。
90 秒超时会中止当前请求并发固定失败提示；在底层任务真正退出前仍占用唯一名额。
计数仅在内存中保存，进程重启会重置。频控命中时回复“查询频率较高，请稍后再问”。

检索只读取指定目录的顶层和 `YYYY_MM_DD` / `YYYY-MM-DD` 日期子目录中的 `.srt`、`.xml`，
不进入切片、临时目录，不读取配置、凭据或视频，也不重新 ASR、下载录像。
同名普通 SRT 优先于重复的 `.speaker.srt`，同一问题的后续关键词搜索复用已解析资料快照，
避免重复占用读取额度；下一次问题重新读取。
模型可按关键词/同音词以及年份、年月或日期搜索，再用已返回的证据 ID 查看附近上下文。
系统提供提问时的北京时间日期，让“这个月”“今天”等问题先限定检索日期。每个搜索命中
直接附带最多 5 条、每条 160 字符的简短上下文；线索足够时即可作答，避免额外模型往返。
候选先按关键词匹配排序，同来源重复文本及同文件相隔 20 秒以内的命中合并，每个文件
最多保留 4 个片段，每次返回最多 16 个候选，避免一段重复字幕占满列表。
XML 检索和上下文均排除配置的 `botUid` 发言、`@鹿饼` 提问以及确认/答案前缀，避免
把历史问答重新当作直播证据。字幕仍不能仅凭关键词判断说话者。
`read_context` 真正扩大到前后各 10 条、距离命中不超过 90 秒的上下文（合计最多 21 条），
每条最多 300 字符。搜索附带上下文和扩展上下文的每个条目都有自己的可引用 ID，
引用真正包含答案/改口的那句话。相同文件位置复用 ID，单问题最多 512 个。
每个问题最多 6 次只读工具调用；每次扫描最多 250 个文件，单文件最多 8 MiB，
整个问题累计读取最多 64 MiB、枚举最多 10000 个目录项。结果包含覆盖受限标记，
不能把一次未命中解释成“所有历史录像都没有”。无日期限制时优先近期资料，旧问题宜带年月。

### 查询规划、证据重排与补查

第一轮模型仅能规划并调用 `search_recordings`，选择具体关键词/ASR 变体、资料类型和日期。
随后每轮模型对候选做语义重排，返回最多 8 个真实证据 ID 的有序列表，再选择四种动作之一：
`answer`、`search`、`context`、`insufficient`。重排与答案生成/补查决策合并在一次模型请求中，
简单问题总共两次模型调用；复杂问题最多六次工具操作、七次模型调用，仍受全局超时约束。
搜索/上下文动作由应用白名单执行；复查阶段不接受模型额外的 function call。
模型必须区分直接陈述、观众猜测、否定/改口和日期不符；已命中主题而没有答案时先补查上下文，
关键词或日期不符时改词或调整日期。相同搜索（忽略键顺序和关键词顺序）及相同上下文请求
不重复执行，仍计入操作预算。最终引用必须选自模型的重排列表，未知 ID、重复 ID、额外字段
或无效动作均拒绝，返回无可靠依据。这是对引用范围的程序校验，不能证明模型的语义判断总是
正确；公开回答仍须保留归属和不确定性。
回答还须标记 `certainty: supported | uncertain`；只有猜测、未确认或“当时不知道”的内容属于不确定。
若模型将已有相关排名的片段判为信息不足或不确定的答案、却从未展开上下文，应用在预算内自动展开排名
第一的条目一次，再让模型评判；不会因此突破六次操作上限。日志以 `contextFallback` 标记此情况。

采用已有的有界工具循环，不引入新的 agent 依赖。官方 [Function calling](https://developers.openai.com/api/docs/guides/function-calling)
提供同样的“工具结果回传后回答或继续调用”模式；[AI SDK Loop Control](https://ai-sdk.dev/docs/agents/loop-control)
的轮数控制和逐步调整，以及 [LangChain 的检索验证模式](https://docs.langchain.com/oss/javascript/deepagents/retrieval)
可作为未来多工具/复杂编排的参考。本模块只有两个本地只读工具，迁移框架不能直接改善语料召回；
保留现有 daiYu Chat Completions 适配器，优先改进候选多样性、真实上下文和可验证的重排决策。

结论须引用工具实际返回的证据 ID。模型同时给出完整回答和用于弹幕的一句短答案；
最终只发 **1 条简答弹幕**，遵守 `maxMessageChars`，不带日期、时间点或证据展开。
简答统一以“鹿饼答：”开头，方便从普通弹幕中识别；前缀计入单条字数限制。
完整结果在鹿饼配置的汇总晚安动态下新增 **1 条评论**，格式为：

```text
直播问答（房间25788785）
问题：以前玩过法环吗?
回复：玩过，记录中提到打过玛尔基特。
线索：
1. 2026-10-01 00:01:02 录像字幕：我玩过法环，打过玛尔基特。
```

日期、时间和摘录由程序从已返回的证据 ID 生成，最多 3 条线索。模型不能指定动态、评论
目标或发送内容中的权限参数。公开摘录会过滤指令/凭据内容、控制字符和提及符号。
SRT 标为录像音轨的 ASR 字幕，可能含播放音频或其他人说话；
XML 为观众弹幕，不能混淆归属，也不能仅凭字幕确认主播本人。
没有有效证据时回复“没在录像字幕和弹幕中找到可靠依据”。房间断线、移除、主播 UID
变化或机器人停止会取消查询，丢弃未发送的回复；重连不会恢复旧问题。

详细评论由应用侧 `bilibili/question-records/QuestionRecordPublisher` 发送，独立于 agent 工具。
发送前核对固定动态的 ID、作者 UID、评论区类型和账号凭据；不自动选择其他动态。
真实发送前在 `data/runtime/live-question-records/` 保存独立意图，再标记 `publishing`；
成功记录评论 ID，网络超时或结果不确定保留 `unknown`，重启后不自动重发。
发布失败的完整内容仍保存在该目录，日志只输出固定错误，不额外刷失败弹幕。
详细评论阶段最多 30 秒，并继续占用唯一问答名额。dry-run 只打印拟发详细评论，
不会请求 B 站、写这个目录或改动现有晚安/回复队列。

查询日志的 `[question step]` 记录每轮模型/检索耗时和成功状态，以及模型复查的动作和重排条数；`[question query]`
记录总耗时、模型耗时、工具耗时、模型轮数及完成/失败/取消状态。诊断字段仅包含房间、
提问时间、阶段和数值，不记录凭据、路径、搜索文字或 provider 原始错误。
查询完成时间与 `[sent room ...]` 的弹幕发送时间分开记录；判断用户是否实际收到时，
还应核对录播姬接收的鹿饼弹幕，不能只凭发送接口成功日志推断展示结果。

复查 JSON、引用 ID 或输出边界校验失败时，整次查询最多允许一次格式修复，仍使用原证据和
同一套严格校验；不把非法输出作为提示词回传，也不放宽引用、长度或敏感内容规则。
再次失败进入“查询暂时失败”路径，不能伪装成“没找到依据”。固定 `validationIssue` 诊断码
区分 JSON、未知/未排名引用、长度、敏感内容、schema 和修复失败，不记录模型原文。
修复共享原任务名额与超时；不创建并行任务，最多增加一次模型调用。

数量问题的关键词召回会合并包含关系的同义词，避免“奶茶/喝奶茶/奶茶数量”重复加分。
`EvidenceRanking` 对已命中主题且含问题所问单位的数值加权，问年度数量时再考虑年度上下文；
这个加权仅影响候选排序，不把数字当成已核实结论。模型须区分平台账单、实际消费、
统计年份和录像年份，保留部分已知答案，不能把“比去年少几百”推算成精确总数。

安全边界由程序实施：工具只有 `search_recordings` 和 `read_context`，没有 shell、任意
文件读取、网络访问、写入或发送权限。路径完全来自本机配置，模型只能引用不透明证据 ID；
搜索参数逐项校验，拒绝额外字段和目录穿越，跳过链接/目录联接，打开前复核真实路径和文件。
endpoint 只接受 HTTPS 或本机 HTTP，禁止重定向；API key、发送 Cookie、绝对路径和
provider 原始错误不会进入模型上下文或公开回复。用户问题、字幕和历史弹幕都标为不可信数据，
明确的凭据/执行命令请求直接拒绝。证据 ID 校验不等于语义核实；ASR 错误或恶意历史弹幕
仍可能影响结论，系统提示要求核对上下文、保留不确定性，不能把输出当成管理员操作授权。

实现位于 `src/services/live-vote/questions/`；回归测试注入模型与发送适配器，不接触真实
provider、B 站弹幕或线上录像。聚焦检查：
`npm test -- --runInBand src/services/live-vote src/services/bilibili/question-records`。

## 字幕向量索引与每日维护

可选的 `questions.semantic` 在现有关键词召回之外增加字幕语义召回；XML 弹幕仍使用关键词检索。
最终证据仍由 daiYu 的 `gpt-6-luna` 复查。每个问题按需只生成一次查询向量，
各次日期过滤及所选房间复用该向量。单房间两路候选交错合并到最多 16 个命中，向量路最多 8 个。
向量只用于找原文，不能直接生成引用：必须重新读取配置根目录内的 SRT、验证 SHA-256，
再登记现有 evidence ID。字幕修改、文件删除、链接越界或版本不匹配都不会引用旧内容。
语义召回不保证覆盖全部历史，因此保留 `limited` 标志；接口/模型/索引不可用时继续关键词查询。

配置示例见 `src/services/live-vote/config.recorder.example.json` 的 `questions.semantic`：

- `backend: "local"`：固定 Python/ONNX 推理入口，使用中文 BGE-small v1.5 的 INT8 导出，
  512 维、CLS pooling、L2 归一化；查询加 BGE 中文检索 instruction，字幕不加。
  `model` 包含固定 Hugging Face revision，`modelDirectory` 指向本地快照。
  依赖 `numpy`、`onnxruntime`、`tokenizers`；可用 `huggingface_hub.snapshot_download` 安装
  `Xenova/bge-small-zh-v1.5` 的 `75c43b069aac4d136ba6bc1122f995fedcfd2781` 版本，
  只需 `tokenizer.json` 和 `onnx/model_quantized.onnx`。推理不下载文件、不执行远程代码、
  不用 GPU，CPU 限 4 线程、微批次最多 8 条。问答结束关闭子进程；建库批量复用进程，
  每轮更新结束释放，不为每天一次的任务常驻模型。
- `backend: "daiyu"`：使用 `providerConfigPath` 的 daiYu 凭据和 `/v1/embeddings`。
  需要该服务实际提供 embedding 路由，并配置实测可用的 `model` / `dimensions`；
  不能因为对话模型可用就假定 embeddings 可用。批次最多 32 条，响应顺序、维度、
  数值和范数均验证，超时 30 秒、禁止重定向，原始错误和凭据不输出。
- `directory`：绝对 SSD 目录；模型、维度、预处理/分块版本改变会使旧 manifest 不匹配，
  必须重建。不能用不相容的本地模型建库再用另一个远程模型查询。

分块按相邻字幕最多约 400 字、15 条、90 秒，重叠 1 条；引用定位在块中间的原始 cue，
需要时由现有上下文工具展开。索引保存每个原文件 SHA-256、日期、房间/根目录和 cue 位置，
向量是 float32 二进制分片，同版本下完全相同的字幕共用分片。查询按房间/日期顺序流读
256 行的小块，保留 32 个候选，不把所有房间的向量或模型加载进投票机内存。

操作命令（先完成编译部署）：

```powershell
npm run vote:index -- --config data/runtime/live-vote.json
npm run vote:index -- --status
pm2 start ecosystem.config.js --only subtitle-index-daily
```

`subtitle-index-daily` 运行 `--loop`：北京时间每天 **05:00** 更新；启动时检查持久化的
成功时间并补跑遗漏任务，失败 15 分钟后重试。每次读取最新配置，逐房间扫描固定根目录与
日期子目录；不递归媒体/剪辑目录，跳过 `.speaker.srt` 副本及链接。每次重新计算字幕指纹，
所以同大小/同修改时间的字幕校正也能被发现；已有相同指纹的分片不重复调用 embedding。
文件删除在新 manifest 中移除；离线根目录保留上次记录，标为 incomplete 并等待重试。
文件上限为 8 MiB，无法稳定读取的文件跳过并报告 incomplete。

单写锁覆盖整轮更新和守护进程生命周期，CLI 与守护任务不会同时建库。Windows 使用按索引
真实路径派生的命名管道锁，进程退出即由系统释放，状态文件里的旧 PID 被复用也不妨碍恢复；
其他系统使用独占的本机回环端口，冲突时拒绝启动，不接收任何命令。
每个完成的分片原子落盘，房间全部处理后原子替换 manifest；中途失败可复用已完成
分片；每完成 20 个文件发布带 incomplete 标记的检查点，让首次建库过程中也能查询已经
完成的部分。可用 `--first-room <房间号>` 指定首次优先处理的房间，其余房间继续全部更新。
旧分片在无任何房间引用且至少 7 天后清理。
`directory/status.json` 记录进度、成功/失败时间和下次执行时间；日志只记房间、数量与状态。
初次历史建库可能较久，可用 `--status` 或 `logs/subtitle-index-out*.log` 查看进度。
整个索引任务不会访问发布适配器、活跃工作流或剪辑队列。部署只更新 `live-vote` 与独立
索引进程，回退时关闭 `questions.semantic.enabled` 并重启 `live-vote` 即恢复关键词模式。

## 本机网页与 Codex 提问技能

[统一 Web 工作台](web-admin.md)提供同一套私有问答/证据检索，以及提醒项目、
模板、总开关、本场暂停/恢复和发送记录管理。网页管理指令由机器人 tick 接收，
保存已应用 ID 与原有每日发送 receipt 后返回生效回执；不会另起发送队列。

### 跨房间和舰礼资料

弹幕来源/网页选择的 `roomId` 是默认房间。`QuestionScope` 从问题中的明确主播全名、
名称中的中文前缀、配置别名或“直播间123”选择资料；没有点名则只查默认房间。
比较时写明双方名字；“你和某主播”同时查默认房间及被点名者。最多 3 个房间，超出拒绝，
不会扫全部资料或让模型指定新路径。当前是明确名称路由，不会推测没有配置的昵称或隐含人名。
`questions.roomAliases` 可配置 `{ "25788785": ["岁己", "小岁", "老岁", "SUI"] }`。
所有选择都限制在 `recordingRoots` 已配置的房间内；AI 在这个范围内规划关键词、日期与补查。

`QuestionCorpus` 顺序查各房间，复用一次查询向量，合并后最多 16 个命中；频控与 90 秒期限不变。
证据 ID 按房间隔离，命中、上下文引用、网页证据和动态详细回复保留 `roomId`、`roomName`。
来源房间不等于字幕说话人身份；嘉宾/播放音频仍须结合上下文判断。

“舰礼”按舰长、提督、总督礼物理解。关键词召回补入各档位和“礼物”，查询向量也补充这个语义，
无需重建字幕索引。问某一档时只回答该档；泛问则分别说明各档，不能自动推定继承低档礼物。

`questions.giftCatalogs` 将房间映射到可信操作员指定的本地 JSON 文件，例如岁己对应
`D:/workspace/myrepo/my-pixijs-game/src/data/gifts/sui.json`。本服务只读，不修改来源仓库，
也不请求档案中的 URL 或图片。每个问题重新读文件，因此另一项目补档后下次查询自动生效。
支持该项目 version 1 的 months/entries/sources 结构，文件上限 2 MiB；非法/离线文件降级到录像检索。
`all`、`subtitle` 检索舰礼主题时会优先返回档案，`danmaku` 仍只查弹幕。
档案证据 `kind=gift-catalog`，`catalogMonth` 表示礼物所属月、`date` 表示依据发布日期，
按所属月筛选，不把发货/回顾/预告日期当所属月。保留各档位、条件、官方/录播/仅线索标签；
“未收录”不等于“没有”，官方图片也不会自动升级录播或待核实条目的可信度。

CLI 额外返回 `searchedRooms`，索引覆盖统计合并所选房间；旧输入字段保持兼容。

`npm run vote:lab` 启动独立的本机问答页，默认地址 **http://127.0.0.1:15126**。
PM2 配置名是 `recording-question-lab`；部署后可用
`pm2 start ecosystem.config.js --only recording-question-lab` 常驻运行。
它读取 `data/runtime/live-vote.json` 的房间与问答配置，支持 `--config`、`--port`，固定只绑定
`127.0.0.1`。此入口不依赖弹幕连接，不导入发送器或动态评论适配器。

- **问鹿饼**：调用与直播机器人相同的 daiYu/gpt-6-luna 问答 agent，页面显示完整答案、
  日期/时间、引用摘录与耗时。每个问题独立检索，页面历史不会作为模型会话上下文。
- **只查证据**：不调用回答模型，直接返回关键词＋字幕向量召回结果，可限制日期和资料类型、
  指定关键词并展开原文上下文。索引文件数、是否完整和降级到关键词的情况随结果显示。

HTTP 校验固定 Host、同源 Origin 和页面令牌，拒绝跨站请求；令牌只发给本机页面，不是 provider
凭据。CSP 限制脚本、样式、连接和嵌入，证据/答案使用 `textContent` 渲染。JSON 请求上限 8 KiB，
只接受已配置房间、最多 120 字问题和白名单检索参数，不能指定文件或外部目标。
网页全局仅一个任务、任务间隔 2 秒、最长 90 秒；取消/断开连接会中止查询，底层退出前不会
释放名额。它与弹幕机器人的频控独立，避免本机测试改变直播间的冷却状态。

仓库技能是 `.agents/skills/recording-questions/SKILL.md`（`$recording-questions`）。
技能通过下面的 CLI 获取证据，随后由**当前 Codex 对话模型**整理答案，不调用 luna 回答。

```powershell
npm run vote:search -- --rooms
node dist/tools/live-vote/recordingQuery.js --input temp/my-question/query.json
```

输入 JSON 包含 `roomId`、`question`，可选 `terms`（1–5 个关键词）、`kind`
（`all` / `subtitle` / `danmaku`）、`date`（年/月/日或 null）和 `expandTop`（0–4，默认 2）。
CLI 在 stdout 输出一个 JSON 对象，含命中及上下文、检索耗时、索引覆盖情况，不输出本地路径。
单次超时 90 秒；纯关键词或本地 embedding 路径无需加载对话 provider 凭据。
词句可能含 ASR 错误，弹幕不等于主播发言；证据 ID 只在单次查询有效，引用应定位到实际支持
结论的上下文 cue，不能把邻近命中的中心句当作答案证据。技能和网页都不自动发送公开回复。
