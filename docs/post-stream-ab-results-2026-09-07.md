# 自动选材真实素材对照结果

## 范围与结论

用户在获知数据去向后回复“同意，可以测试”。本次仅使用 2026-09-05 岁己第 21、27、31 条已选片段实际范围内的字幕和弹幕：190 条字幕、646 条弹幕。未发送视频、未发布结果、未修改已有投稿。文本请求均通过当前 daiYu 网关成功返回，没有触发 tuZi 备用路由。

截至本轮：证据完整性和可复核性改善，本地阶段缓存及当前网关的隐式前缀缓存获得了真实验证；但“冷启动选材不变慢”尚未满足，不能将这批修改宣称为已经验收的整体性能优化。全量任务角色切换实验没有通过速度验收，已经撤回；保留由真实响应发现的数组解析兼容修复。后续文本提取与缓存修复已单独激活，见下文，不代表所有实验均已上线。

## 方法

- 相同三个源窗口，同一 `gpt-5.6-luna` 模型及 `high` 推理设置，没有降低模型或推理档位。
- 先测相同候选的重排，再测一次召回加重排。两阶段实验将三个窗口合在一个批次，不含未授权窗口的字幕/弹幕，不代表完整数小时直播的并发和排队分布。
- 旧版从 Git 基线读取；两阶段旧版只修复缺失的 `buildEmotionContextLines` 导入，以便比较原本工作的算法，不拿崩溃当作性能基线。
- 所有成功响应及阶段结果保留。部分早期运行未保存原始模型响应，不能解释其中“一条结果”是主动少选还是被校验剔除；随后增加了 proposed/accepted/rejected 诊断。
- 第一轮匿名 A/B 标签由脚本随机分配，文本核对后再打开标签对应文件。这不是独立人工盲评，时间戳精度也可能透露版本身份。
- 事实核对来自原字幕及相应弹幕，没有逐句复听真值。因此结论不超出源文本证据，也不报告整体标题准确率。

初版虽然输入减少约 6.0%，两阶段总耗时仍增加约 15.6%；总输入加输出从 27,928 降至 27,581，也不能用这点减少抵消用户明确要求的速度约束。

随后复用同一次已经成功的首轮召回，仅重做重排，避免为试验重复付费。以下不是新的完整冷启动测量：

| 修正 | 单次重排耗时 | 输入 tokens | 输出 tokens | 核对结果 |
| --- | ---: | ---: | ---: | --- |
| 复用首轮边界、来源及引用 | 48.324s | 10,104 | 2,507 | 更快，但将浴室写字与后来回写/没看到混成易误解的关系，不能验收 |

只将旧召回耗时或另一次新召回耗时与这些数字相加，属于跨次估算，不是实测冷启动结果。

测试中发现并修正的实际问题：

- 不再用首轮模型的事件标题/自然语言理由作为重排事实依据。保留本地信号码和原始模型结果供审计；重排读全文，不受“引用等于现编”等初稿误判牵引。
- 首轮边界、关键引用及来源只在源哈希、范围和引用均匹配时可复用；重排仍可显式覆盖。节目内容发生变化时，不能凭 ID 相同复用旧定位；观众引用还要匹配原始文本和时间。
- 文案提到观众或弹幕反应但没有弹幕引用时标为待审核。
- 拒绝未知候选、未知/未提供边界、非法文案类型、时长越界和串窗时，记录逐条剔除原因，不再只返回更少条数而没有诊断。
- 保留人物、转述、引用与原创、两次事件和前后回应的区分。源码里的 `linked` 仍只表示出处和时间关联通过，不是事实准确性的认证。
- 未胜出的命名字段、时间戳输出、逐候选内联排布开关已删除，避免实验分支增加生产复杂度。历史请求结果保留；测试脚本拒绝再次用这些失效开关冒充历史版本。

所有 stage cache warm replay 都没有新增模型请求，结果逐字和时间范围一致，用时约 8-10ms。这证明可避免重复运行同一阶段的消耗，不证明首次执行更快。

## 首轮文案实验

随后验证“首轮写完整文案，全局只排序或纠错”是否比先召回事件再重写更快，模型档位和全文证据不变，仍只用已授权的三段：

| 批次 | 执行顺序 | 旧版总耗时 | 文案复用实验总耗时 | 缓存重放 |
| --- | --- | ---: | ---: | --- |
| 17:41Z | 新版先 | 153.337s | 135.549s | 未通过，首轮弹幕引用没有完整进入重排表 |
| 17:47Z | 旧版先，补齐引用表后 | 105.604s | 267.499s | 未通过，首轮返回一条越界弹幕引用，缓存正确拒绝复用 |

第二批次中实验版输入共 24,060 tokens，输出共 14,717；旧版输入 21,811、输出 5,724。实验版首轮已命中 12,032 输入 tokens，仍不能抑制高推理长度引起的耗时波动。因此不能以第一批次较快就宣布成功，文案复用实验已撤回，不作为默认分工，也没有保留未使用的自动复用文案分支。

保留了由实验发现的引用传递修复：首轮弹幕使用稳定 D-ID，缓存校验必须验证 ID 实际提供给模型且落在片内；重排除自身样本外，还携带有效首轮定位已经引用的原始弹幕，防止丢失引用后重复调用模型。默认仍为首轮召回事件/证据、全局生成公开文案。

同时统一了提示词与原有时长校验：目标区间之外原本就允许最多5秒句尾容差，现在明确告知模型，不再要求它为了绝对整数上限反复调整边界。没有改变裁切校验数值或媒体参数，此说明变更尚未另做真实耗时对照。

排查还发现，直接把整个切片 worker 提前到漫画前存在文件生命周期风险：部分任务在切片结束或启动失败后删除源视频，而漫画截图可能尚未读取它。没有为了掩盖选材变慢而直接调整这条启动顺序；需要单独的媒体持有/释放契约及调度验收。

后续已实现临时硬链接保留、读者 PID 登记与保守回收，并通过真实文件/进程/FFmpeg 和编排回放检查。真实文本调度对照中，串行总耗时 188.365s、并行 159.938s，但漫画脚本由 47.419s 推迟至 56.351s，接受片数也由 2 变成 3。因此并行开关继续关闭，详情见 [安全并行记录](comic-clip-overlap-2026-09-07.md)。真实图片和压制耗时没有测量，不能用文本总耗时掩盖图文阶段推迟。

结果位于 `tmp/poststream-staged-2026-09-06T17-41-01-788Z/result.json` 与 `tmp/poststream-staged-2026-09-06T17-47-28-657Z/result.json`。失败的 warm replay 会标记 `identical=false` 和诊断，不能把其 7-9ms 当作有效缓存成绩。

使用人工构造文本，不使用直播内容，通过候选工作流请求格式连发两次请求，没有增加缓存等待或更改推理档位：

| --- | ---: | ---: | ---: | ---: | --- |
| 首次 | 1.574s | 3,685 | 0 | 3,685 | CACHE_OK_1 |
| 第二次，任务后缀变化 | 1.092s | 3,685 | 2,816 | 869 | CACHE_OK_2 |

两次前缀哈希相同；第二次约 76.4% 输入命中缓存。用量归因中 2,784 cached tokens 来自输入事实块，32 来自 instructions，不是此前仅固定系统提示命中的假象。显式断点此前被当前网关拒绝，改为兼容的隐式路由后已确认可以实际命中。

不把此比例泛化到所有直播、跨组织或跨 provider 请求，也不按官方标价估算此网关费用。

### 解析与内容核对

第二次调用成功返回完整 JSON 数组，而不是要求的 `{"clips":[...]}`。旧解析器报 `Missing clips array`，对照在第二次后暂停；该记录和原响应保留，没有重跑该模型请求。随后添加顶层数组兼容，本地重放恢复三条，再完成剩余两次原定请求。

现在对象包装和顶层数组共用同样的元素类型、候选 ID、时间、引用、文案及缓存校验；不是把错误结果直接当作合格片段。新增测试同时覆盖两种包装下的串窗、非法文案和未提供/越界弹幕引用。四次原响应本地重放均接受三条，引用关联检查通过，但 `linked` 不代表语义真值。

源文本核对仍暴露了更高层的文案风险：原请求第一次将两个不同的生活细节写得像一次刷牙回来同时发生，也把观众的作文使用意向写得过于确定；统一角色的对应描述较克制，但有一次将第三段结束在后续互相回应之前。这些差异说明不能仅用“3/3 接受”判断标题准确率或片段完整性。没有新增逐句听审或独立人工盲评。

### 保留与撤回

全量统一角色和未选中缓存时改变源分块的实验已从当前源码撤回，没有新增默认开关来保留失败实验。当前请求字段恢复到实验前；Responses/Chat Completions 各三种缓存状态共六组请求体本地深度比较均相同。原有已选中缓存请求的角色行为不变，缓存灰度可能影响角色的问题仍是待解项，不声称已经修复所有 provider。

保留数组解析修复，以及阶段缓存的请求协议版本失效机制。协议版本升为 3，防止以后复用版本 2 实验中的缓存结果。本轮远端测试关闭了阶段结果缓存，未产生可供生产复用的模型缓存文件。

原始文件：`tmp/live-role-ab-2026-09-06T19-29-04-661Z/result.json` 和逐次 `.log`；本地重放与用量归因：同目录 `analysis.json`。生成器当前返回值只保留汇总 attempts，完整 usage 从已保存的原始日志 JSON 解析，缺失值不视为零。工具为 `tmp/benchmark-live-role-20260907.cjs`，本轮总共四次远端请求，没有为了格式包装重复生成。

## 结构化输出对照

继续检查关键路径后确认：漫画开启时，45 秒预热窗口后仍会等待同一个梗概 Promise；它不是额外累加的固定 45 秒，直接删去这一层不会自动节省 45 秒，也不能删掉漫画所需的梗概事实约束。

此前固定请求耗时与输出量高度相关，约为每秒 55 个输出 tokens，但这不是对网络、排队或首包时间的单独测量。进一步检验同一强模型是否能借助 JSON Schema 减少格式和 ID 处理负担，没有降低 reasoning 或输出上限。

先用人工短文本做兼容探测。第一次请求未可靠保存结果，采集脚本提前读取 `node-fetch` 响应副本存在阻塞风险，该次用量记未知，不算零；修正为捕获调用方正常的 JSON 读取后，第二次返回 `SCHEMA_OK` 对象，约 1.871s，输入 4,435、输出 15 tokens，API 回传的 `text.format` 也确认了严格 Schema。

随后仍只使用前述三个授权窗口的固定提示词。四次请求分别为普通、Schema、Schema、普通；去掉唯一变量 `text.format` 后，请求体哈希完全相同。模型 `gpt-5.6-luna`、推理 `high`、输出上限 100,000 均相同，无备用路由或重试。Schema 只约束已有字段类型、提供过的候选/字幕/弹幕 ID、来源枚举和原有数量/分数边界，不删事实，也不要求多选片。

| 顺序 | 格式 | 耗时 | 输入 tokens | 缓存命中 | 输出 tokens | 推理 tokens | 接受片数 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 普通 JSON | 122.464s | 10,134 | 3,840 | 6,737 | 5,696 | 3 |
| 2 | JSON Schema | 128.058s | 10,644 | 0 | 7,049 | 6,317 | 3 |
| 3 | JSON Schema | 132.184s | 10,644 | 0 | 7,275 | 6,527 | 3 |
| 4 | 普通 JSON | 116.037s | 10,134 | 3,840 | 6,389 | 5,696 | 3 |

Schema 两次均通过标准 `jsonschema` 验证及现有片内证据校验，但平均耗时为 130.121s，普通请求为 119.251s，约慢 9.1%。正文输出虽然少了，推理输出更多；Schema 自身还增加了每次 510 输入 tokens，本批原有 instructions 缓存也没有命中。当前不将它加入生产选材，更没有保留一个默认开启的实验开关。

### 不能用结构校验替代事实审核

四次均为三条有效结构、引用检查通过，仍出现下列源文本问题：

- 普通请求第四次把“朋友先洗澡、写字”与“主播在另一次回写，朋友没去洗澡而没看到”写成朋友写字后没有洗澡的同一次事件；G139-G161 与 G169-G178 明确属于不同叙述段，写字主体也反转了。
- Schema 第三次写“被问文学性如何”，但 G70-G71 及提供的弹幕没有充分确定是谁向谁提问。属于证据不足的归属断言，不将其冒充已经复听确认的硬错误。
- 普通请求第一次把“朋友告诉写了什么”写成主播带看后亲眼发现内容；G156-G161 仍含“没有看到”，不能升级成无歧义的目击事实。
