# 鹿饼 QQ 群聊回复

`services/qqbot` 接收腾讯官方 SDK 的已认证消息；`tools/qqbot/run.ts` 装配凭据、
只读录播资料、固定文本模型和发送适配器。无需 DeepSeek Harness，亦不运行通用
coding agent。底层使用 `@tencent-connect/qqbot-nodejs` 1.0.5；扫码绑定可独立使用
`@tencent-connect/qqbot-connector` 1.2.0，手机 QQ 为官方机器人的管理者。

## 当前交互

- 群聊接收模式由 `groupMessageMode` 控制，当前示例配置为 `all`。QQ 平台开启“接收所有消息”
  后，`GROUP_MESSAGE_CREATE` 的普通群消息会进入独立的按日 JSONL 归档，不触发模型问答；
  同群有已完成待领取图片时，可借该消息的有效回复窗口补发已有结果。
  `GROUP_AT_MESSAGE_CREATE`，或 `GROUP_MESSAGE_CREATE` 中服务端标注 `mentions[].is_you=true`
  的消息仍按问答入口处理。昵称、普通文字“@鹿饼”、手打 mention 标记和回复引用均不单独
  触发。旧配置显式写 `groupMessageMode: "mention"` 时保留艾特-only 模式。
- 艾特问答会带上同群最近一小段归档上下文；需要较长范围的群聊总结时，agent 可调用
  `read_group_chat` 读取当前群已归档消息。群聊归档与问答记录分开保存，管理工作台的“QQ 群聊”
  页面可按日期、关键词查看，并用“删除更早归档”按日期永久删除旧目录。
  `groupMessageMode: "all"` 只决定本地是否归档普通事件；QQ 开放平台侧仍需为机器人开启
  “接收所有消息”，否则网关不会把普通群消息推送给进程。
- 生图请求先经过一次专用意图整理：整理器逐条读取近期消息的发言人、时间和内容，判断哪些消息
  真正承接当前用户、当前对象或当前图片；它会把其他发言人的独立生图要求排除，而不是按时间窗口
  机械拼接。整理结果再交给生图 agent，生图 agent 不开放未筛选的 `read_group_chat`；无法确认关联时
  只执行当前消息能确定的部分，并保留澄清标记。
- QQ 的消息范围是按群单独授权的群设置，由群主或具备权限的群管理者选择。常见选项为“获取群内全部消息”、
  “获取@机器人的最近10条消息”和“仅获取@机器人的消息”。机器人无法用本地配置绕过这个平台权限；
  其他群若尚未授权全部消息，只能等待该群有权限的管理者调整设置。群员询问时应先解释这一点，
  再说明鹿饼当前功能需要“获取群内全部消息”才能归档普通群聊并做长时间总结。
- QQBot 启动时会按需打开 `data/runtime/qqbot/knowledge.sqlite`，使用 SQLite/FTS5 保存本地维护的
  配置规则和使用说明，不启动额外数据库进程。Agent 通过 `search_local_knowledge` 检索启用条目；
  管理工作台的“QQ 知识库”页面可搜索、编辑、停用和删除条目。知识库只保存脱敏后的确认规则，
  不保存截图、群号、QQ ID 或原始群聊内容。
- 私聊仅接受 `C2C_MESSAGE_CREATE`，回复配置中的固定进群引导；同一私聊用户每十分钟
  至多提示一次，不检索资料、不调用模型。未配置具体群号时不会虚构邀请链接。
- 每次群聊提问独立运行 OpenAI Agents SDK（`@openai/agents-core`）的 `Agent` / `Runner`，
  复用鹿饼人设，由模型选择资料或图片工具、读取结果、补查后回答；可以零工具直接回复，
  不按生图关键词分流，也没有固定工具步骤。`QQKnowledge` 每题创建
  独立的房间范围、证据 ID 和工具闭包，不再先按关键词跑固定的 `CommentKnowledge`。
  保留资料日期、房间和覆盖标记；不读取 B 站账号凭据，不改变共享索引。
- 空艾特返回使用提示。启用 `images` 时，agent 可选择专用图片接口，使用
  `ai.streamerRegistry` 的名字/别名和 `public/reference_images` 的其他具名角色参考图，
  多名角色分别带参考图；明确的新图要求直接执行，无需固定确认口令；
  支持引用图片或同条消息附图后提出明确改图要求。未启用时返回准备提示。主动聊天及定时消息仍未实现。
- 每次被动回复都会同时携带触发消息的 `msg_id` 和 `message_reference`。前者保留 QQ 开放平台的
  回复窗口与幂等关联，后者让文本或图片在 QQ 客户端中显示为对应发言的原生引用；排队后仍按
  原始消息 ID 回复，不会把回答挂到同群稍后到达的另一条消息上。

## 配置与命令

### 视频生成、草稿确认与领取

`videos.enabled` 启用现有 Seedance 队列的 QQ 入口，`videos.queuePath` 指向同一队列文件。

视频正式入队与草稿确认在 QueueStore 同一事务内检查独立于图片的次数账本：普通用户滚动5小时10次、
每天30次、全局每天300次、全局启动间隔60秒；每日按上海时间零点更新，滚动窗口跨天继续生效。
配置了图片额度时，视频沿用其 `dailyLimit/userDailyLimit`。保存/修改草稿、查进度、领取不计次，
直接生成或确认草稿成功入队才记录 `qq_admitted_at`，后续失败不返还入队次数；消息重放不重复计次。
历史已入队任务缺少该字段时使用 `created_at`，草稿及未入队的取消草稿不计入额度。

`mediaOperators[]` 为可信配置中的 QQ 用户 SHA-256 标识列表，和回执的 `user` 字段一致；不能填昵称，
不能从群消息、模型参数或角色名取得权限。配置中的运营者图片/视频各自允许滚动5小时50次、每天150次、
视频个人启动间隔10秒；图片不设置单张启动间隔，按下述滚动调度执行。对应媒体全局每日额度仍有效。
普通用户最多1个未完成视频（跨群合计），运营者最多4个；视频全局24个活动任务上限继续有效。
默认领取和查询始终选择本人本群最新创建的任务，不因旧片未领取而回退；最新任务排队、失败或待确认时
返回该任务的状态。旧任务缺少 `qq_admitted_at` 也遵守相同规则。QQ 确认发送后只为实际发送的任务写
`qq_delivered_at`，重复领取仍返回最新任务，不轮换到旧片，也不覆盖其他任务。
运营者生图最多4个同时生成，普通用户共用2个并发位，总并发最多6个；所有用户明确的新绘图要求
均不被旧图领取拦截，后台受理后立即释放串行消息 worker，按原窗口自动回图与同群后续补发规则交付。
明确生图命令每用户入站待处理上限至少20条；普通聊天运营者至少8条，其他用户使用 `maxUserQueue`。文本预算与平台发送间隔继续生效。
`qq_ready.mediaLimitsVersion: 1` 标识媒体身份规则，`imageQueueVersion: 1` 标识已加载持久化图片等待队列。
不要把积分到期日当作公历每月固定日期，也不要据此自动切换未知的下一周期规则；以账号实际页面为准。
新 QQ 视频任务使用已登录的 `dreamina-canvas`；旧任务继续使用原 Dreamina CLI。
Luna 在现有工具循环内整理创意、镜头、台词、素材名和设置，不另启创作代理。
仅开放 `seedance2.0fastvip`（内部 `seedance2.0fast_vip`）和 `seedance2.0mini`，
默认 Fast VIP、720P、9:16、15 秒；720P 固定，时长可在 4—15 秒内调整，支持目录中的六种比例。

常用说法：

- “生成小花帽岁己散步的视频，mini，横屏16:9，10秒。”
- “生成单马尾无外套JK转身的视频，用岁己的声线。”也可在同条消息附多张图片。
- 默认先返回草稿，逐项展示图片／声线名称、模型、比例、时长和完整 prompt。
  `draft` 不参与调度，不上传素材、不报价、不扣生成积分。
- “修改视频：改成8秒，镜头拉远。”读取本人本群最新草稿，保留未改设置与原附图，重新展示。
  新草稿替换旧草稿，旧草稿成为 `cancelled`，两者都不会自动运行。
- 检查后回复“确认生成视频”或单独“直接生成视频”，才将本人本群最新草稿改为 `pending`。
  在完整创作要求中写“直接生成……的视频”可跳过草稿，直接排队。
- “领取视频”“查询视频进度”仅查询本人本群最新任务；完成后通过当前艾特消息的被动回复窗口发送视频。
  任务受理不表示完成；排队较久时需再次艾特领取，不主动跨窗口推送。

自动引用与生图共用 `QQImageCatalog` 和最长重叠别名匹配。具体衣装替换同角色基础参考，
其余角色保持独立。无需用户附图即可使用自备角色参考；视频工具选择支持素材库完整名称和
已登记的唯一别名（忽略大小写、首尾空格和全半角差异），并将草稿保存为完整素材名。
生图工具和生成器使用同一解析规则，入队前统一为完整名称并去重；查询多个角色时，
直接匹配的角色优先于附带展开的皮肤，避免12项返回上限挤掉本次请求的角色。
完整名称优先；未知、部分名称或存在歧义的别名要求重新查询，不猜测素材。
最多 9 张图片（含附图与角色参考）、3 段视频、3 段声音，合计最多12份；无参考时使用文生视频，
声音参考必须同时有图片或视频。附图沿用可信 QQ 下载／解码适配器，模型不能指定文件路径。
附带或引用的视频由 `QQVideoInputPolicy/Inputs` 独立处理，视频引用不再被当作缺失图片回执。
只下载鉴权 SDK 附件中的白名单 QQ CDN 地址，不读取正文 URL；拒绝重定向，每段最多50MiB。
本地 `ffprobe` 校验 MP4、单段2—15.4秒、宽高200—2160像素，总视频时长最多15.4秒。
超限或下载失败明确告知本次未提交，不抽帧、裁剪、忽略视频或换成无参考生成。
原视频保存在既有 `video-inputs/<AppID>/<请求哈希>` 运行时素材目录；草稿修改保留视频路径与时长，
模型只看到素材名称和设置。`qq_ready.videoReferencesVersion: 1` 标识视频引用支持已加载。
模型首轮说明明确给出当前视频引用数量与绑定状态；`read_video_sources` 可只读查询此状态，
不下载、不观看视频、不付费，也不将附件绑定误报为格式校验通过。误调用图片读取时仍提示
视频引用存在；只有正式提交时的下载与探测决定视频是否可用，不因缺少图片要求重发视频。
`qq_ready.mediaSourceAwarenessVersion: 1` 与 `imageCharacterAliasesVersion: 1` 标识这两项入口修复已加载。
队列新增可选 `video_references`、`video_durations_ms` 与稳定 `canvas.videoResourceIds`，
Canvas 按视频资源上传并将 `@Video N` 绑定到对应公开资源身份，使用多模态模式；旧任务兼容空视频列表。
领取已暂停的任务时区分参数校验失败与生成服务不可用；领取本身不恢复或重试生成。
`videos.voices[]` 维护已授权声线样本路径、名称及别名；缺少对应样本时拒绝声线请求。
声音只约束声线，台词以本次要求为准。当前示例收录岁己的一段约 9 秒音频。

Canvas 身份与旧 CLI 登录态独立。账号校验失败回复检查登录，不能将旧 CLI 的匿名零余额
误判为“没积分了”。远端结构化错误明确指出积分不足时回复“没积分了”；未知错误保留为需检查，
不凭本地化错误文案猜测余额。视频积分已由管理员统一授权自动处理：按最新权威报价
自动取得积分凭证并提交，不再要求群用户回复“确认视频90积分”。创作草稿预览确认仍保留。
旧积分暂停任务只有 sidecar 确认尚未运行、且没有在途提交／预留时才恢复原任务；未知提交继续核对原 ID。
每次报价与运行意图按原 submit ID 原子记录到任务的 `credit_usage`，昵称作为独立展示字段保存，
不改变本人本群的摘要归属。Web“AI 视频”页按用户汇总提交报价上限、待核对积分及缺价历史；
当前接口不提供最终结算／退款账本，不将报价称为实际净扣费。
积分凭证仅留内存，不写队列、日志或 QQ 回复。

服务端视频草稿最多 4500 个 Unicode 字符；公开发送检查与问答存档共用
`QQ_RECORD_ANSWER_CHARS`，管理 API 也按同一上限读取。普通模型回答仍限 300 字。
调整草稿容量时须同步部署 QQ 独立目录与管理 API 中的共享记录校验模块，
避免草稿在发送前被旧存档契约拒绝并停止服务。
草稿超过 1200 字时按段落或句末优先拆分，单条最多 1200 字、最多四条，附“（1/4）”等序号；
去除序号后可逐字还原完整草稿。每条都引用同一原消息，共用五秒发送间隔与四分钟内部窗口。
每个分段均需有效发送 ID 才继续下一条；失败或过期即停止，部分发送不会自动从头重放。

明确的生图、改图命令先检查等待队列容量和个人/每日图片额度，已知队满或额度不足时直接回复原因，
不发送处理回执、不调用规划模型，也不预留图片或文本额度；工具执行前仍复查准入与额度。
通过检查的生图、改图、视频创作、修改或确认命令通过文本额度检查并持久化后，先回复一次
“收到生图要求，正在处理。”或视频处理提示，再交由原 agent 处理。提示只表示收到要求，
不声称已经生图、视频已入队或扣费；帮助、闲聊、领取结果及额度拒绝不发送此提示。
接收提示有独立的持久化发送意图；回执不明时暂停且不继续调用模型，明确的平台业务拒绝
不重发提示，仍可继续处理本题。`qq_progress_sent` 与最终 `qq_reply_sent` 分开记录，
`qq_ready.replyProgressVersion: 1` 和 `multipartReplyVersion: 1` 标识已加载。

队列通过固定 Python bridge 和原 `QueueStore` 锁写入；每条请求固定一次任务，
每位用户在当前群最多一个未完成任务，全局 QQ 未完成上限 24。提交前持久化全部公开标识，
有歧义的付费提交只查询原操作，禁止自动重生。完整草稿由服务端交付，独立于普通 300 字限制，
仍检查凭据、路径和提及标记。Web“AI 视频”页只观察队列与历史，不代用户确认或重试。

### JK 与地雷素材

新增素材来自本机“岁己JK服”目录的六张非半身 PNG，复制原始文件到 `public/reference_images/`：
单马尾无外套JK、地雷岁双马尾黑外套、地雷岁长发双啾啾、小揪揪外套JK、
小粉帽外套玩手机JK、小粉帽无外套椭圆嘴。映射维护在 `images.characters[]`。
生图、生视频均支持具体素材名；“JK岁己”默认单马尾无外套，“地雷岁己”默认双马尾黑外套，
“小粉帽”默认小粉帽外套玩手机JK，“地雷帽”默认地雷岁双马尾黑外套；
指定其他具体造型时以具体造型为准。默认岁己形象保持现有参考。

示例为 `config/qqbot.example.json`。所有相对路径以项目根目录为基准。
示例通过 `secretConfigPath` 直接读取 Git 忽略的 `config/secret.json` 中的专用 `qqbot`
分组。扫码取得的 AppID/AppSecret 与专用 sub2api key 在这里统一维护；不要打印或提交
真实凭据。仅在受跟踪的 `config/secret.example.json` 留占位结构：

```json
{
  "qqbot": {
    "appId": "替换为扫码取得的 AppID",
    "appSecret": "替换为扫码取得的 AppSecret",
    "keyName": "qq鹿饼用",
    "baseUrl": "http://127.0.0.1:8080",
    "apiKey": "替换为专用密钥"
  }
}
```

兼容旧配置的 `credentialsPath` 和 `providerConfigPath` 两个独立 JSON 文件；配置了
`secretConfigPath` 时只读中央分组，缺失字段不会回退到旧文件。密钥更改后需重启 QQ 服务。
Web 配置编辑器会隐藏 `appSecret` 和 `apiKey`，保留遮蔽值即可保持原密钥。

文本模型固定为 `gpt-6-luna`。QQ 专用字段直接读取，不合并全局配置、其他 provider 的密钥或
环境变量，防止无意用错 sub2api key。endpoint 必须为 HTTPS 或本机 loopback HTTP。
模型上下文不包含密钥、QQ openid、消息 ID 或其他群消息。

### 问答与图片 agent

采用 SDK 的标准工具循环。`QQAgentModel` 实现 SDK 的 `Model` 适配器，保持现有
专用 daiYu endpoint、代理、固定模型及可注入 HTTP 传输；生图请求会先运行一次受限的 `QQImageIntent`
整理 pass，再运行图片 agent；两阶段共享同一模型调用和字节预算。不添加 shell、任意路径或发布接口，
图片后台任务仅对明确的 502/503/504 上游 HTTP 失败自动重试一次，其他付费请求不自动重试。SDK tracing 在每个 Runner 上关闭，查询过程
仅保存在本地问答记录。框架接口见 [Agents SDK models](https://openai.github.io/openai-agents-js/guides/models/)
与 [running agents](https://openai.github.io/openai-agents-js/guides/running-agents/)。

没有搜索密钥时网页工具报不可用，不影响行情等固定来源。公开查询结果也用 `basis=evidence` 和实际证据ID，
不伪装直播资料；各题网页ID隔离，不授予任意URL访问。公开查询无须初始化录播语料。
QQ 示例启用 `knowledge.allConfiguredRooms=true`，使用 `runtimeConfigPath` 中
`questions.recordingRoots` 的全部已配置主播；每题仍按提问中的主播名或 `roomAliases`
选择最多八间房，未指名时使用 `roomId`，不会全库扫所有主播。未启用时兼容原来的
`roomId` 加 `collaborationRooms` 白名单。录播目录名会提供完整主播名和中文简称，
其他昵称需在 `roomAliases` 显式配置。泛问主播情报时优先查直播概述；没有生成概述时，
继续浏览该主播的 ASR、弹幕，不能把“没有概述”解释成“没有资料”。此设置不改变 B 站评论范围。
直播资料对象仅在实际调用资料工具时初始化；检索房间限制不会在绘图、看图或普通聊天之前抛错。

其他工具仍可用。没有资料配置时仍可直接聊天；帮助和普通聊天也由 agent 判断，不强制检索。
工具参数错误或读取失败作为固定、不含原错误路径的反馈返回，允许 agent 修正或换工具。
“上次玩某游戏/何时做过某事”优先用主题词搜索历史正文，不以最新概述代替；
正式名称问题先按主题、简称或同音变体查指定日的字幕/弹幕，再展开上下文。
原文仅重复问题里的叫法不能证明正式名称；继续核对命名、英文名或商店标题线索，
仍无证据时区分已确认的直播叫法与未确认的正式名称。
目录与开头/抽样预览仅提供线索，未搜正文不能据此宣告未找到。命中游戏名仍须区分
推荐、回忆与实际游玩；索引覆盖不足时只能报告已查到的线索，不能断言最近一次。
同一操作不重复 IO；每题最多 9 次模型调用、8 次工具操作，每次只执行一个工具。
轮次上限由共享 `QQ_AGENT_LIMITS` 约束，调整时同步部署 QQ 运行闭包与管理 API 的
记录校验和额度策略，保证较长调用链仍可归档并在网页读取。
预算按完整请求 UTF-8 字节数保守预留；继续检索前另留下一步结果及最终答案空间。
最终作答禁用工具并省去工具 schema，避免重复发送和预留无用的 schema 挤占检索预算。
每步资料最多 6000 UTF-8 字节，并按本轮实际剩余作答预算进一步收缩；预留时计入
工具 JSON 嵌入下一轮请求后的转义开销。缩减完整记录并附 `truncated`，不截坏 JSON。
最终结构化输出包含公开回答、回答依据类型和证据 ID；事实答案必须引用本题实际保留的
工具证据，资料不足的回答也可引用已确认的局部线索；所有非空引用都须校验，未知 ID
会导致生成失败，聊天常识的引用必须为空。图片工具不直接发送，返回生成、拦截或失败回执；
worker 持久化图片后，与最终单段文本合成一次被动回复。图片和资料工具共用上述次数上限。
意图整理 pass 获得当前消息、带发言人标记的近期群聊和是否有原图的元数据；有同群上下文时会复用
受限的原图预览帮助判断“这张图/上一张图”的指代。图片 agent 仍按需调用 `read_image_sources`，
成功后回答模型会接收真实 JPEG 预览，原图字节由服务端交给图片编辑模型。

`questions/LiveOverview` 只读配置录播根目录及其日期子目录，每根最多最近 14 个日期目录、
每目录最多 10000 个条目，至多尝试 48 份产物；不递归扫描媒体或切片目录。
按录制文件名时间排序，支持 DDTV 与历史下划线时间命名，不用复制/生成的 mtime 判新旧。
返回最近有可用概述的同一录制产物，以及目录中最新已见录制时间，两者不能混作真实开播历史。
跨零点的新片段不自动算另一场；最新也不等于查询当天。指定日期缺资料不会借用其他日期。
只接受 `_LIVE_CONTENT.json` 的成功 v1 同房间结构化内容，剥除晚安 Markdown 的 front matter，
漫画只取叙事与画内文字，不取绘图指令；成功梗概优先，其次同场晚安、漫画，缺少时可用精选摘要。
生成概述可支持内容概括，不能充当主播逐字原话，精确引用仍需回查字幕。

### 参考图生图

`images.registryConfigPath` 指向受维护的角色配置（示例 `config/production.json`），
只读取原始角色注册表及 `ai.roomSettings` 的角色参考图、名字和描述，不合并凭据配置。
新图正文中的角色名字、昵称和别名匹配参考图；英文别名
按单词边界匹配。同图最多八个角色参考；匹配到一名角色不证明同一要求中的其他角色已识别。
可用 `images.characters` 补充显式名字、别名、外观描述和图库内路径。
图库独立收录“饼干岁人”，“饼干岁人 / 饼干人 / 饼干岁”均指向
`binggan_sui_humanoid.png`：整个头部是戴皇冠的圆饼干，脖子以下为正常人类身体。
该图原样取自 AI 视频 `binggan` 常用参考《饼干岁人2.png》，运行时使用仓库副本，不依赖本机素材路径。
改图时服饰可保留，但必须完整替换成饼干头，不能画成人脸加饼干装饰。
“恶魔饼干岁”单独使用 `岁己SUI小猫帽带饼干岁紫色外套双马尾.png` 右上方的小饼干角色，
不作为饼干岁人的通用参考。同位置重叠别名取较长者，分开提及两者时可同框；精确查询优先返回对应角色。
只要求饼干角色时不加入岁己。参考文件缺失时不提供对应条目。
同一角色的皮肤可在该列表补充 `baseCharacter`（默认角色的完整 `name`）和 `skin`（皮肤名），
两个字段须同时提供。示例维护岁己的小红帽、小花帽、小蓝帽和小猫帽，均来自本机已有参考素材；
小花帽全身立绘与小蓝帽三视图已纳入 `public/reference_images`，无需依赖机器外部路径。
`find_image_characters` 查询“岁己”可列出默认形象与皮肤，查询“小蓝帽”等名字可直接定位，
结果提供名字、外观、皮肤名与归属，不暴露文件路径；只询问参考时不调用生图。
绘图时 `characters` 选择返回的完整名字，如“岁己·小蓝帽”。原始要求明确提及皮肤时，
服务端补齐对应参考并替代同一身份的默认图，避免模型漏选或混入默认衣装；其他角色保留。
未指定皮肤的“岁己”仍用原有默认参考。明确指定两套皮肤同框时分别带图，不融合造型；
改图中指定皮肤视为衣装、发型与配饰要求，仍保留原画风构图，用户明确要求保留服装等细节时优先。
同次请求会收集全部命中角色，以独立的 `image[]` 文件字段上传，并在提示词中逐张编号绑定角色，
支持三人以上同框，仍受八张参考图上限约束，不会只取第一个角色。多角色分别保留外观和动作关系。
简称与完整账号名不一致时，应在受维护的 `streamerRegistry.aliases` 显式补齐，
不从长中文名字任意截取短名。例如阿梓的“阿梓 / 梓神 / 阿梓从小就很可爱”均绑定
`azusa_standing.png`；“七海使用魔贯光杀炮攻击阿梓”会同时附带七海和阿梓各自的参考图。

新图绘制意图由 agent 判断；用户直接发送“生成岁己和栞栞在摔角赛场上对战的图片”
或“帮我画一个星汐”等明确要求即授权本次绘图，无需再按固定格式确认。
图片工具、worker 和生成适配器在付费调用前复核原始正文中的绘图要求；
只有“确认”、引用示例、否定绘图、询问用法或未说明主体的空泛请求不会授权新图。
这些请求不预留图片额度或启动间隔；agent 规划与说明仍消耗文本预算。
保留兼容格式 `确认按描述生图：完整绘图要求`，中英文冒号均可。
未匹配的具名角色仍须说明外观不确定，不把猜测当成已核实设定；不因陌生角色要求重复确认。
不从未整理的群历史或其他用户的确认补全请求。整理器按每条消息的发言人和语义关联选择上下文；
其他发言人的图片属性不能跨人继承。原有限额和安全检查保留。
参考列表由 CLI 装配给 agent 工具与 worker，生成前仍按可信图库复核；新图正文明确命中的
已知角色不会因模型漏选而丢失参考图，模型另选的角色也必须来自图库。确认前缀不会进入绘图提示词。

例如发送“生成三理穿宇航服站在月球上的图片”会直接带三理参考图，复用晚安图的身份一致、
精细画质、自然比例规则，再加入用户指定的场景、动作、服装和风格；不会擅自添加
晚安文字或虚构直播事件。仅有本机 `public/reference_images` 下的参考图可上传。
有参考图使用 `/v1/images/edits`，无参考图使用 `/v1/images/generations`，两者都用
中央 `qqbot` 分组的专用 key；普通图片示例模型为 `gpt-image-2.5-sunburst`、`high` 质量。
明确说“GIF”“动图”“动画”或“让它动起来”时，服务端选择 `images.gifModel`（示例为
`gpt-image-2.6-sunburst`），请求 `output_format: gif`，并校验上游确实返回至少两帧 GIF；
只返回静态图会作为失败提示，不会悄悄按 PNG 发送。GIF 文件沿用图片额度、后台领取、
发送回执和管理页预览链路，存档扩展名为 `.gif`，普通 PNG 行为不变。
GIF 输出还依赖上游账号对 GIF 预览能力的开通；账号未开通时上游会返回
`GIF output is not enabled for this request`，机器人会明确提示改发“静态图”，不会把它误报成普通
HTTP 400。增加输入拼图的帧数只能改善模型对动作顺序的理解，不能绕过这个账号能力限制。

### 引用图片修改

未引用图片时，也可通过同群近期图片承接看图或改图。`QQRecentImages` 在已接收的群图片事件中
保存可信附件关联，机器人成功发送图片后保存原图回执；私有 sidecar 位于
`data/runtime/qqbot/chat/<AppID>/<北京时间日期>/images.jsonl`，与对应日期的群聊归档一起删除。
普通消息不触发模型回答或生图，仅在同群有待领取成图时允许补发；mention 模式仍只处理艾特消息。
此索引从部署后开始记录，不补抓平台未推送或此前未索引的图片。

当前消息没有原图时，agent 可调用 `read_recent_images`，查看同群、不晚于本次提问、
最近30分钟最多3条图片消息及其真实预览，再用 `select_recent_image` 绑定一个已成功读取的候选。
每条候选仅预览第一张，并返回总图数；选中后读取该消息全部原图。当前附图或明确引用始终优先，
读取失败也不偷偷换成历史图。候选唯一且语义吻合可直接承接；多图指代不明时先询问是哪张，
不能只因最新就绑定。过期、跨群、跨应用、未来消息、任意文字URL和纯引用不进入候选。
附件失效时返回不可用；不按描述重新捏造原图。

选图仅授权读取；只有当前用户要求修正或承接当前修正意图才可编辑，点评和画面问题不触发生图。
其他群友的独立绘图要求不得继承。模型只获得本题候选ID、发言人类别、时间、配文与受限JPEG预览，
不获得附件URL、平台标识、磁盘路径或原图字节；私有索引不进入普通群聊工具JSON。
绑定后不可在本题切换原图，worker、后台任务与编辑适配器共享所选原图和读取缓存，
继续执行原有一次图片尝试、额度及发送收据规则。稍后领取的生成图以实际原任务PNG定位，
不会误用领取消息的日期或键。

在 QQ 中引用要改的图片并艾特机器人，例如 `@鹿饼 改成一前一后抬棺`，或将原图与
`把背景换成月球` 等修改要求一起发送。明确改图指令和本条消息携带的原图引用即可授权
这次编辑；“生成图片,改成一前一后抬棺”等表述也由模型判断为编辑。`加入一个饼干人作为老公`
这类在原图上新增人物或物件的表达同样属于编辑；即使模型误报为 create，服务端也会按明确
改图意图纠正为 edit，保留并上传当前引用原图，不会丢弃原图重新生成。

附图也可以只作为新图参考。例如“参考这个画一个岁己和栞栞的，近的是岁己”会把附图当作
构图、画风或氛围参考，重新创作新场景，不会误当成编辑原图。“模仿这张参考图的风格，做一张岁己的”、
“生成cos图”等附图创作要求由 agent 按语义选择 create/edit，不再用少数参考图句式否决已选模式。
两种模式都必须成功读取并上传本题绑定的全部原图；工具执行及最终生成计划都会检查原图，
读取失败或返回空图时停止，不退回纯文字生图。后台队列冻结原图后继续遵守同一规则。
`qq_ready.imageSourceModeVersion: 1` 标识已加载这套原图绑定与模式校验。
引用中的文字不进入创作指令。仅引用或称赞图片
不会触发生图，普通群消息的引用也不会触发问答或编辑；已有成图的补发遵循下述独立规则。

支持引用图或同条附图后说“变XX”“变成XX”“换成XX”来替换角色；“变岁己”即
把图中角色换成岁己形象，不是询问词义，也不是让岁己变成其他形象。agent 查询目标角色
参考并选择 edit；服务端也会补齐正文明确命中的可信参考，避免模型漏选。默认只改变目标
角色的脸型、发型、发色、瞳色等身份特征，保留原图画风、构图、黑白或彩色表现、姿势、
表情、服装、背景、文字和分格；明确提出的额外要求优先。单个主要角色直接替换，
同一角色在多格和特写中的形象同步替换；多人且替换对象不明时才澄清对象。未匹配到的
角色仍说明外观不确定；缺少原图时请用户引用或附图，不改为凭文字新画。

`QQImageInputPolicy` 只解析已认证 SDK 的 `attachments`、`refMsgIdx` 和引用 `msgElements`。
优先选择与规范化 `refMsgIdx` 匹配的元素，否则查找携带图片的元素，再兼容第一个引用元素。
明确的图片附件不依赖可选引用 ID 或消息类型，缺这些元数据时仍可下载当前事件明确附带的原图。
不从文字链接、昵称或其他群消息猜原图。
`QQImageInputs` 在成功发送图片后将平台 `id` 与 `ext_info.ref_idx` 映射到本机生成的 PNG；
索引位于 `data/runtime/qqbot/image-replies/<AppID>/`，键包含会话哈希，值仅保存日期、
请求哈希与内容 SHA256，不保存原始群号、用户标识或平台引用 ID。重启后可继续修改

默认 `--check` 只检查配置、SDK 加载和资料运行配置，不连接 QQ、不调用模型或发消息。
`--live` 为显式运行入口。PM2 的 `shikamochi-qqbot` 使用独立的
`dist/qqbot/tools/qqbot/run.js`，仅在该功能的部署任务授权后，按架构指南验证候选、
部署到这个独立目录并启动该进程；不覆盖其他服务的 `dist` 文件。
QQ 候选应从已通过 `verify:all` 的 `build/service` 收集该入口的完整静态依赖与 JSON 资源，
保存文件清单及 SHA256，在隔离目录先执行编译入口的 `--check` 和使用注入传输的离线检查。
确认账本及后台图片日志无处理中任务或仍在有效窗口的待核对发送后，仅停止 `shikamochi-qqbot`，保存账本、图片任务日志快照和旧 QQ 目录，
整体切换独立目录再启动；核对文件清单、新 PID 的 `qq_ready`、未暂停状态及既有收据。
回退仅恢复代码目录及对应配置，保留最新额度、图片任务、结果和发送收据，不使用 Webhook 部署脚本操作 QQ 分区。
历史已过期的 `unknown` 收据及 `delivering` 图片任务须原样保留，不因部署清空、自动重发或重新付费；
确认暂停原因前不得在部署中顺带执行 `--resume`。
SDK 仅发布 ESM，`QQSdk` 用固定的原生 import 表达式保留 CommonJS 构建兼容性；
不接受来自配置或聊天的模块名。

## 去重、限额和失败

单进程串行处理，默认至多20条未完成入站请求；普通聊天每用户2条，明确生图命令每用户最多20条（仍受全局入站上限约束）。群提问每用户滚动五小时
最多 100 次，没有额外的个人每日文本次数上限；
全局每滚动一分钟最多 5 次文本生成。每次预留 262144
token，示例每日预算为 40960000 token。QQ 独立记账，不与 B 站共享已用次数或预算，
不读取或推断 QQ 用户的 B 站粉丝牌。完整上限先持久化，成功后按全部模型轮次的用量结算、
释放未使用的预留；缺少 provider 用量时使用保守字节估计。失败或中断保留完整预留，防止重试刷费。
每次 HTTP 前累计检查消息、工具 schema、输出上限和协议余量；接近上限时停止补查并完成回答。
这是调用预算，不等同于含缓存折扣的网关实际
usage 账单。额度提示每用户一小时至多一次。私人固定引导和空艾特不消耗文本模型预算；
图片请求与能力说明使用同一 agent，按一次提问预留，只有实际执行图片工具才预留图片次数。
用户分组依据 QQ openid，不猜 B 站
粉丝牌或跨平台身份。五小时窗口跨午夜保持，日计数仅作统计并单独重置。

消息有效期四分钟；每次文本 HTTP 超时九十秒，未启用图片时整个 agent 也限九十秒；
启用图片时整个循环最多使用消息剩余有效期减十秒。所有发送开始至少间隔五秒。文字答案只允许单段
至多 300 字纯文本，拒绝公开工具调用、截断响应、链接、真实凭据和路径输出；允许回答
隐私与权限问题时提到“密码”“Cookie”“执行命令”等安全说明词，因为这些词本身不是凭据。
一次请求至多一次图片发送；明确被平台拒绝的图片允许另外发送一次固定文字提示。
发送目标始终由入站事件确定，不能由模型修改。普通问答一次被动回复；明确创作命令可先发一条处理提示，
再发最终结果。长视频草稿最多四条，加处理提示最多五条，不增加图片或视频生成次数。

状态位于 `data/runtime/qqbot/<AppID>.json`，复用 PID 独占锁和原子快照。只保存消息
摘要哈希、额度、时间和收据状态；问答正文单独长期保存，原始 openid 不落盘。收据保留
24 小时、最多一万条。内存排队请求不跨重启恢复；进入模型前已持久化的请求不会
重放。中断的生成保留预算并标记跳过；中断、传输异常的发送标记 `unknown` 并暂停。
`qq_send_receipt` 区分上传失败、消息发送失败和正常返回；只记录固定结构标志、HTTP 状态与数字平台错误码，不记录回执正文、消息 ID、URL、SDK 异常正文或上传凭据。
消息发送阶段收到 SDK `ApiError` 的 HTTP 400 且包含正整数业务错误码时，视为本条请求被平台拒绝，
记录 `qq_send_rejected` 并保留 `unknown` 收据阻止重放，继续处理其他排队和新入站请求。
不自动重试图片、发送替代消息或宣称该图已送达；失败图片仍遵守既有领取恢复规则。
上传失败、网络异常、其他 HTTP 错误、正文读取失败和正常返回但缺少消息 ID 时仍暂停，
避免把不确定发送当成明确拒绝。`qq_ready.sendRejectionIsolationVersion: 1` 标识此隔离行为已加载。
图片消息明确被拒绝时，群内再回复一次“图片已经生成，但QQ拒绝发送这张图”，附数字错误码。
仅凭数字错误码不推断“内容违规”等具体原因，提示“目前未确认具体原因”；
包括已观测到的 `40034006`，也不能把未经一手资料核实的社区错误码解释写成平台确定结论。
文字提示仍绑定并引用原入站消息，共用五秒发送间隔，过四分钟被动回复时限则跳过。
提示不把失败图片标记为已送达，也不注册可引用图片回执；文字提示本身失败时不循环补发。

`notificationConfigPath` 显式指定现有通知配置，示例使用 `config/production.json`，由共享配置加载器
合并其 `wechatWork.webhookUrl`、secrets 和环境变量。QQ 的文本/图片模型仍使用专用凭据。
拒图时企微先收到错误说明、用户原始创作要求、请求时间和 QQ 文字提示投递状态，再收到对应结果图片。
复用 `WeChatWorkNotifier` 的 2MB 图片压缩规则；图片必须在本 AppID 的成图目录内，发送前重验 SHA256。
企微失败不影响后续 QQ 提问，不重新生图或发送原图到 QQ。
`data/runtime/qqbot/send-alerts/<AppID>/<请求哈希>.json` 分别持久化 QQ 文字、企微文字和企微图片的发送意图与结果；
发送不明或中断的步骤不自动重发，独立步骤仍可完成。磁盘状态损坏时不擅自重发，记录脱敏诊断。
`qq_image_rejection_notice` 只含请求哈希、步骤、结果和数字错误码；
QQ 为共享通知器注入静默日志器，由上述受限事件记录结果，避免其原始网络异常暴露 webhook 凭据或本地图片路径。
`qq_ready.imageRejectionNotificationsVersion: 1` 确认已加载。企微未配置时不会宣称通知成功。
`qq_ready.sendReceiptDiagnosticsVersion: 1` 确认这版诊断已加载。发送调用抛错和缺少 ID 必须区分，具体平台原因以实际诊断证据为准。
磁盘检查点失败同样停止后续调用与发送。恢复前检查 `--status` 与平台情况，显式执行：

```powershell
npm run qqbot -- --resume
```

恢复不会重试旧收据；之后重新启动 QQ 进程。进程退出码 2 禁止 PM2 自动重启，以免
反复发送不明结果。日志使用结构化 JSON，带 `diagnosticsVersion: 1`、PID、AppID 和时间；
请求相关事件共用 `requestId`（本地请求哈希），可与存档文件名和网页诊断标识对应。
`qq_generation_started` 区分 text/image 并记录开始处理前的等待时间；`qq_agent_trace`
在模型调用前后、工具完成及最终清理后记录最新受限 trace。失败事件附同一份安全诊断，
即使存档磁盘写入失败，仍可通过 `qq_state_failure` 定位异常和对应请求。
启用图片时，已接收群艾特额外记录 `qq_image_input`：消息类型、是否有引用、顶层及引用
元素附件数量、已解析原图数量和无效标记，数量均有界；不保存图片 URL、签名、引用正文或原始平台 ID。
图片地址被拒绝时附 `urlDiagnosticsVersion: 1` 和最多八条 `rejectedImageUrls`，仅含附件来源、
拒绝原因、地址结构类型及长度受限的合法域名；不保存路径、查询、端口、账号、密码或片段。
此诊断不放宽图片下载规则，用于区分地址格式、协议、认证字段、端口、片段和域名校验失败。
未识别为图片的附件附 `attachmentDiagnosticsVersion: 1` 和最多八条 `unclassifiedAttachments`，
仅记录来源、固定 MIME 类别及地址缺失／允许／拒绝类别，不保存原始 MIME、URL 或附件字段。
`qq_ready.attachmentDiagnosticsVersion: 1` 标识已加载。生视频原图读取失败或为空时，明确告知
“本次视频未提交生成”，请用户在新消息直接附原图与要求；不会让用户查询不存在的任务，
也不会丢弃原图要求后改成纯文本生成。`qq_ready.videoSourceErrorsVersion: 1` 标识此处理已加载。
普通群聊与重复入站不写此诊断。不启用 SDK 原始调试日志，不记录任意异常 message、原始堆栈、HTTP 错误正文或请求凭据。

## 本地问答记录与网页

`data/runtime/qqbot/records/<AppID>/<北京时间日期>/<请求哈希>.json` 独立保存每次已接收
问答的正文、答案、模型、状态和时间，群/用户标识只记录哈希；QQ 事件若提供发送者昵称，
另存经清理且最多 80 字的 `senderName`，用于 Web 展示和筛选，不用于身份授权或额度分组。
旧记录和未提供昵称的事件兼容显示用户哈希，不推断昵称。生成前保存问题，发送前保存
答案，平台成功回执后才标记 `sent`。磁盘失败停止后续调用和发送；普通未艾特群聊不生成问答记录，
若触发已有成图补发，只为派生的图片交付请求存档。
固定私聊、额度提示和已接收后跳过的请求也留档。发送中断保留待核对状态，不自动重试。
此目录不随 24 小时收据清理，可供后续复盘。
文本问答另保存可选 `agent`：模型调用数、用量、工具名/结果状态/耗时，以及逐轮 `calls`
和 `failures`。每次 HTTP 前先持久化 `running` 轮次，完成后记 `ok/failed`；预算或轮数
在 HTTP 前拦截时记 `blocked`，不算已发出的模型调用。工具执行后立即保存，最终清理失败
也不覆盖原始错误。后续发送检查点保留这些字段，兼容没有诊断字段的 version 1 旧记录。
不保存工具原始参数、摘录全文、模型原始回答、凭据或 SDK 云端 trace。

每轮记录时间、耗时、请求 UTF-8 字节数、调用前累计预留、本轮预算和上限；收到响应时
保留 HTTP 状态、安全的上游请求 ID 和固定枚举的 `finish_reason`。`failure` 区分模型准备、
预算、HTTP、JSON 解码、响应结构、SDK 运行、答案/证据校验、资料工具、清理、诊断写盘、
图片准备/HTTP/解码/存图等阶段。错误码区分超时、主动取消、网络失败、HTTP 失败、截断、
无效 JSON/schema/引用、不可公开回答及预算/轮数不足；回答校验还记长度和失败校验项。
未知错误保留白名单异常类型、系统错误码、SHA256 异常指纹，以及最多六条仅文件名与行列号
的项目/Agents SDK 调用位置，不含完整机器路径。凭据不会因异常或响应头进入诊断。
`queuedMs` 记录消息创建至开始处理的等待时间，避免把排队误判成模型耗时。
生成失败的根因保留在 `failure`；若固定失败提示也未确认发送，另存 `sendFailure`，
不覆盖前面的生成错误。诊断存档失败和其他持久化检查点一样暂停，不继续调用或发送。

网页“查询过程”展示逐轮 HTTP 与工具顺序，“失败原因”显示阶段、错误码、预算、请求 ID
和安全调用位置；旧记录明确提示没有详细原因，不能从新字段反推历史异常。只读 API 对新增
诊断对象同样逐字段投影，剥除未知字段。

Web 工作台侧栏“QQ 问答”（`http://127.0.0.1:3000/#qq`）经本机鉴权只读
`GET /qq-records` 展示记录，每 5 秒刷新；按北京时间日期、群/私聊、状态及正文关键词
筛选，每页 50 条，默认最新有记录日期。单次最多读取选中日期一万条，损坏或超限明确报错。
支持精确的 `user` 和 `conversation` 筛选，值均为 `<AppID>:<64位哈希>`，与日期、消息类型、
状态和关键词组合，不混合不同机器人的同名用户。用户下拉列出所选日期和消息类型下的所有用户；
选中用户后，会话下拉只列其参与的会话，用户统计表定位该用户。用户统计同样按所选日期与
消息类型汇总，不受会话、状态、关键词或分页影响；默认展示最近提问的 100 位用户，
其余用户可通过下拉筛选定位。问答概览则按全部筛选条件、在分页前统计记录、已回复、生成/发送异常、
额度提示、用户、会话、处理中、跳过和成图数。生成失败但成功发送固定提示可同时计入异常和已回复。
额度提示数只识别固定限额提示，不能据此判定当前仍限频。

当前额度独立于历史日期筛选，使用只读运行账本及默认常驻进程的
`config/qqbot.example.json` 中公开的预算/生图限额，返回快照时间。显示个人五小时用量与剩余量、
全局每分钟文本门控、每日文本预算、生图个人五小时与每日额度、全局十分钟图片滚动调度、私聊引导冷却以及暂停状态。
限频原因分别给出可重试时间，个人五小时窗口跨午夜保留，每日预算在北京时间零点按规则投影重置。
`noticeUntil` 只抑制重复提示，不作为实际限频依据。账本或额度配置缺失、损坏时显示未知；
运行账本合计最多读取 32 MiB，超限账号同样显示未知。不读取 key，不改写账本，不清额度，
不恢复暂停，也不以文件存在证明网关在线。
生图记录同时展示成图预览和提示词；只读图片路由为
`GET /qq-records/<AppID>/<日期>/<请求哈希>/image`，校验目录、JSON 归属、PNG 签名和
内容哈希，拒绝符号链接和任意路径。页面不调用模型、发 QQ 消息或读取 provider/账号凭据。

## 验证

相邻 `QQPolicy`、`QQWorker`、`QQAgent`、`QQState` 和 CLI Jest 测试注入模型/发送
适配器，覆盖提及门控、私聊引导、预算、去重、暂停与重启恢复，不使用真实 QQ 或模型。
按开发指南运行聚焦测试、`verify:quick` 和跨模块 `verify:all`。
真实上线后仍需 QQ 用户在群里艾特确认平台端到端发送；单纯 `READY` 只证明连接。
