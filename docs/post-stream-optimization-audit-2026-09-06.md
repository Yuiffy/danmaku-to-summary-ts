## 1. 文案与最终片内证据绑定

### 当前缺口

- `own_stream_clipper.js:937` 默认每个候选只给重排 520 字符。
- `clipping/own_selection.js:232` 保留首部约 65%、尾部约 35%，中段直接省略，而且可能从时间戳或句子中间截断。
- `own_stream_clipper.js:965` 还附带第一轮模型的标题和理由。后续模型可能沿用初稿推断，却没有足够原话纠正它。
- `own_stream_clipper.js:1799` 在文案生成之后才对齐边界；`generateOwnStreamClipJob` 直接使用已有 title/description，未检查文案证据是否仍在最终范围内。
- 六场 92/137 条最终片段的结尾比模型原定时间延长超过 20 秒，12 条被回裁。延长不一定有错，但文案证据与最终时间范围必须同步。

例：09-05 第 31 条的候选字幕有 2,215 字符，重排只得到 520 字符，充电、牙膏之后的大段人物关系及后续细节不可见。第 27 条候选证据含约 04:30:51 的“高考要用那你用吧”，最终结束为 04:30:43.215；这证明后处理可以移除原本被用于命名的句子，不代表该标题一定错误，弹幕仍可能有独立证据。

### 建议

让现有调用产出可验证的事实，不默认增加一轮全片审稿模型：

1. 召回结果返回短事件描述、关键字幕/弹幕 ID，以及铺垫、转折、收束的 cue ID；title/cover/description 不必在召回阶段全部写一遍。
2. 重排拿到候选完整证据或去重后的共享字幕表，并以 cue ID 决定最终边界和文案；不能只凭模型初稿或弹幕猜原话。
3. 区分主播当前发言、转述过去经历、播放内容和观众弹幕。来源不明就保留不确定状态，不因声纹置信分或模型自评分直接认定事实。
4. 本地检查人物/数字/引号引用对应的证据 ID 存在，并落在最终片内。存在不等于语义正确，但可以先消除越界、串片和无出处引用。
5. 封面文字、简介和标题共用同一份已选事实；图片脚本同样引用这些事实及已有截图 ID，避免“看回放”被升级成“本场正在表演”。

若需要额外语义复核，只对有证据冲突的候选试验，尽量与已有压制重叠；必须实测总完成时间不退步后才能启用，不能把每片再调用一个大模型当默认方案。

六场成功请求的元数据合计：

| 晚安 | 6 | 156,604 | 23,040 |
| 漫画脚本 | 6 | 138,606 | 0 |

这不是完整账号账单，不包括未报告用量的失败请求、图片和切片，也没有重复累加 `TUZI_TEXT_USAGE` 与 `COMIC_SCRIPT_USAGE` 对同一次请求的记录。

09-05 一场的共享前缀：晚安 `fcea5e...`、漫画 `7e80eb...`、全量梗概 `472a14...`。晚安和漫画分别约 48,076/48,423 字符，明显不是相同前缀。日志中固定 3,840 cached tokens 的样例归因于 instructions，不能解释成整场直播事实已被缓存。其他房间日志也存在大额缓存命中，因此不是断言供应商“完全不支持缓存”。

原因及代码位置：

- JS `live_generation_context.js:113` 与 Python `ai_comic_generator.py:1266` 分别拼前缀。
- Python 的 `format_live_generation_context` 会将稍后生成的 LIVE_CONTENT 和漫画专用规则放进前缀，改变字幕之前的内容。
- 当前岁己 experiment tasks 是 summary/ownStreamClips，但切片仍为 staged。`background_clip_runner.js:97` 只是传入 sidecar，没有切换策略；staged 分支不消费整场共享前缀。
- `src/workflows/text/requests.ts:76` 明确因网关兼容问题移除了 Responses 的 `prompt_cache_breakpoint`；两段 input_text 和一个 cache key 不是成功缓存的证明。

建议使用一个生成器落盘“不可变源事实前缀”，晚安、漫画读取同一份字节；后到的梗概和任务专用规则放在后缀，保留全部规则和事实。再针对当前网关验证可用的断点、消息布局、路由与命中用量，而不是仅把 rollout 开到 100%。

生产目前还有缓存等待：`enhanced_auto_summary.js:1751` 的 45 秒预热，以及 `1798` 随后无条件等待梗概完成。后者承担了约束漫画游戏名的质量功能，不能直接删除。可先把不依赖梗概的切片规划从该等待中解耦；在不增加网关排队、且图文 P95 不退步的前提下让独立阶段并行。不要为了缓存再新增等待。

OpenAI 官方文档说明缓存要求完整前缀匹配、路由与可用断点共同满足；当前供应商网关行为及计费必须另测，不能套用官方“最高节省”数字。缓存减少未缓存输入计算与可能的计费，不一定减少 usage 中记录的总输入 token 数。

参考：[Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)。本次已读取该页正文。

## 3. 收敛重试与阶段缓存

`ai_comic_generator.py:2453` 启动 Node 文本生成器，父进程硬超时 120 秒。Node 内部还会按模型、provider 和 transient failure 重试；父进程超时后 Python 又进入自己的 fallback 路径。

今日日志可直接定位两次：

- `logs/pm2-combined-0.log:29793`：18:14:30 北京时间 Node 超时；之后 Python 的同型号请求再用约 92.3 秒完成。
- `logs/pm2-combined-0.log:31127`：18:51:39 Node 超时；之后 Python 的同型号请求再用约 103.2 秒完成。

现有日志不能证明被终止请求是否在服务端完成、是否被计费，因此这里确认的是重复启动和额外等待，不把它直接换算成双倍账单。

建议：

- 由一个组件管理请求尝试、可重试错误、截止时间与取消，Python 只消费结构化结果；保留不同 provider 的同型号容灾能力，避免两套重试嵌套。
- 有服务端请求 ID/可查询状态时，复用已提交任务及迟到结果，不在结果不明时盲目新建。不要把单纯延长超时当成优化。
- 补上分块召回与重排的阶段缓存：键含源内容哈希、模型及生成参数、prompt 版本、选材策略；只复用验证成功的结果。修改一段字幕只使相关分块失效。
- 源更新、prompt/model 更新必须失效，不能只判断文件存在。已有漫画脚本 `3018`、梗概 `readReusableSummary` 的校验缓存应保留并复用设计。
- 同源同参数的并发去重与“多场并发”分开。目前 `ai.comic.outputLockEnabled=false`，避免同一输入重复生成不应把不同直播串行化。本次没有发现六场日常任务重复启动，不能宣称正常场次立刻省下一半费用。

## 4. 无损整理输入，而不是再砍上下文

`clipping/own_selection.js:499` 将每 45 分钟字幕压在 14,000 字符以内，仅截取前部。09-05 第 7 块到约 05:02:19 就截断，但该块覆盖到约 05:13:04；后面充电、牙膏等内容仍被本地信号捞起，却未获得相同的首轮全文理解机会。

六场已选候选的带时间戳表示共 142,570 字符，纯字幕文本约 72,267 字符。约一半字符是逐条时间标签、空白等结构开销；这不是“能无损省一半 tokens”的测量，因为 tokenizer 和新格式也有成本。

建议先试可逆的紧凑输入：连续碎句按说话人/时间连续性拼成句群，用短 cue ID 与精确时间映射表保留每条原始时间；跨说话人、明显停顿和源类型边界不合并。不能丢时间信息或把不同人的话拼成一句。

在相同输入预算内优先保留完整话语，必要时按实际长度动态分块，交界处提供必要上下文。分块数量、并发和跨块去重都要测，不能单纯把 chunk 切小导致调用数和排队时间上涨。

召回阶段去掉最终封面文案、长发布简介的重复生成，把输出预算转给事实和关键原话。最终文案仍使用同一强模型与完整证据。09-05 切片 8 次调用的 output 为 87,820 tokens，其中 reasoning 为 74,697；不能把所有 output 都当作“重复文案”宣称可以删除。

## 5. 小而确定的本地性能优化

### 每个源只探测一次视频参数

`topic_clipper.js:1173` 的 `async getVideoResolution` 内部实际使用 `execFileSync`；`1237` 每片都会探测同一个源视频。

对 09-05 同一 1920x1080 源文件，五次只读 ffprobe 耗时为 107、100、100、100、104ms。31 条片段可以将 31 次探测收敛为一次约 100ms，避免约 3 秒累计同步阻塞；这不是整场会快 3 秒的保证。

使用同源的进行中 Promise 和成功结果缓存；以文件身份、大小、mtime 及探测参数限定复用。不能复用仍在增长或已被替换录播的旧信息。编码器、画质、字幕大小、精确裁切及 packet 起点校准均不变。

### 同一进程共享资源采样

`ffmpeg_resource.js:250` 每次 GPU telemetry 都启动 nvidia-smi，`264` 每个 FFmpeg 阶段独立创建采样器，默认约 1 秒一次；`clipping/resource_scheduler.js:229` 调度器另行采集 GPU 总量及进程信息。

09-05 的 31 条切片元数据记录了 1,399 次成功 GPU 采样；六场共 4,938 次。这不是 1,399 次全部冗余，也不等于峰值监测造成同等秒数延迟。

可以让同进程的并行 FFmpeg 阶段共享最新的同一份 GPU/host 样本，各自统计阶段峰值；保持现有 1 秒采样和游戏负载响应速度，不通过延长间隔省开销。先做进程内复用，不为这点收益新建复杂监控服务。

类似地，同一录播的 SRT/XML 解析与相同截图请求可复用已验证结果，但收益应排在模型证据链和重试之后。不要降低截图分辨率、取消必要参考图或更换更快但更差的编码预设。

## 上线门槛

先修确定性回归，再逐项验证；不能把多个优化混成一组，无法判断收益来源。

- 固定人工审核集，覆盖单人、联动、回放、转述、低热度完整故事和跨分块边界。标题事实错误、人物归属、片内引用及起承转合分开打标；记录审核修改原因，不只看上传成功率。
- 同一素材、相同模型及推理设置 A/B；交错执行以降低网络与机器负载波动。人工盲评质量和召回不能下降。
- 分别测下播到晚安可发布、图片就绪、首片就绪、全部切片就绪，以及 P50/P95；并行优化还要确认没有拖慢别的直播任务。
- 记录每阶段请求 ID、prompt/cache/output/reasoning tokens、尝试次数、截断量、输入哈希和最终产物版本；失败请求未知用量不能当成零。
- 本地无损改造检查文本、时间映射和媒体规格等价；共享采样检查峰值误差与响应延迟；缓存检查输入变更失效与同源并发去重。
- 不建议直接降模型、降 reasoning、砍参考图、缩短字幕、减少候选上限，或用批处理延迟换折扣。也不建议把全量梗概直接替换为“精选片段摘要”，它无法保证全场歌曲、游戏和话题覆盖。
