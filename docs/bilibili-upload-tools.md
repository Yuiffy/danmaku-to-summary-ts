# Bilibili Upload Tools

For SDK ownership, maintained upstream references and upgrade contracts, see
[Bilibili API upstreams and diagnostics](bilibili-api-upstreams.md).

This repo has two categories of upload-related scripts:

- Reusable tools live in the relevant `src/scripts` subdirectory or as documented root-level helpers.
- Shared clipping and evidence modules live in `src/scripts/clipping/`; the root-level
  `clip_resource_adaptive.js` and `clip_output_path.js` files are compatibility entrypoints.
- One-off scripts tied to a date, BV list, local media path, or recovery batch
  should live under `local-scripts/` or `tmp/`; both are ignored by Git.

发布前先运行 `npm run bilibili:clip-audit -- --video ...`，按
`docs/bilibili-clip-verification.md` 核对媒体、SRT、元数据、封面和线上稿件。
同标题只表示“需要核对”，不表示当前本地文件已经上传；查重冲突会写入
`title_conflicts` 并停止队列。修正已有线上稿件使用 `replace_video.py`，只有明确
授权的新修正版投稿才使用 `--force`。

## Batch Upload Clips

Use `src/scripts/batch_upload.py` for normal clip batches generated by
`own_stream_clipper.js` or `topic_clipper.js`. Generated batches use the
structured `UPLOAD_MANIFEST.json` and per-clip metadata JSON as the machine
contract; `REVIEW.md` remains the human-facing review document.

Queued JSON-backed uploads pass `--queue-job` and `--queue-ids` to resolve exact
registry records under the queue lock. They do not reread a mutable batch
manifest by review index: another recording on the same day may replace that
export. The registered media, copy, per-clip metadata and current quality gates
remain authoritative, with cancellation and authorization rechecked before
submission. Standalone `--manifest` and historical `--review` remain supported.
Input read failures and review/validation failures have separate error messages;
the queue's terminal failure reason retains the specific input/review error.

Example:

```powershell
python src\scripts\batch_upload.py `
  --manifest "D:\files\videos\DDTV录播\25788785_岁己SUI\2026_06_26\own_stream_fun_clips\UPLOAD_MANIFEST.json" `
  --source "岁己SUI 直播《悠哉悠哉夜晚》2026-06-26" `
  --tags "小岁,虚拟主播,直播切片,岁AI切片" `
  --prefix "【小岁】" `
  --tid 21 `
  --delay 0 `
  --state "D:\files\videos\DDTV录播\25788785_岁己SUI\2026_06_26\own_stream_fun_clips\upload_state.json"
```

Useful options:

- `--dry-run`: parse the manifest (or legacy review) and run duplicate search without uploading.
- `--only 1,3,5`: upload only selected manifest/review indices.
- `--skip 2,4`: skip selected manifest/review indices.
- `--state <path>`: keep upload state separate for supplemental batches whose
  review indices overlap with an earlier batch.

Complete Sui performances and viewing sessions use the separate
[stream activity workflow](stream-activity-clips.md). Each kind occupies one
multipart submission and one queue ID per recording, with a dedicated collection.

Complete allowlisted gameplay uses the [game workflow](stream-game-clips.md).
It checks current account multipart permissions and file limits before grouping
and upload. Videos keep the original audio mix; hash-bound external SRTs are
submitted to verified CIDs through a separate retry service after the BV exists.

To auto-attach uploads to a Bilibili合集/series after success, set:

- `bilibili.upload.collectionSectionId`: the collection section `section_id` to
  add each successful upload to. (`collectionSeriesId` remains supported only
  for legacy configurations.)

season `8941979` (section `9974272`), before matching the source streamer.

`publicationKind: keyword_topic`; legacy clips use the exact `topic_clips`

## Reviewed Clip Short IDs and Upload Queue

Reviewed clips can be addressed by short numeric IDs instead of passing long
local paths to agents.

Automatic `own_stream_clipper.js` runs now import their JSON upload manifest into:

```text
data/runtime/clip_upload_registry.json
```

That file is local runtime state and is ignored by Git because it contains
machine paths. The upload queue is stored next to it:

```text
data/runtime/clip_upload_queue.json
```

The generated `REVIEW.md` is still rewritten with:

- a header line like `上传短ID: 17,18`;
- per-clip lines like `上传ID: 17`.

The WeChat review notification also includes those short IDs, so a human can
tell an agent to upload `17,18` without passing the long review or media paths.

Useful commands:

```powershell
npm run upload:clips:list
python src\scripts\clip_upload_registry.py show 1,3,4
python src\scripts\clip_upload_registry.py enqueue --ids 1,3,4
npm run upload:clips:queue
```

To import an older `REVIEW.md` manually:

```powershell
python src\scripts\clip_upload_registry.py import-review `
  --review "D:\...\own_stream_fun_clips\REVIEW.md" `
  --source "岁己SUI 直播《标题》2026-06-26" `
  --tags "小岁,虚拟主播,直播切片,岁AI切片" `
  --prefix "【小岁】" `
  --tid 21
```

For a generated JSON batch, the equivalent registry command is:

```powershell
python src\scripts\clip_upload_registry.py import-json `
  --manifest "D:\...\own_stream_fun_clips\UPLOAD_MANIFEST.json"
```

The manifest references each clip's metadata JSON. It carries the upload
title prefix, tags, room, streamer, source, and output paths; the uploader does
not reconstruct these values from Markdown.

Queue processing is single-worker and calls `batch_upload.py` with grouped
manifest indices for new JSON batches. Historical Markdown batches still use
review indices. Each group is split into at most four clips by default
(`enqueue --batch-size` can override it), and each uploader subprocess has a
30-minute timeout by default (`enqueue --timeout-seconds` can override it).
This bounds the impact of a hung upload while preserving order. Existing
duplicate checks, upload state and ambiguous submission reconciliation stay inside
`batch_upload.py`; actual SDK initialization is admitted by `clip_upload_pacing.py`.

Uploads can run consecutively while the same account has fewer than five actual
per-P initializations in the preceding 300 seconds. The sixth waits until the
oldest slot expires, with a one-second scheduling buffer. Failed initializations
consume slots, and each P consumes one. The atomic SQLite ledger at
`data/runtime/clip_upload_pacing.sqlite3` shares slots across batches, processes
and restarts. Queue jobs always pass `--delay 0`, including legacy jobs with a
stored 60-second delay; the standalone CLI retains an optional extra delay.
The persistent worker checks for runnable jobs every 30 seconds.

Extra preupload availability probes are disabled. Each HTTP 406 stops later
uploads in the batch and starts a fixed ten-minute account cooldown. The queue
then retries actual work through its existing duplicate/intent checks. A known
SDK initialization rejection can clear its submission intent; an ambiguous
failure at a later stage retains reconciliation before any resubmission.
The legacy `probe_upload_available`/`wait_for_upload_available` exports are
no-op compatibility functions, and old `--rate-limit-wait`/`--rate-limit-retries`
arguments remain accepted without controlling this policy. These are experimental
local limits, not documented platform quotas or a promise of recovery.

Sustained HTTP 406 protection is account-wide and persists in the same SQLite
ledger. Consecutive actual 406 failures whose first-to-last span reaches three
hours trigger one WeChat Work alert and 24 hours of slow mode. A successful
archive, another terminal outcome, or more than 30 minutes without another 406
breaks the consecutive-failure episode; idle time alone never triggers it.
An archive confirmed by the existing ambiguous-submission reconciliation also
breaks the episode. Chunk HTTP 406 escapes the SDK's internal chunk retry loop
and goes through the same cooldown/protection policy.
Slow mode admits at most one new archive every ten minutes, including failed
starts, while multipart archives keep the existing five-per-P-initializations
per 300 seconds guard. Queue groups contain one archive in slow mode and yield
between archives, so waiting does not consume the uploader subprocess timeout.
Existing 137022 and rolling-24-hour guards remain independently authoritative.

Any further actual HTTP 406 during slow mode latches a manual account pause and
sends another WeChat Work alert. New/queued jobs, compatibility uploads and worker
restarts cannot release this pause, even after the slow-mode expiry. Notifications
use a durable outbox with delivery leases; failures retry after five minutes and
never release protection. Queue status and pacing statistics expose the pause,
slow-mode deadline and next allowed archive start. No availability probes are sent.
After investigation, stop the worker and use the existing `resume --note "..."`
command; it releases paused jobs and starts another 24 hours of slow mode.
As before, this explicit recovery command also clears the 137022 cooldown.

For a confirmed historical long-406 episode that predates the ledger, an operator
can activate protection from the current time without fabricating upload events:

```powershell
python src/scripts/clip_upload_pacing.py --account ACCOUNT_ID --activate-slow --note "confirmed long-406 incident"
```

This command queues the same alert for the worker to deliver. Repeating it during
active slow mode does not extend the deadline or create another alert, and it
cannot release a manual pause.

`[UPLOAD_REQUEST]` records actual starts, failures, part completion and final
submission, with 60/300/900/3600-second start counts and no credentials or SDK
payloads. Read recent counts and events without platform requests:

```powershell
python src/scripts/clip_upload_pacing.py --hours 24
```

The persistent queue treats the per-clip upload state as authoritative when a
subprocess exits. A job with partial success is retried with only unfinished
clips; deterministic problems such as a missing video, metadata JSON, or
legacy REVIEW row become
`failed` with a recorded reason; transient exits, including batch timeouts,
enter `retry_wait` with backoff and eventually become `blocked` after the
automatic retry limit. A zero-count summary such as `同标题冲突: 0` is not
treated as a title conflict. On a worker restart, only jobs left in `running`
are recovered to `pending`, while `blocked` remains a manual-review state.
`queue --verbose` shows the last uploader output for diagnosis.

Bilibili submit error `137022` (`投稿过于频繁，请稍后再试`) has a separate
account-wide policy. The uploader stops the current subprocess immediately,
and the queue pauses every upload job for 20, 40, 80, 160 minutes, and so on,
doubling up to a 24-hour ceiling. A confirmed successful upload clears this
streak. `npm run upload:clips:queue` prints the active cooldown and its expiry.
After a manual Creator Center submission confirms recovery, stop the worker and
run `python src\scripts\clip_upload_registry.py resume --note "..."` before
starting it again. This clears both the cooldown and stale `137022` output from
the released jobs.

The queue also enforces a proactive account guard of at most 90 submissions in
any rolling 24-hour window. Before each uploader subprocess it merges Creator
Center archive timestamps for the configured `DedeUserID` with the worker's
per-video `submittedAt` ledger. A four-clip batch is shortened when fewer than
four slots remain, so the 90th success cannot spill into a 91st submission.
At the limit, the unfinished job enters `retry_wait` until enough oldest events
have aged past 24 hours (plus a five-second boundary buffer). The worker sends
a WeChat Work markdown alert with the account, current count, next short ID,
and planned next upload time in Asia/Shanghai. Queue status prints the rolling
count and any active guard expiry.

For persistent operation:

```powershell
npm run pm2:clip-upload:start
npm run pm2:logs:clip-upload
npm run pm2:status:clip-upload
```

## Check Public Duplicates

Use the maintained Python diagnostic to search public Bilibili results for the
current account and group exact duplicate titles.

```powershell
python src/scripts/check_bilibili_duplicates.py --keyword "小岁 空洞骑士" --pages 5
```

This is useful after upload errors such as HTTP 406, where a submission may
have succeeded but the uploader did not return a BV id.

## Check Creator Archives

Use `src/scripts/check_archives.py` when a submission is not visible in public
search, may still be under review, or may have been rejected/hidden.

```powershell
python src\scripts\check_archives.py --status all --keyword "糖浆" --pages 3
```

Common status values:

- `pubed`: published archives.
- `not_pubed`: unpublished or hidden archives.
- `all`: creator-center archive list across statuses when the API accepts it.

The output includes `state`, `open_shield`, publish time, title, and reject
reason when present.

## One-Off Scripts

If a script hardcodes any of these, keep it out of Git:

- a specific local video directory;
- a fixed date or stream title;
- a fixed BV id list;
- a manual 406 recovery plan;
- a replacement/upload list for one batch only.

Put those scripts under:

```text
local-scripts/one-off-scripts/<date-or-task>/
```

`local-scripts/*` is ignored by `.gitignore` except for
`local-scripts/README.md`, so these files remain available locally without
polluting future commits.
