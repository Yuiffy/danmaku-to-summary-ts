# 岁己歌切与同步视听

`streamActivityClips` 与原有趣味切片并行存在。生产环境只对房间 `25788785` 开启，在下播后台队列运行。默认 `detectionMode: "summary"`，复用本来就要生成的直播梗概，不再另扫全场字幕/弹幕。

日常流程只有三步：

1. **出梗概时顺便粗定位。** 同一次请求、同一份完整 ASR/弹幕输入，输出普通梗概和 `activityTimeline`，记录每次实际演唱与每个完整观看会话的粗起止、标题或空值、原文引用。共享提示前缀保持一致；新增输出不额外发起全场检测请求。主播实际唱歌、播放歌曲、点歌未唱和影片声音分别判断，未知歌名仍保留演唱。
2. **只校准附近短音频，一轮合批。** 整首歌曲与观看会话只取开始/结束附近的音频（默认外侧 45 秒、内侧最多 15 秒）；短片段取本段加前后最多 15 秒。本地独立运行 SenseVoice 和多语言 Whisper，分短段保留原始识别、语言、音频事件和时间原点，不输入源字幕或改词规则。DaiYu GPT 只接收这些文本、一秒能量数据和原帧，明确没有收到音频；不会向它发送 `input_audio`，也不会自动回退 TuZi Gemini。每批最多 8 项、600 秒音频，每场最多 3 批远程请求，每批超时 60 秒，只请求一轮。电影和歌曲中间保持完整，不另送整场录播、整首歌或每 P 做检查。
3. **直接制作两个投稿包和歌单。** 成功边界用于切片；校准失败、格式错误或预算耗尽直接标记待核，不再换模型重试或启动昂贵检测。不确定歌切保留前后余量，观看保留连续会话。重跑复用同源梗概、校准结果与成片。

能量数据和音频事件标签不能证明演唱者身份。保留决定须有本候选独立听写中的字面引文、演唱前后语境和原帧支持；混合源字幕仅作辅助。模型用明确的音频序号和片段内秒数返回边界，程序换算为录播秒数，拒绝借用另一个候选的音频。所有演唱都不能截入已观察到的演唱区间内部；精确前奏/尾奏不清时可保留已经证明完整的上下文包围区间，标记 `complete_context_enclosure`，不能宣称 GPT 听过原音或精确定位了音乐起点。窗口外仍可能有演唱或播放者不明时继续待核。无法确认时记录 `provisionalWindow`、`media_verification_unconfirmed` 与边界待核项，不计入确认歌数；排除的误检留在 `rejectedActivities`。

已有梗概没有时间线或手工处理旧录播时，只补一次包含时间线的梗概请求。时间线缺失/不完整、源摘要不匹配时保存失败状态，不把它解释为本场没唱歌，也不自动启动另一套全场扫描。源 SRT 的已知对齐异常会标记 `source_transcript_timing_unreliable`；默认只复用已完成的修复转写，**不会为了歌切重做整场 ASR**。

梗概请求使用严格 JSON Schema：公开 `songs/games/topics/activityTypes` 保持字符串数组，演唱和观看的时间、未知名称及引用放在独立的 `activityTimeline.events`。格式约束不替代时间范围和源证据校验；非法对象或空值不能被直接转成歌名。格式失败保留 `failed`，失败尝试在 `generation.attempts` 保存返回原文及 SHA-256，供定向修复后重跑。

梗概提示 v2 明确区分本场实际活动、观众推荐、未来计划和拒绝/取消；角色介绍、查资源、试画质、预告或拉片解说不能证明观看了对应正片。梗概与时间线均须结合前后语境，保留否定和后续决定。请求时间线时，缺失、不完整或引用校验失败会使本次梗概保留为 `failed`，不再保存成可发布的成功梗概；旧提示版本和不完整时间线不能作为成功缓存复用。修复重跑仍使用同一份完整字幕/弹幕，不另扫视频或重做 ASR。

`PLAN.json.efficiency` 记录实际新增的全场扫描次数、整场 ASR 次数、边界请求批数、音频秒数、缓存命中与耗时。日常前两项应为零；已完成梗概的本场切片只有局部解码和边界请求。默认 `verification.evidenceMethod: "independent_local_asr"`、`provider: "daiYu"`、`apiMode: "openai_chat"`，使用现有 DaiYu 凭证。本地 Whisper 只读已安装模型，不自动下载或切换远程服务。显式 `native_audio` 保留给独立配置的原生音频路线。原音提取、独立解码、原帧和远程答复都有出处和摘要，投稿验收重新读取。

`run/plan --scan` 或 `detectionMode: "standalone_scan"` 是人工排查召回遗漏的旧检测模式：全场拆窗口、逐项音画复核，必要时修复已知漂移转写。它不作为日常流程的自动回退。

## 最终审核后自动入队

`streamActivityClips.automaticPublication` 默认 `off`。生产按用户授权为房间
`25788785` 使用 `mode: auto`、`policyVersion: stream-activity-v1`、明确 `roomIds`、
`activatedAt` 与 `authorizationNote`。新制作且晚于启用时间的 summary 模式投稿包
才带 `activityAutomaticPublicationRequired`。手工扫描、restyle、旧包导入或边界重放
不自动取得该授权；显式修复本场字幕时间轴后重新制作的包重新走当前最终审核。

独立原音校准必须确认实际演唱/观看、闭合的完整起止，且没有待核问题。最终审核
另读实际封面、每 P 的首中尾抽帧、完整活动与分 P 表、独立解码结果及边界答复，
完成全片媒体解码检查，绑定当前来源、文案、所有 Ps、标题与封面。AI 通过保存为
`activityReview.authority: automatic`，不会声称人工听审。注册表登记原数字 ID 后，
通过包才进入既有单实例上传队列；上传前再次校验文件、证明和当前生产授权。
实际多 P 权限预检仍执行，未确认的歌名、人物、边界或源字幕时间异常继续待核。

审核/队列结果写进既有 `REVIEW.md` 和 AI 用量列表，区分已投稿、已排队、待入队、
待人工复核。未收到队列回执时保留“入队结果待确认”，不盲目重投；已排队或发布
的 ID 也不重复入队。不增加逐片成功消息或 BV 消息。保留原录播供异步上传校验。

## 已知字幕漂移的显式修订

普通切片检测到 Paraformer `sentence_info_fallback` 的已知时间轴异常时，只对该异常
重建一次分段转写及本地声纹证据，保留原 SRT。WAV 解码保留时间戳空隙并补齐音视频
尾部小差值，再核对完整时长；不会用一个猜测偏移平移字幕。两种活动复用已完成
的转写，正常日常活动处理不额外转写全场。

本场已有错误待核包时，用 `activity:clips run --repair-timing --transcript-record
<RESULT.json> --revision-note <修复原因>`，并照常传原 media/SRT/XML 和匹配的新共享
梗概。该修订要求原录播和源证据未变、所有既有包未批准/入队/发布，同时修订两类
检测。原计划、歌单、审核、manifest 和元数据先备份；原数字 ID、metadata 路径与
manifest 保持，旧视频保留，新视频写独立版本目录。新时间线重新校准、渲染、最终
审核，不继承错误包的通过状态，也不手改 queue JSON。

## 分阶段优先级与恢复

最终发布审核按传输上限分批：每批最多两个 P，传入实际封面和各 P 的首、中、尾帧。
每个 P 的三帧组成一张带 BEGIN/MIDDLE/END 与录播时间的证据图，标签不遮挡原帧，
两 P 批次只需三张图片。`reviewScope` 列出本批 P 编号、图片和帧位置；每次 AI 的
内容/画面/政策检查只负责本批，其他 P 由独立批次检查，全部通过才批准整包。
每批同时读取全部活动、分 P 时间线、本批每个 P 的完整保留字幕与活动前后各九十秒的
源文本，并读取本批窗口内原始弹幕。分批的并集覆盖全部 P，不为每批重复整场文本。
字幕/弹幕分别注明来源和绝对录播时间，不能凭混合音轨字幕
确认说话人或把影视对白当作主播家庭经历。原音校准与完整文本一起供独立判断；
全部批次明确通过才批准整个投稿包。理由只含一至两条中文阻塞项，完整原答复仍保存。
审核服务或图片传输不可用时保留原包和失败原因，不自动反复请求。修复故障后可用
`run --kind watch --retry-publication --revision-note '具体故障与修复原因'`（歌切使用
`songs`），照常传原 media/SRT/XML。该命令只复核原 ID 的当前成片，复用原计划、
转写和所有视频，不重新检测或压片；旧待核元数据备份到 `temp/publication-retries/`。
它处理 `automatic_activity_review_unavailable`；对旧版未传完整文本、仅边界或政策
检查待核的包，也允许显式补证一次。旧 proof 必须仍绑定当前来源，内容、标题和
画面检查全部通过，且没有任何 rejected 批次。旧 `evidenceVersion:2` 分批材料若边界
全部通过且无 rejected 批次，也可显式升级一次到带标签证据图和明确分批范围的协议。
升级重新审核所有批次，不继承旧批准。新审核保存 `evidenceVersion:3`、完整文本、
图片摘要、分批范围和升级出处；同版材料不能再重试，真实拒绝不因重试获准。已批准、已排队、回执不明
或已发布的包不能重试；当前来源或成片变化也会拒绝。

自动下播按普通切片、歌切、游戏完整切片、同步视听依次处理。歌切与视听共用本场梗概，但分别开始短音频校准和媒体制作；不会在歌切阶段先校准或渲染视听。所有阶段共用每场边界请求预算，视听不会重置已经使用的额度。

`run/plan --kind songs` 只处理歌切，`--kind watch` 只处理视听；不传 `--kind` 仍处理两类。恢复歌切可用 `npm run activity:clips -- run --kind songs --media 'D:\录播.flv' --srt 'D:\录播.srt' --xml 'D:\录播.xml'`。人工 `--scan` 仍共用一次完整文本检测，但只对所选类别做原音复核和渲染。

两阶段保留同一个计划签名、`PLAN.json`、`SONGS.json` 和投稿 manifest。`calibratedKinds` 区分已校准与尚未开始的类别；只有视听先完成时，歌单标记 `awaiting_songs`，不能当成未唱歌。后续阶段合并投稿记录并保留已有审核索引、数字 ID、视频与批准状态；单类失败不会清空另一类已完成的候选和成片，重跑继续复用同源梗概、校准和成片。已有成片后，源、梗概或制作参数变化需要显式审核修订，后续类别不能自动替换原计划并另造投稿包。

边界服务故障恢复后，可显式执行 `run --kind songs --retry-boundaries`（视听使用 `watch`），其他输入参数与原命令一致。该命令只重试所选类别中 `uncertain` 的原始候选，保留已确认项目和另一类别，累计请求不超过原每场预算；普通重跑不会触发此重试。必须有同源待审核成片，已批准、排队、上传中或已发布稿件会在请求前被拒绝。旧计划、歌单、审核清单及元数据备份到 `temp/boundary-revisions/`，新视频和封面写入独立版本目录，原视频保留；元数据路径、manifest 索引和数字 ID 不变。重试后仍需审核，全部候选被排除时旧包失去有效活动，不能批准上传。该恢复不支持 `plan`、`--scan` 或整场重新检测。

不超过 90 秒的片段演唱也保留配置的 `boundaryContextSeconds` 前后文，不再缩为
两端各 15 秒，避免漏掉粗定位前的歌词或稍后的续唱。仍用一个短音频区间、原每场
请求和音频预算；上下文不闭合则继续待核，不因扩大上下文自动确认歌名或投稿。

服务路线需要替换时，使用 `run --kind songs --retry-boundaries --revise-verifier --revision-note '具体授权与路线原因'`。该修订必须只改变复核设置：原媒体、字幕、共享梗概、分 P 参数和已注册包身份保持一致，源签名不符会拒绝。已批准或在投稿队列的包不能修订。保留原计划签名、manifest、数字 ID、旧视频和历史用量，在 `verifierRevisions` 记录前后设置与授权原因；新路线只获一份明确记录的最多三批附加额度，累计请求数继续增加。普通重跑、同路线重复修订和回到已用路线都不能重置预算。

粗定位将试听/练唱和后面的正式演唱混在一起时，可给待核歌切重试附加 `--review-prelude`。仍使用原累计预算；只对待核候选提取完整粗区间和上下文，每三十秒提取原帧。只有独立听写包含明确的新开唱宣告、之前整个试听阶段有完整音频和画面覆盖、正式演唱连续且首尾闭合，才允许修订粗起点。保留宣告所在完整八秒原音块及后续前奏、演唱和尾奏，不能裁掉一段歌词或缩短结束点。`preludeCorrection` 连同原粗定位、模型原答复和所有出处保留，投稿时重新计算；不明则继续待核。

一场直播分别生成最多两个投稿包：

- **歌切**：每次实际演唱一个视频、一个 P，保留前奏、间奏、尾奏；重复演唱和有歌词的片段演唱各自保留，片段会在 P 标题注明。没有证据确认歌名时保留演唱并写 `name: null`。
- **同步视听**：按实际观看顺序保留完整会话，包括暂停、反应和讨论，每部作品/剧集单独计算连续分段，再放入本场同一个投稿。默认目标 1500 秒（25 分钟）、最大 1800 秒（30 分钟）；均衡分 P，避免很短的末 P。不足 20 分钟的完整会话保留原时长。超过 100 P 时保留计划并报错，需要人工处理。

两类保留原始直播音画，不烧入未经歌词校对的混合音轨 ASR 字幕。准确解码/编码切片避免流复制从关键帧提前起播造成分 P 重复或遗漏，使用现有 NVENC/CUDA 设置、CPU 回退和自动资源调度。每个视频的实际时长必须与源区间相差不超过 0.25 秒。分 P 控制视频时长，不能保证影视内容通过 B 站审核；审核拒绝需根据实际原因处理。

## AI 用量与企微汇报

每次歌切、视听处理在目录内分别保存 `AI_USAGE.songs.json`、`AI_USAGE.watch.json`；未指定类别的手动命令使用 `AI_USAGE.activities.json`。每次服务商请求完成即保存，按阶段、模型记录输入、输出、缓存和推理 token，并记录失败、未知用量、本地缓存复用及本地 ASR 时长。结束或失败后通过既有企微 webhook 汇报本次及该工具累计用量；`streamActivityClips.notify.enabled=false` 可关闭该通知。

统计覆盖该处理进程内实际发生的请求；复用的既有直播梗概不重复计费，其原请求仍记录在 `LIVE_CONTENT.json.generation`。缺失的服务商字段保持未知，缓存/推理 token 不重复加到总量，不按未经核实的价格推算账单。通知状态保留 `sent`、`not_sent`、`unknown`；通知失败不会重跑模型，状态未知不自动重发。新统计不会补造旧进程没有记录的请求。

## 栏目封面与标题

歌切和视听使用独立栏目包装，不沿用普通趣味切片的 `【小岁】` 前缀、梗句标题或双层描边大字。

- **歌切**：视频主标题为 `【岁己歌切】歌名-2026.10.2`，使用开播录制日期，月日不补零。多首投稿按演唱顺序使用 `歌名一 / 歌名二-2026.10.2`，各 P 为 `歌名-2026.10.2`；名称过长时稿件标题可简写为首歌名加“等 N 首”，完整歌名仍在各 P 和简介。加入专用合集时只去掉主标题开头的 `【岁己歌切】`，合集条目保留歌名与日期，视频主标题不受影响。封面为暖金与深灰的唱片封套，大字是实际歌名，日期紧随歌名醒目显示；多首逐行列出前三个不同歌名并标明总演唱数，长英文名按单词换行，不再把“歌切”或“本场演唱合集”作为封面主题。
- **同步视听**：视频主标题为 `【岁己同步视听】《作品名》｜2026.10.4`，先写实际播放的片名，再写开播录制日期，月日不补零。多部按观看顺序列片名，超长时主标题简写首部加“等 N 部”；各 P 为 `《作品名》01/06`（书名号后留空格）。封面模板 v2 保留一张完整观影截图，电影画面和主播均可见，只在右下角叠加片名与小号主播名/日期；不再使用占据画面的大字“同步视听”、栏目面板或虚构反应文案。默认取首 P 的中间帧，用户指定或人工更新时可以复用同一成片里更清楚的已审核原帧。合集条目省略 `【岁己同步视听】`，保留片名与日期。

已有证据确认的歌名/作品名才能进入标题；歌名未知保留待核，不能以“本场演唱”“片段演唱”代替歌名投稿。片段属性在简介/歌单中说明。未确认演唱者或完整边界的歌切不能批准。视听包装 v3 的未知片名使用“待确认片名”作为本地草稿，投稿验收拒绝空名和泛化类别名，不再自动以“电影同看”投稿。共享梗概的 overview 已写《片名》而时间线漏名时，只在该会话现有引用原文支持唯一名称时本地补齐并保留 titleEvidenceIds；支持“雷神3/雷神三”等序号表达，不从剧情、角色、无关推荐或未引用的弹幕猜名，也不新增 AI 请求。

封面由 `stream_activity_cover.py` 使用一帧实际视频和中文字体在本地排版，**不增加 AI 请求**。歌切与视听均使用封面模板 v2，渲染器保留旧模板兼容；歌切包装仍为 v2，视听名称/日期与截图包装为 v3。模板版本与输入签名独立于检测计划；换封面不会重做梗概、校准、ASR 或视频编码。日常重跑可升级尚未批准的旧版包装，已批准/上传的稿件保持原批准内容。

用户授权更新已发布包装时，先读取当前 BV 的主标题、P 标题与合集条目，保留线上人工改名；复用已有原帧在本地生成独立封面文件，通过 `src/scripts/update_cover.py --bvid ... --cover ...` 修改当前稿件封面，再读取稿件与合集确认生效。已符合规则的合集名不重复写入，需改名时修改合集 episode 的标题字段。原审核元数据、视频、上传状态与数字 ID 保留，不能用 `restyle` 绕过发布保护或再上传视频。
需要同时改名时，`update_cover.submit_cover` 接受显式 `title`、`description`、`part_titles` 与 `expected_videos`；读取前后稿件与各 P，发现并发文案/P 变更即拒绝覆盖，原 cid、filename、P 描述和字幕/互动设置保留。用户未授权改名时不传这些参数。已退回稿件的重提仍是独立任务，不能因这次包装调整自动重提。

已有待审核包可显式更新，保留视频、原数字 ID、旧封面及原元数据备份，并刷新 `REVIEW.md`：

```powershell
npm run activity:clips -- restyle --manifest 'D:\...\UPLOAD_MANIFEST.json'
# 只更新其中一类
npm run activity:clips -- restyle --metadata 'D:\...\songs.json'
```

命令拒绝修改已批准、排队、上传中或已发布的稿件；封面制作全部成功后才写入新元数据。更新包装仍是待审核，投稿授权继续使用下文的 `approve --enqueue`。

一类只包含一个活动时，若实际封面源画面明确显示作品名，可在核对原图后给单条 `restyle --metadata` 附加 `--content-name`、`--evidence-frame`、`--evidence-note`。证据必须是该投稿包 `temp/presentation/` 下提取的 `frame.jpg`；文件摘要和所述原文保存在 `presentation.titleEvidence`。该文案校对不修改检测中的未知名/边界，不凭截图确认演唱完整性，也不额外调用 AI。

多首歌名可使用 `restyle --metadata '...songs.json' --title-evidence '...reviewed-names.json'`。文件为 `{"items":[{"activityId":"activity-1","name":"歌名","sourceAlias":"原字幕里的歌名","segmentIndices":[123],"note":"为何能确认这是该首歌"}]}`；索引是该 PLAN 的 `transcript.path` 中从一开始的字幕段编号，时间修复过的源不能改用旧 SRT。引用必须在活动前三百秒至结束后六十秒内并逐字支持名称或经过复核的原文译名。保存完整原句、时间、字幕摘要，投稿验收重新读取；多个活动不能借用另一首的名称。已发布旧稿只修改已有 BV 文案，不重新投稿视频。

## 产物与歌单

产物放在录播旁的 `stream_activity_clips/<录播基本名>/`；归档录播沿用原有 D/E 输出映射。`PLAN.json` 保存源文件身份、梗概输入覆盖、活动与校准；日常的覆盖指完整梗概文本输入，不代表听过整场视频。`SONGS.json` 是每场格式化歌单，包含场次、房间、开播时间、歌曲名或空值、每次演唱起止与时长、完整/片段类型、证据 ID、待核项和 P 序号，并引用粗定位梗概及成本数据。`status: failed` 与一个成功检查且 `songs: []` 的歌单含义不同。`LIVE_CONTENT.json.content.songs` 继续作为梗概；统计应使用歌单以保留重复、未知歌名和时间区间。

视频和两个投稿元数据位于计划签名命名的子目录。`songs.json`/`watch.json` 各自引用所有分 P，`UPLOAD_MANIFEST.json` 每类只有一条投稿记录，`REVIEW.md` 列出本地视频、合集和审核命令。重跑复用源文件和参数完全一致的检测缓存及已完成视频，保留审核结果；已审核视频变化时不能直接覆盖。活动处理失败或仍有待审核投稿时，后台流程保留原录播，供检查完整边界、修订及源文件身份校验。

```powershell
$env:NODE_ENV = 'production'
npm run activity:clips -- plan --media 'D:\录播.flv' --srt 'D:\录播.srt' --xml 'D:\录播.xml'
npm run activity:clips -- run --media 'D:\录播.flv' --srt 'D:\录播.srt' --xml 'D:\录播.xml'
npm run activity:clips -- stats --root 'D:\files\videos\DDTV录播\25788785_岁己SUI'
```

可选 `--summary 'D:\..._LIVE_CONTENT.json'` 与 `--full-context 'D:\..._FULL_LIVE_CONTEXT.json'` 指定同源梗概和共享输入。自动下播会等待该场梗概完成再启动歌切，避免多个进程重复补请求。梗概保留原有公开内容字段，内部新增 `activityTimeline`；后者绑定 SRT/XML 摘要及共享输入摘要，改过源文件后不能复用旧时间线。

统计输出按歌名汇总音画已确认的演唱次数、片段次数和涉及场次；未知歌名、未确认演唱候选 `unverifiedPerformances`、失败/未完成场次单独计数。歌单逐项保留 `verificationStatus`，未确认候选不计入已确认歌数，不伪装成已识别或没有演唱。

## 审核、投稿与合集

自动制作只注册待核投稿短 ID。检查实际演唱/观看、完整起止、P 标题和文案后批准具体投稿包，可显式加入现有上传队列：

```powershell
npm run activity:clips -- approve --metadata 'D:\...\songs.json' --note '已核对实际演唱者、前奏尾奏及所有歌曲标题' --enqueue
npm run activity:clips -- approve --metadata 'D:\...\watch.json' --note '已核对完整观看起止、作品标题与连续分P' --enqueue
```

省略 `--enqueue` 只保存审核结果并刷新 ID。队列计数、90 次/24 小时额度、137022 冷却、查重和 406 恢复都按**投稿包**计算；不会把各 P 拆成独立投稿。活动包上传允许至少四小时 subprocess 时间，适合长素材。所有 P、顺序、区间、封面、文案和合集路由都绑定审核摘要；修改或丢失任何一个 P 均拒绝上传。投稿成功后只把该 BV 加入对应专用合集一次；合集失败记录错误，不重复投稿视频。

真实上传前查询官方视频投稿页实际使用的 `archive/white` 与 `archive/pre`，取得当前**网页投稿渠道**的权限和文件限制。不要用创作中心通用的 `white` 替代 `archive/white`：两者的 `have_permission_of_p` 可以不同。`have_permission_of_p` 控制网页新增分 P，`new_web_edit.max_count` 与 `single_max_count` 分别给出稿件 P 数及网页单次添加数量；本项目活动包仍保留最多 100 P 的本地限制。`season` 与 `season_add_multip` 分别确认合集和多 P 入合集权限，不能把“可建合集”当成“多 P 可入合集”。未开通时返回 `capability_blocked` 并保留同一个完整投稿包，不自动拆成独立投稿。这些网页能力不代表所有客户端渠道的资格，也不能推导出粉丝数或等级门槛。

`approve --enqueue` 在入队前也检查当前权限；失败时保留本地批准和原短 ID，直接报 `[BLOCKED]`，不创建反复失败的上传任务。权限恢复后可把同一个已批准 ID 加入现有投稿队列，实际上传仍会再检查。

生产合集在 `streamActivityClips.songs.collection` 与 `watch.collection` 中独立配置，`seasonId` 是展示用合集 ID，`sectionId` 是创作中心实际加入小节的 ID。不使用按房间匹配的通用合集路由，避免把原有趣味切片也改投歌切/视听合集。

`npm run activity:collections` 只查询；`npm run activity:collections -- --apply` 创建缺少的“岁己歌切”和“岁己同步视听”，按精确名称复用已有合集，使用岁己自动切片合集封面。输出的 ID 写入生产配置，不能把 season ID 当作 section ID。遇到“合集编辑过于频繁”先重新查询部分成功结果，稍后仅创建仍缺少的一类；不盲目重复创建。
