# 岁己歌切与同步视听

`streamActivityClips` 与原有趣味切片并行存在。生产环境只对房间 `25788785` 开启，在下播后台队列运行。默认 `detectionMode: "summary"`，复用本来就要生成的直播梗概，不再另扫全场字幕/弹幕。

日常流程只有三步：

1. **出梗概时顺便粗定位。** 同一次请求、同一份完整 ASR/弹幕输入，输出普通梗概和 `activityTimeline`，记录每次实际演唱与每个完整观看会话的粗起止、标题或空值、原文引用。共享提示前缀保持一致；新增输出不额外发起全场检测请求。主播实际唱歌、播放歌曲、点歌未唱和影片声音分别判断，未知歌名仍保留演唱。
2. **只校准附近短音频，一轮合批。** 整首歌曲与观看会话只取开始/结束附近的音频（默认外侧 45 秒、内侧最多 15 秒，观看开头至少覆盖此前 90 秒并避开上一活动）；短片段取本段加前后最多 15 秒。本地独立运行 SenseVoice 和多语言 Whisper，分短段保留原始识别、语言、音频事件和时间原点，不输入源字幕或改词规则。DaiYu GPT 只接收这些文本、一秒能量数据和原帧，明确没有收到音频；不会向它发送 `input_audio`，也不会自动回退 TuZi Gemini。每批最多 8 项、600 秒音频，每场最多 3 批远程请求，每批超时 60 秒，只请求一轮。电影和歌曲中间保持完整，不另送整场录播、整首歌或每 P 做检查。
3. **直接制作两个投稿包和歌单。** 成功边界用于切片；校准失败、格式错误或预算耗尽直接标记待核，不再换模型重试或启动昂贵检测。不确定歌切保留前后余量，观看保留连续会话。重跑复用同源梗概、校准结果与成片。

能量数据和音频事件标签不能证明演唱者身份。保留决定须有本候选独立听写中的字面引文、演唱前后语境和原帧支持；混合源字幕仅作辅助。模型用明确的音频序号和片段内秒数返回边界，程序换算为录播秒数，拒绝借用另一个候选的音频。所有演唱都不能截入已观察到的演唱区间内部；精确前奏/尾奏不清时可保留已经证明完整的上下文包围区间，标记 `complete_context_enclosure`，不能宣称 GPT 听过原音或精确定位了音乐起点。窗口外仍可能有演唱或播放者不明时继续待核。无法确认时记录 `provisionalWindow`、`media_verification_unconfirmed` 与边界待核项，不计入确认歌数；排除的误检留在 `rejectedActivities`。

已有梗概没有时间线或手工处理旧录播时，只补一次包含时间线的梗概请求。时间线缺失/不完整、源摘要不匹配时保存失败状态，不把它解释为本场没唱歌，也不自动启动另一套全场扫描。源 SRT 的已知对齐异常会标记 `source_transcript_timing_unreliable`；默认只复用已完成的修复转写，**不会为了歌切重做整场 ASR**。

梗概请求使用严格 JSON Schema：公开 `songs/games/topics/activityTypes` 保持字符串数组，演唱和观看的时间、未知名称及引用放在独立的 `activityTimeline.events`。格式约束不替代时间范围和源证据校验；非法对象或空值不能被直接转成歌名。格式失败保留 `failed`，失败尝试在 `generation.attempts` 保存返回原文及 SHA-256，供定向修复后重跑。

梗概提示 v2 明确区分本场实际活动、观众推荐、未来计划和拒绝/取消；角色介绍、查资源、试画质、预告或拉片解说不能证明观看了对应正片。梗概与时间线均须结合前后语境，保留否定和后续决定。请求时间线时，缺失、不完整或引用校验失败会使本次梗概保留为 `failed`，不再保存成可发布的成功梗概；旧提示版本和不完整时间线不能作为成功缓存复用。修复重跑仍使用同一份完整字幕/弹幕，不另扫视频或重做 ASR。

`PLAN.json.efficiency` 记录实际新增的全场扫描次数、整场 ASR 次数、边界请求批数、音频秒数、缓存命中与耗时。日常前两项应为零；已完成梗概的本场切片只有局部解码和边界请求。默认 `verification.evidenceMethod: "independent_local_asr"`、`provider: "daiYu"`、`apiMode: "openai_chat"`，使用现有 DaiYu 凭证。本地 Whisper 只读已安装模型，不自动下载或切换远程服务。显式 `native_audio` 保留给独立配置的原生音频路线。原音提取、独立解码、原帧和远程答复都有出处和摘要，投稿验收重新读取。

`run/plan --scan` 或 `detectionMode: "standalone_scan"` 是人工排查召回遗漏的旧检测模式：全场拆窗口、逐项音画复核，必要时修复已知漂移转写。它不作为日常流程的自动回退。

## 从弹幕和歌词识别歌名

`identify-songs --metadata <songs.json> [--activity-id <id>] [--hint <用户线索>]`
是只读检索命令。它先读取本段附近的选歌讲话、弹幕点歌和实际歌词，由模型提出最多
4 个有本地引用的搜索词，再请求公开歌曲目录及歌词。外部名称只作为候选；至少
3 句不同歌词、3 条不同源字幕、30 个匹配字符并跨越实际演唱时段，才建立名称证据。
歌词引用只能来自对应活动内；点歌、近音报幕和模型猜测本身不证明作品或演唱者。
同一作品的专辑/现场/翻唱版本归一，不同作品都有歌词支持时保留待核。

结果通过 `ACTIVITY_SONG_IDENTIFICATION_RESULT` 返回，研究记录和 `title-evidence.json`
写到原包 `temp/song-research/`，不改包或队列。确认匹配后用现有
`restyle --metadata <songs.json> --title-evidence <返回路径>` 更新标题、简介、封面和 P 标题。
`catalog_lyric_match` 绑定源字幕摘要、目录来源、歌词摘要和逐句对应关系；
重用包装及 Python 投稿审核均重新验证。它不替代独立原音、完整边界或最终成片审核。
边界修复后可直接 `restyle --metadata ...` 重绑已知目录歌曲：先验证旧证据的原文与摘要，
再仅从当前保留演唱中重新匹配歌词、生成引用。当前范围不足以支持名称则拒绝；无需为
同一已知作品重新联网搜索，最终投稿检查仍严格拒绝范围外引用。

`streamActivityClips.songs.identifyNames: true` 开启新歌切包的自动检索，在首次生成后、
最终发布审核前运行一次；保留失败诊断，不把失败当成已识别。默认关闭，已有包、
已批准或已投稿包不会因打开设置被批量改名。测试注入目录/模型适配器，不请求真实服务。

对同一数字 ID 的反馈，`review --metadata <songs.json|watch.json> --note <保存的意见>`
执行完整自动终审，记录绑定本次意见和时间的 `activityOperatorReview`，批准仍标为
`authority: automatic`。该命令只处理已登记且未投稿的待核包，备份旧元数据，逐 P 核验
实际成片、全文、封面和边界；完成后单独调用原编号入队命令。它不把 agent 分析登记为
人工确认，不授予其他历史包自动投稿资格。明确的“核对无误”仍使用人工 approve。
终审同时检查当前成片是否落实保存的意见。若歌曲或观看包的终审明确拒绝某个 P 的边界，
可用 `run --kind songs|watch --retry-boundaries --review-boundary-ids activity-N --revision-note ...`
重开该活动，读取终审失败原因并保留已通过的兄弟活动。此修复本身不授予自动投稿；
原编号仍须通过再次完整终审。只有绑定的当前终审失败、尚未入队/投稿的编号才可重开。

对独立听写仍无法区分播放/现场演唱的歌切，可显式组合
`--retry-boundaries --review-prelude --review-audio`，使用已配置 Gemini 对这一段完整原音
及原画面补充观察，再由原 DaiYu 边界核验交叉判断。补听和边界各计一次原请求预算，
至少保留两次额度；503 等暂时故障只在剩余额度内重试，仍为最终边界核验保留一次。
无自动跨提供方回退。补听返回文本不是批准，原音、画面、模型响应和摘要全部留档，
Node 复核、Python 投稿检查和最终成片审核均使用绑定证据。
`verification.nativeListening: {version:1,protocolVersion:2,model:"gemini-3-flash-preview"}` 可随显式复核路线
修订登记；不改变本地双模型识别设置，也不重置历史消耗。协议 2 隐去粗定位候选时间，
强制返回片段内时间并重验每个引用音频和区间，拒绝把绝对录播秒数当成听音结果。
长原音仍有时间漂移时可显式修订为 `protocolVersion:3`：把同一证据区间按最多 60 秒
连续分段，一次补听请求覆盖所有分段。每段时钟从零开始，程序映射回原独立解码时间轴；
复用已有本地识别，保留完整前后语境。投稿检查重新核验每段原音提取记录、连续覆盖、
原始响应和时间映射，缺段或越界继续待核。该路线仍消耗原预算，分段本身不授予审核通过。
未变化的已绑定补听可复用：再次核对来源、全部输入摘要、候选和模型后，只重跑独立边界
判断，继续累计实际新增请求。多附件请求为每段附上编号，文字说明中的分段编号也映射给
下游审核，避免把分段编号误读为原解码音频编号。

显式 `verification.preludeReviewVersion:3` 与 `--review-prelude --review-audio` 可处理
试唱后完整重唱。前一段可能含主播试唱，不再强制证明全是播放器声音；必须有独立
原音支持完整重唱、选歌讲话前后相同的开头歌词，以及未丢失独有主歌/演唱内容的证明。
保留整个选歌讲话块及之后全部内容，禁止截短尾部。Node 和投稿检查重放相同引用、
连续画面和原音证明；仅重复副歌、未完整重唱或仍有独有内容会继续待核。

### 用户明确确认作品名

原音研究已给出名称、用户随后明确接受该名称时，仍用 `restyle --metadata ... --title-evidence ...`
修订原待审核 ID。证据文件可用 `{"items":[{"activityId":"activity-1","method":"explicit_user_title","name":"作品名","confirmation":"用户原始确认","note":"所接受的名称及研究依据"}]}`。
该入口记录 `authority: user`、`audioVisualReviewed: false` 和活动原范围，不冒充字幕、画面或自动歌词匹配证据。
它仅修订标题、封面与 P 文案；投稿必须另用已有 `approve --feedback-authorized --enqueue`，
入队和实际上传都要求人的反馈接受记录，不能继承自动发布权限。来源、成片及重复投稿检查继续生效。

## 最终审核后自动入队

用户明确接受当前包并要求投稿时，可沿原数字 ID 使用
`approve --metadata <songs.json|watch.json> --note <原始反馈与授权> --feedback-authorized [--enqueue]`。
这记录 `acceptanceMode: feedback`、`audioVisualReviewed: false`；`authority: human`
只表示人的投稿授权，不表示逐句核听或已经完成独立边界审核。
活动保存 `explicit_user_feedback` 接受记录及原独立核验、待核理由和旧包审核，
不把 uncertain 改成独立 keep，不消耗或重置边界预算。原 P、范围、音画和曲名不变。
只有这个显式入口可接受已有 AI 待核意见；自动终审仍要求独立核验通过。
来源版本、字幕侧车、曲名证据、每 P 文件摘要、时长和顺序继续验证，入队及实际投稿
仍通过原注册表和单实例 worker；反馈授权不允许重复投稿或使用失败/变化的成片。

最终审核若发现某个观看 P 混入下一视频，可在确认原帧后使用
`run --kind watch --retry-boundaries --retry-publication --review-boundary-ids activity-N --revision-note '具体边界问题'`。
该入口只接受原 ID 尚未投稿、当前最终审核确实有边界失败且所选活动属于失败批次的情况。
它重新读取原粗候选，补采粗结束点、旧成片结束点和结束上下文的原帧，结合独立原音重新校准；
不会继承旧批准、手改边界或重置每场预算。未变的 P 可复用，变化的 P 重新渲染，整包重新审核。

`streamActivityClips.automaticPublication` 默认 `off`。生产按用户授权为房间
`25788785` 使用 `mode: auto`、`policyVersion: stream-activity-v1`、明确 `roomIds`、
`activatedAt` 与 `authorizationNote`。新制作且晚于启用时间的 summary 模式投稿包
才带 `activityAutomaticPublicationRequired`。手工扫描、restyle、旧包导入或边界重放
不自动取得该授权；显式修复本场字幕时间轴后重新制作的包重新走当前最终审核。

独立原音校准必须确认实际演唱/观看、闭合的完整起止，且没有待核问题。最终审核
另读实际封面、每 P 的首中尾抽帧、完整活动与分 P 表、独立解码结果及边界答复，
完成全片媒体解码检查，绑定当前来源、文案、所有 Ps、标题与封面。AI 通过保存为
`activityReview.authority: automatic`，不会声称人工听审。注册表登记原数字 ID 后，
通过包才进入既有单实例上传队列；上传前再次校验文件、证明和当前生产授权。
实际多 P 权限预检仍执行，未确认的歌名、人物、边界或源字幕时间异常继续待核。

审核/队列结果写进既有 `REVIEW.md` 和 AI 用量列表，区分已投稿、已排队、待入队、
待人工复核。未收到队列回执时保留“入队结果待确认”，不盲目重投；已排队或发布
的 ID 也不重复入队。不增加逐片成功消息或 BV 消息。保留原录播供异步上传校验。

## 已知字幕漂移的显式修订

普通切片检测到 Paraformer `sentence_info_fallback` 的已知时间轴异常时，只对该异常
重建一次分段转写及本地声纹证据，保留原 SRT。WAV 解码保留时间戳空隙并补齐音视频
尾部小差值，再核对完整时长；不会用一个猜测偏移平移字幕。两种活动复用已完成
的转写，正常日常活动处理不额外转写全场。

本场已有错误待核包时，用 `activity:clips run --repair-timing --transcript-record
<RESULT.json> --revision-note <修复原因>`，并照常传原 media/SRT/XML 和匹配的新共享
梗概。该修订要求原录播和源证据未变、所有既有包未批准/入队/发布，同时修订两类
检测。原计划、歌单、审核、manifest 和元数据先备份；原数字 ID、metadata 路径与
manifest 保持，旧视频保留，新视频写独立版本目录。新时间线重新校准、渲染、最终
审核，不继承错误包的通过状态，也不手改 queue JSON。

## 分阶段优先级与恢复

最终发布审核按传输上限分批：每批最多两个 P，传入实际封面和各 P 的首、中、尾帧。
每个 P 的三帧组成一张带 BEGIN/MIDDLE/END 与录播时间的证据图，标签不遮挡原帧，
两 P 批次只需三张图片。`reviewScope` 列出本批 P 编号、图片和帧位置；每次 AI 的
内容/画面/政策检查只负责本批，其他 P 由独立批次检查，全部通过才批准整包。
视听证据图在保留原首、中、尾帧的基础上，增加开头后两秒、中段前后两秒、末尾前两秒
的邻近帧，按三列网格逐行排列，所有采样限制在当前 P 内并标注真实录播秒数。
电影换 P 的短黑场可能正好落在制作切点或中段采样点；邻近帧用于判断短暂转场与持续
画面缺失，不删除黑帧、不凭黑场对齐直接判定通过。歌切仍使用原三帧图。
审核证明保留 `evidenceVersion:3`，新增 `sampleEvidenceVersion:1`。
已绑定黑场对齐证据的视听原 ID，旧三帧协议仅 `visuals` 待核、其余检查及所有批次
的其他检查均通过、没有 rejected 时，可用 `--retry-publication --revision-note ...`
显式补充邻近帧一次；完整成片与来源重验、全部批次重新审核，旧证明及升级出处保留。
普通重启、同版证据、其他失败、已批准/排队/回执不明/已投稿包均不触发该升级。
每批同时读取全部活动、分 P 时间线、本批每个 P 的完整保留字幕与活动前后各九十秒的
源文本，并读取本批窗口内原始弹幕。分批的并集覆盖全部 P，不为每批重复整场文本。
共享原音解码与边界响应按文件去重，每个活动明确引用自己的当前证据；保留完整观察，
不在活动元数据里再次嵌入解码全文。片名上下文中的活动内弹幕随对应 P 审核，活动外
上下文仍随每批提供，避免整段观影弹幕在每批重复。完整原始文本仍保存在最终审核档案。
字幕/弹幕分别注明来源和绝对录播时间，不能凭混合音轨字幕
确认说话人或把影视对白当作主播家庭经历。原音校准与完整文本一起供独立判断；
全部批次明确通过才批准整个投稿包。理由只含一至两条中文阻塞项，完整原答复仍保存。
审核服务或图片传输不可用时保留原包和失败原因，不自动反复请求。修复故障后可用
`run --kind watch --retry-publication --revision-note '具体故障与修复原因'`（歌切使用
`songs`），照常传原 media/SRT/XML。该命令只复核原 ID 的当前成片，复用原计划、
转写和所有视频，不重新检测或压片；旧待核元数据备份到 `temp/publication-retries/`。
它处理 `automatic_activity_review_unavailable`；对旧版未传完整文本、仅边界或政策
检查待核的包，也允许显式补证一次。旧 proof 必须仍绑定当前来源，内容、标题和
画面检查全部通过，且没有任何 rejected 批次。旧 `evidenceVersion:2` 分批材料若边界
全部通过且无 rejected 批次，也可显式升级一次到带标签证据图和明确分批范围的协议。
升级重新审核所有批次，不继承旧批准。新审核保存 `evidenceVersion:3`、完整文本、
图片摘要、分批范围和升级出处；同版材料不能再重试，真实拒绝不因重试获准。已批准、已排队、回执不明
或已发布的包不能重试；当前来源或成片变化也会拒绝。

自动下播按普通切片、歌切、游戏完整切片、同步视听依次处理。歌切与视听共用本场梗概，但分别开始短音频校准和媒体制作；不会在歌切阶段先校准或渲染视听。所有阶段共用每场边界请求预算，视听不会重置已经使用的额度。

歌切因共享梗概未就绪而失败、随后视听成功取得同源梗概时，后台只补做一次歌切。
补做仅能读取并重新校验已有成功梗概，不新增梗概请求；其他失败不触发此恢复。
时间线引文校验报告具体活动、引用 ID 与秒数，提示要求每条引用位于活动前后 180 秒内。

独立听写的短中文收尾语（如“看完了”）可以作为补充证据；每条至少两字且须逐字匹配
指定音频块，每个候选仍至少需要一条四字以上的上下文引用，演唱者和完整起止检查不变。
单个候选引用失败只将该项标记待核，不丢弃同批其他合格项。短音频推理仅附带对应窗口的
混合源字幕，不重复传入整部电影的文本；最终发布审核仍覆盖全部保留字幕。
歌曲的短音频窗口还会覆盖候选已引用的选歌讲话（最多向前 180 秒），以及结束后
120 秒内首次“唱完/唱得”等收尾讲话（最多取至结束后 135 秒）。源字幕只用于定位，
新覆盖的原音须独立解码并按原批次/每场预算复核，不能凭源字幕直接确认演唱者。
复核结合选歌、演唱和收尾的连续证据，避免一句同音误识压过完整语境。
共享梗概已有歌名、候选引用中逐字出现且相邻三秒内有选歌语境时，本地补齐标题依据；
多个候选歌名冲突、仅弹幕点歌或同音改写仍须独立校对，最终发布审核保留。
分 P 区间在压片前检查顺序和重叠，冲突保留计划与原始候选，不裁切证据来凑区间。
这种尚未压片的 `planned` 计划也可使用 `--retry-boundaries`，沿用原预算并备份计划。

`complete_context_enclosure` 与精确音乐起止分别记录：独立证据重验确认两端上下文闭合、
区间完整包围演唱时，允许 `startObserved/endObserved: false` 保留“未精确定位音符”的事实。
发布检查只在原音、听写、模型原答复及区间全部重验通过后，将这两个精确边界标记视为说明项；
待核演唱者、源时间异常、区间重叠或其他待核项仍阻止发布，最终 AI 审核仍须通过。

对于已有自动发布资格、尚未投稿且最终审核因故障未完成的原 ID，显式恢复可组合
`--retry-boundaries --retry-publication --revision-note '具体修复原因'`：备份旧包，重新校准和
制作当前版本后重新执行完整发布审核。普通边界重试不获得自动发布资格；已批准、入队、
回执不明或发布的包仍拒绝该操作。此组合不继承原审核通过结果，也不重置请求额度。

`run/plan --kind songs` 只处理歌切，`--kind watch` 只处理视听；不传 `--kind` 仍处理两类。恢复歌切可用 `npm run activity:clips -- run --kind songs --media 'D:\录播.flv' --srt 'D:\录播.srt' --xml 'D:\录播.xml'`。人工 `--scan` 仍共用一次完整文本检测，但只对所选类别做原音复核和渲染。

两阶段保留同一个计划签名、`PLAN.json`、`SONGS.json` 和投稿 manifest。`calibratedKinds` 区分已校准与尚未开始的类别；只有视听先完成时，歌单标记 `awaiting_songs`，不能当成未唱歌。后续阶段合并投稿记录并保留已有审核索引、数字 ID、视频与批准状态；单类失败不会清空另一类已完成的候选和成片，重跑继续复用同源梗概、校准和成片。已有成片后，源、梗概或制作参数变化需要显式审核修订，后续类别不能自动替换原计划并另造投稿包。

边界服务故障恢复后，可显式执行 `run --kind songs --retry-boundaries`（视听使用 `watch`），其他输入参数与原命令一致。该命令只重试所选类别中 `uncertain` 的原始候选，保留已确认项目和另一类别，累计请求不超过原每场预算；普通重跑不会触发此重试。必须有同源待审核成片，已批准、排队、上传中或已发布稿件会在请求前被拒绝。旧计划、歌单、审核清单及元数据备份到 `temp/boundary-revisions/`，新视频和封面写入独立版本目录，原视频保留；元数据路径、manifest 索引和数字 ID 不变。重试后仍需审核，全部候选被排除时旧包失去有效活动，不能批准上传。该恢复不支持 `plan`、`--scan` 或整场重新检测。

普通续做和边界重试复用同源计划保存的 `verificationSettings`，避免生产默认超时或
其他复核默认值变化使已修订任务无法恢复。只有显式 `--revise-verifier` 才采用当前
复核参数并登记新版本；源、梗概和分 P 参数仍须一致，重复同版不能增加预算。

新计划的 `verification.watchContextVersion: 1` 在粗结束点后最多十五分钟的源字幕中
寻找“看完了”“没有彩蛋”“下一个看”等切换线索，并避开下一个活动。
开头原音至少覆盖粗起点前九十秒，并避开上一活动，
用于保留从选片/杂谈到实际播放的完整上下文。每个观看候选即使没有额外切换窗口，
也提供开头和末尾原音窗口两端的原帧及中段原帧，避免仅凭中段播放画面确认首尾。
后续“私下自己看”“不看了”等话语也只用于定位短音频和原帧，不能直接批准结束点。
所有新增证据仍受原批次音频上限和每场请求预算约束。
保留原首尾音频，再最多补两个短窗口，仍受每批音频和每场请求上限约束。
字幕线索只定位原音；独立解码必须确认实际停止或切换，不能把关键词当作观看结束。
额外窗口同时取切换前、中、后三张原帧，结合片尾、播放器状态与搜索/选片原话判断
当前作品是否结束；后续继续看同系列的另一条视频不等于当前作品仍在播放。
复核仍保留完整中段、暂停与讨论，全部分 P 继续走最终审核。
旧版待核包可用 `--retry-boundaries --revise-verifier --revision-note '补充结束点之后的切换证据'`
显式升级一次，沿用已有版本记录和累计用量，不重置预算。

观看边界待核时在编码前停止，保留 `planned` 计划和诊断；已有待核包及原 ID 不变。
尚未生成投稿包的边界恢复会对校准后的观看区间重新执行已启用的黑场对齐；
已有成片的边界修订仍按下面的复用规则保留原分 P，不自动重新对齐整包。
修订时区间、来源和摘要一致的原分 P 直接复用；只编码变化或完整性校验失败的 P。
只延长观看末尾时，保留此前完整分 P 的边界，只重新均分末 P 与新增尾段，避免整场
重新均分造成所有视频失效；仍校验无缝连续和每 P 最长三十分钟。
自动投稿包片名未齐也在编码前停止。可在 `run --kind watch` 或边界修订命令中提供
`--title-evidence <reviewed-names.json>`，使用下文的逐活动字幕引用格式，在制作前绑定
已核对的片名。它只修订包装，不改原检测，不授予批准；只重审原成片时仍先 `restyle`。

不超过 90 秒的片段演唱也保留配置的 `boundaryContextSeconds` 前后文，不再缩为
两端各 15 秒，避免漏掉粗定位前的歌词或稍后的续唱。仍用一个短音频区间、原每场
请求和音频预算；上下文不闭合则继续待核，不因扩大上下文自动确认歌名或投稿。

服务路线需要替换时，使用 `run --kind songs --retry-boundaries --revise-verifier --revision-note '具体授权与路线原因'`。该修订必须只改变复核设置：原媒体、字幕、共享梗概、分 P 参数和已注册包身份保持一致，源签名不符会拒绝。已批准或在投稿队列的包不能修订。保留原计划签名、manifest、数字 ID、旧视频和历史用量，在 `verifierRevisions` 记录前后设置与授权原因；新路线只获一份明确记录的最多三批附加额度，累计请求数继续增加。普通重跑、同路线重复修订和回到已用路线都不能重置预算。

边界复核遇到网络超时、连接中断、HTTP 408/429/5xx 时，同一材料最多尝试三次，
失败后分别等待 2 秒、8 秒；每次实际请求都计入原每场累计额度，额度耗尽立即停止。
有效答复中的待核、拒绝、引用错误、来源变化和配置错误不会触发自动重试。
失败记录保存在 `TRANSPORT_RETRIES.json`，服务故障仍保留已完成的独立原音证据，
审核明确报告复核尚未完成。显式边界恢复按原区间、来源、模型实现和 ASR 设置重验并复用
本地解码结果，不重跑整场识别。仅歌切已成片、视听因区间冲突尚未成片时，
`--kind watch --retry-boundaries` 也可恢复原视听候选，保留歌切包。
已有自动发布授权时，可组合 `--retry-publication --revision-note '故障恢复原因'`
让这份首次生成的视听包执行完整发布审核；不会继承其他类别的审核结论。
调整超时等复核设置须使用上述显式 `--revise-verifier` 修订及原因记录，不能直接重置预算。

粗定位将试听/练唱和后面的正式演唱混在一起时，可给待核歌切重试附加 `--review-prelude`。仍使用原累计预算；只对待核候选提取完整粗区间和上下文，每三十秒提取原帧。只有独立听写包含明确的新开唱宣告、之前整个试听阶段有完整音频和画面覆盖、正式演唱连续且首尾闭合，才允许修订粗起点。保留宣告所在完整八秒原音块及后续前奏、演唱和尾奏，不能裁掉一段歌词或缩短结束点。`preludeCorrection` 连同原粗定位、模型原答复和所有出处保留，投稿时重新计算；不明则继续待核。

没有固定“开始唱/请听”报幕时，`reviewPrelude` 也可识别独立的播放后重新演唱：
须有完整原音与原画面覆盖、独立听写中的选歌讲话、选歌前后同一句至少六字的开头歌词，
并明确确认先前是播放、随后从开头重新演唱。重复副歌、离席返回或静态立绘都不能单独
构成此证明。保留整个选歌讲话音频块、后续全部前奏/演唱/尾奏，不丢弃主播练唱或截短结束。
这类 `preludeCorrection` 使用 version 2，Node 与 Python 都重验引用、顺序、覆盖和原答复。

一场直播分别生成最多两个投稿包：

- **歌切**：每次实际演唱一个视频、一个 P，保留前奏、间奏、尾奏；重复演唱和有歌词的片段演唱各自保留，片段会在 P 标题注明。没有证据确认歌名时保留演唱并写 `name: null`。
- **同步视听**：按实际观看顺序保留完整会话，包括暂停、反应和讨论，每部作品/剧集单独计算连续分段，再放入本场同一个投稿。默认目标 1500 秒（25 分钟）、最大 1800 秒（30 分钟）；按具体作品的审核难度，可通过 `watch.targetPartSeconds` 与 `watch.maxPartSeconds` 配置更短或更长的分 P，两者必须为有限正秒数且目标不超过最大值。均衡分 P，避免很短的末 P；较短的完整会话保留原时长。长度选择不是自动过审判断。超过 100 P 时保留计划并报错，需要人工处理。

两类保留原始直播音画，不烧入未经歌词校对的混合音轨 ASR 字幕。准确解码/编码切片避免流复制从关键帧提前起播造成分 P 重复或遗漏，使用现有 NVENC/CUDA 设置、CPU 回退和自动资源调度。每个视频的实际时长必须与源区间相差不超过 0.25 秒。分 P 控制视频时长，不能保证影视内容通过 B 站审核；审核拒绝需根据实际原因处理。

### 将视听分 P 对齐电影区域黑场

新计划可选启用 `watch.blackAlignment`，或在 `run/plan` 传
`--watch-black-region 'x,y,width,height'`。坐标均为相对整帧的 0–1 比例。
先检查会话开始、中间、结束原帧，选择实际电影内容内部的矩形，避开主播、聊天栏、
播放器固定黑边、字幕和角标。画面布局变化时拆成独立观看会话或停用这项检测，
不能把前一场区域盲目应用到全场。区域定位是人工原帧确认，不是自动识别播放器。

检测使用本地 FFmpeg `crop + blackdetect`，逐源帧处理；优先 CUDA 解码，失败用软件解码，
共用现有低优先级 FFmpeg 资源门控，一次一个窗口/一个线程。不需要 OpenCV、ASR 或远程模型。
`nvidia-smi` 只提供显卡利用率，不能判断画面是否黑。
均分切点前后各 300 秒提供兜底扫描；周期预测另有下述有界起始窗口和局部验证，
不另扫完整电影。
候选黑场持续 0.35–8 秒，至少 98.5% 区域像素低于 `pixelThreshold: 0.08`。
过短闪黑、持续黑屏/暂停和被窗口边缘截断的黑场不选。切点取黑场中间，
所有切点一起求解：保持原 P 数、观看起止、连续无缝覆盖与当次 `watch.maxPartSeconds` 上限；
优先增加落在黑场中的切点，再优先已经局部验证的周期点，最后选各 P 时长最接近原计划的组合。
原计划有长短不一的 P 时保留其长度安排。默认对齐下限为 900 秒，实际取该值、当次长度上限的一半、
原计划最短 P 三者中的最小值，让短分 P 也能微调；可用 `blackAlignment.minPartSeconds` 指定正秒数。
单 P 完整会话不延长。找不到可用黑场就保留原计划切点。
黑场可能是自然转场，检测不能证明影片网站真正换 P；它只提供减少播放中断的候选。

固定长度的电影 P 使用 `blackAlignment.cadence`：默认先在会话前 2400 秒中寻找
间隔 120–1200 秒的黑场组合，多个近似等间隔点优先于仅两个点的假设。
允许漏检若干个周期，但稀疏的倍周期巧合降低评分，避免把三分钟一 P 算成六分钟。
只有两个点时周期仍标为候选；此后每个预测位置先扫描前后 45 秒，未命中扩大到
前后 240 秒。命中实际黑场后用这个位置重新锚定，保留原周期，暂停造成的偏移
不会被错误地吸收为新的 P 长度。连续三个预测未匹配就放弃该规律，继续使用均分附近
真实检测到的黑场；不生成只靠外推的切点。过长暂停或不等长 P 可能无法自动恢复，
可根据新的实际黑场重新提供 `cadence.seeds`，或停用周期预测。
周期是黑场节奏假设，不是播放器 P 编号识别。报告记录预测、实际偏移、扩大搜索与失配。
预测出的黑场还须经过同一个连续覆盖/时长求解器；不是每次电影换 P 都另拆我们的 P。
制作长度先按具体作品的审核需要决定，电影换 P 只提供候选切点。例如当次决定约二十五分钟、
电影每三分钟换 P，可以选二十四分钟处的黑场；两小时会话保持五个约二十四分钟的 P。
当次决定短分 P 或长分 P 时同样按该安排对齐，不因电影 P 密集而增加制作 P 数。

每次扫描在活动输出的 `temp/watch-black/<binding>/WATCH_SPLITS.json` 保存源快照、
区域、阈值、扫描窗口、解码路线、候选黑场和实际分 P。`PLAN.parts.watch` 与成片元数据
保留 `splitBoundary` 和 `blackAlignmentEvidence`；来源/参数/分界均绑定缓存摘要。
失败保存诊断并停止计划，不把解码失败当作“没有黑场”。正常重跑复用计划与扫描，
已有成片不因新区域自动重新分 P；边界修订继续保留旧 P 的恢复规则，不重选旧切点。
配置变更不授予投稿许可，既有最终审核和上传检查继续执行。

可在下播前或制作前只预览切点，无需字幕、梗概或队列操作：

```powershell
npm run activity:clips -- watch-splits --media 'D:\录播.flv' --start 3600 --end 10800 --region '0.27,0.25,0.58,0.55' --output-dir 'temp/watch-preview'
```

预览默认使用 1500/1800 秒，可附加 `--target-part-seconds 600 --max-part-seconds 720`
检查短分 P，或 `--target-part-seconds 3600 --max-part-seconds 4200` 检查长分 P。
实际制作读取当次配置中的 `watch.targetPartSeconds` 与 `watch.maxPartSeconds`。

这里的区域只是命令示例，需按本场原帧确认。直播中只扫描已经完整写入的时间段，
暂定会话结束不等于最终观看结束；下播后用实际起止重算分 P。此预览只保存本地报告，
不会渲染投稿、登记 ID、发送通知或入队。使用报告中的绝对秒数检查候选前、黑场中、
黑场后原帧，确认黑场和画面布局；实际制作仍用完成校准的完整观看会话。
`--no-periodic` 只扫均分附近。`--movie-part-seeds '4200,4800'` 提供人工确认的两个
电影换 P 的绝对录播秒数；它们仍必须在本会话内并匹配实际检测到的黑场，不能凭数字切片。

开发验收可执行 `npm run build:workflows` 后，给上述预览命令加 `--candidate`，
在当前预览子进程使用 `build/workflow-candidate.json` 指定的完整候选 release。
这不会激活生产 workflow；该标志不能用于 `run` 或其他队列操作。
生产自动流程使用新功能仍须按架构指南单独部署。
部署工作流或修改生产配置后，注意 `background-clip-queue-runner` 是常驻进程，
会缓存启动时的配置和 workflow release。确认其队列没有 pending/working 任务后，
使用 `pm2 restart background-clip-queue-runner` 刷新，并核对新 PID 已取得 `worker.lock`。
旧进程退出后，锁可能等待现有 60 秒过期再自动接管。仅激活指针不能刷新已运行的队列进程。
若改动只有源 CLI、工作流及配置，直播结束后新启动的梗概子进程会读取新设置；
服务编译产物有变更时才需要另外部署 webhook 服务。

自动任务的可选配置形如（启用前确认对应直播布局）：

```json
{"streamActivityClips":{"watch":{"blackAlignment":{"enabled":true,"region":[0.27,0.25,0.58,0.55],"searchSeconds":300}}}}
```

可调字段还有 `minBlackSeconds`、`maxBlackSeconds`、`pixelThreshold`、
`pictureThreshold` 和 `minPartSeconds`；区域缺失或越界、阈值不合法立即报错。
`cadence` 可设置 `enabled`、`bootstrapSeconds`、`minPeriodSeconds`、
`maxPeriodSeconds`、`searchSeconds`、`recoverySeconds` 和 `seeds`。

## AI 用量与企微汇报

每次歌切、视听处理在目录内分别保存 `AI_USAGE.songs.json`、`AI_USAGE.watch.json`；未指定类别的手动命令使用 `AI_USAGE.activities.json`。每次服务商请求完成即保存，按阶段、模型记录输入、输出、缓存和推理 token，并记录失败、未知用量、本地缓存复用及本地 ASR 时长。结束或失败后通过既有企微 webhook 汇报本次及该工具累计用量；`streamActivityClips.notify.enabled=false` 可关闭该通知。

统计覆盖该处理进程内实际发生的请求；复用的既有直播梗概不重复计费，其原请求仍记录在 `LIVE_CONTENT.json.generation`。缺失的服务商字段保持未知，缓存/推理 token 不重复加到总量，不按未经核实的价格推算账单。通知状态保留 `sent`、`not_sent`、`unknown`；通知失败不会重跑模型，状态未知不自动重发。新统计不会补造旧进程没有记录的请求。

## 栏目封面与标题

歌切和视听使用独立栏目包装，不沿用普通趣味切片的 `【小岁】` 前缀、梗句标题或双层描边大字。

- **歌切**：视频主标题为 `【岁己歌切】歌名-2026.10.2`，使用开播录制日期，月日不补零。多首投稿按演唱顺序使用 `歌名一 / 歌名二-2026.10.2`，各 P 为 `歌名-2026.10.2`；名称过长时稿件标题可简写为首歌名加“等 N 首”，完整歌名仍在各 P 和简介。加入专用合集时只去掉主标题开头的 `【岁己歌切】`，合集条目保留歌名与日期，视频主标题不受影响。封面为暖金与深灰的唱片封套，大字是实际歌名，日期紧随歌名醒目显示；多首逐行列出前三个不同歌名并标明总演唱数，长英文名按单词换行，不再把“歌切”或“本场演唱合集”作为封面主题。
- **同步视听**：视频主标题为 `【岁己同步视听】《搞笑化名》｜2026.10.4`，使用能辨认作品的剧情/人物特征化名，禁用原片名、系列名及缩写；日期使用开播录制日期，月日不补零。例如银河系列用“宇宙蹦迪天团”，奇异博士用“卷毛医生在线画圈”。多部按观看顺序列化名，超长时简写首部加“等 N 部”；各 P 为 `《搞笑化名》 01/06`，保留速通解说、预告、片段等真实属性。简介中的直播标题也替换片名。封面模板 v2 保留完整观影截图，在右下角叠加化名和主播/日期；合集条目省略栏目前缀并使用同一化名。标签固定为 `岁己、小岁、同步视听、虚拟主播`，不添加电影名、系列、角色、厂商或电影相关标签。

歌切投稿标签优先逐首加入本稿件实际收录 P 的已确认歌名，按演唱顺序去重，
不加日期、片段标记或“待确认歌名”。剩余位置按 `songs.tags` 配置补充主播/栏目等通用标签。
上传 SDK 最多接受 10 个标签：歌名优先占位，超过 10 个不同歌名时保留前 10 个，
完整歌名继续保留在 P 标题和简介。新包、未批准包重跑及显式 `restyle` 共用此规则；
标签进入包装签名，已批准/上传稿件仍保留原批准内容。

视听包装 v4 将真实作品身份留在 `activities.name` 和原始标题证据中，
`presentation.publicNames` 逐活动绑定 `{activityId,name,publicName}`。
`work_alias_recording_date` 验收核对真实身份、化名、全部 P 和日期，拒绝公开文案保留原名、
电影相关标签、重复/错绑身份和未确认化名。真实身份未知仍不能投稿，不能拿化名替代证据。
共享梗概/显式扫描同一次请求附带 `publicName`；已有作品使用维护的化名规则，
其他作品缺少合格化名时只生成“待确认化名”草稿，后续独立审核必须确认化名可辨认且不误导。
旧版包装保持兼容，不自动修改已批准/上传稿件。化名只是编辑风格，不改变平台版权判断。

已有证据确认的歌名才能进入歌切标题，视听化名须绑定证据确认的真实作品名；歌名未知保留待核，不能以“本场演唱”“片段演唱”代替歌名投稿。片段属性在简介/歌单中说明。未确认演唱者或完整边界的歌切不能批准。视听未知身份/化名保留本地草稿，投稿验收拒绝空名和泛化类别名。共享梗概的 overview 已写《片名》而时间线漏名时，只在该会话现有引用原文支持唯一名称时本地补齐并保留 titleEvidenceIds；支持“雷神3/雷神三”等序号表达，不从剧情、角色、无关推荐或未引用的弹幕猜真实身份，也不新增 AI 请求。

封面由 `stream_activity_cover.py` 使用一帧实际视频和中文字体在本地排版，**不增加 AI 请求**。歌切与视听均使用封面模板 v2，渲染器保留旧模板兼容；歌切包装仍为 v2，视听化名/日期与截图包装为 v4。模板版本与输入签名独立于检测计划；换封面不会重做梗概、校准、ASR 或视频编码。日常重跑可升级尚未批准的旧版包装，已批准/上传的稿件保持原批准内容。

用户授权更新已发布包装时，先读取当前 BV 的主标题、P 标题与合集条目，保留线上人工改名；复用已有原帧在本地生成独立封面文件，通过 `src/scripts/update_cover.py --bvid ... --cover ...` 修改当前稿件封面，再读取稿件与合集确认生效。已符合规则的合集名不重复写入，需改名时修改合集 episode 的标题字段。原审核元数据、视频、上传状态与数字 ID 保留，不能用 `restyle` 绕过发布保护或再上传视频。
需要同时改名时，`update_cover.submit_cover` 接受显式 `title`、`description`、`part_titles` 与 `expected_videos`；读取前后稿件与各 P，发现并发文案/P 变更即拒绝覆盖，原 cid、filename、P 描述和字幕/互动设置保留。用户未授权改名时不传这些参数。已退回稿件的重提仍是独立任务，不能因这次包装调整自动重提。

已有待审核包可显式更新，保留视频、原数字 ID、旧封面及原元数据备份，并刷新 `REVIEW.md`：

```powershell
npm run activity:clips -- restyle --manifest 'D:\...\UPLOAD_MANIFEST.json'
# 只更新其中一类
npm run activity:clips -- restyle --metadata 'D:\...\songs.json'
# 用户明确指定只投稿部分活动：保留原 ID、完整 P 视频及选材历史，重新生成包装并使旧审核失效
npm run activity:clips -- restyle --metadata 'D:\...\songs.json' --retain-activity-ids activity-5 --selection-note '只保留指定区间的完整演唱'
```

`--retain-activity-ids` 只能缩减一个待核包内已有活动，不能改 P 起止、加入其他来源或
修改检测计划。被移除的活动、旧元数据和原视频均保留；当前包保存 `activitySelection`
记录。选择后须对同 ID 重新执行完整 `review`，再单独入队，不继承原批准。

尚未生成该类投稿包、但已完成校准的计划，可在首次制作时使用
`run --kind watch --retain-activity-ids activity-N --selection-note '用户明确指定的保留范围与排除原因'`。
仅制作这些活动，其他普通视频的待核边界不会阻塞所选作品。原 PLAN、粗候选和校准结果
完整保留；选材意见及排除前活动记入新包 `activitySelection`，正常续做复用这一范围。
已生成投稿包须使用 `restyle` 调整选择；首次制作的相同参数重试保持幂等。
该选项不支持 `plan` 或与边界、时间轴、发布重审修订合用，不赋予审核或投稿批准。

命令拒绝修改已批准、排队、上传中或已发布的稿件；封面制作全部成功后才写入新元数据。更新包装仍是待审核，投稿授权继续使用下文的 `approve --enqueue`。

一类只包含一个活动时，若实际封面源画面明确显示作品名，可在核对原图后给单条 `restyle --metadata` 附加 `--content-name`、`--evidence-frame`、`--evidence-note`。证据必须是该投稿包 `temp/presentation/` 下提取的 `frame.jpg`；文件摘要和所述原文保存在 `presentation.titleEvidence`。该文案校对不修改检测中的未知名/边界，不凭截图确认演唱完整性，也不额外调用 AI。

多首歌名可使用 `restyle --metadata '...songs.json' --title-evidence '...reviewed-names.json'`。文件为 `{"items":[{"activityId":"activity-1","name":"歌名","sourceAlias":"原字幕里的歌名","segmentIndices":[123],"note":"为何能确认这是该首歌"}]}`；索引是该 PLAN 的 `transcript.path` 中从一开始的字幕段编号，时间修复过的源不能改用旧 SRT。引用必须在活动前三百秒至结束后六十秒内并逐字支持名称或经过复核的原文译名。保存完整原句、时间、字幕摘要，投稿验收重新读取；多个活动不能借用另一首的名称。已发布旧稿只修改已有 BV 文案，不重新投稿视频。

最终审核同时接收已绑定的 `presentation.titleEvidence`、校对说明及该活动前三百秒至
结束后六十秒的原始字幕/弹幕上下文，分批审核不丢弃这些曲名依据。说明或点歌弹幕本身
不能证明实际演唱，模型仍需独立比较原话、演唱语境与同音误识。审核证明记录
`titleEvidenceVersion: 1`。旧版因遗漏已有曲名证据而仅 `titles` 不通过的待核原 ID，
可用 `--retry-publication --revision-note '补齐被遗漏的已绑定曲名证据'` 显式升级一次；
须重验旧证明绑定与全部成片。已发稿、其他检查失败、明确 rejected 或新证据下仍不通过
均不能使用此例外重试，普通重启不触发审核。

## 产物与歌单

### 中断恢复与常驻 worker

生产环境由 PM2 的 `background-clip-queue-runner` 常驻处理既有后台串行队列。
部署并验证工作流后，用 `pm2 start ecosystem.config.js --only background-clip-queue-runner`
启动，确认在线后 `pm2 save`。服务重启或 worker 异常退出后，PM2 拉起新 worker；
新 worker 等待旧锁过期且持有者已退出，再接回 `.working.json`，不会抢占仍在运行的 worker。
这依赖 PM2 自身正在运行；主机重启后还需现有 PM2 启动机制恢复已保存的进程列表。

每个后台任务的 `.progress.json` 保存已完成阶段。异常保留 payload、原视频和错误，
一分钟、五分钟后分别重试，最多三次抛错后保留 `.failed.json` 供处理；不再失败即删任务、
误报完成。成功保留 `.done.json` 与进度，重启不会重跑已完成阶段。审核待定是正常完成的
制作结果，不能因为重试而变成审核通过，也不会自动反复请求审核或投稿。

歌切/视听每个 P 完成时写入 `<video>.render.json`，绑定源路径、大小、纳秒修改时间、
源区间、编码设置和输出摘要。恢复时重验输出摘要及实际时长，匹配才复用；不完整视频、
缺少回执或已变更的输出重新编码。编码先写每次尝试独有的临时 MP4，校验后再替换正式文件，
避免旧 worker 遗留的 FFmpeg 覆盖恢复后的成片。未完成的 `.partial.mp4` 不会被采纳为成片。
该回执只是制作进度，不能替代最终内容审核。旧任务在此版本前完成的 P 没有回执时仍需重做。

手动正常制作/继续未完任务可加 `run --background`，进入同一个持久队列；相同参数复用
原任务身份，包括完成和失败记录。使用 `--reuse-summary-only` 可禁止新增梗概请求，
`--no-notify` 可关闭这次活动处理的通知。后台模式不接受边界、源时间或发布重审修订选项；
先完成显式修订，再把普通续做放入队列，避免进程重启重复消耗修订额度。

```powershell
npm run activity:clips -- run --background --kind watch --media 'D:\录播.flv' --srt 'D:\录播.srt' --xml 'D:\录播.xml'
```

产物放在录播旁的 `stream_activity_clips/<录播基本名>/`；归档录播沿用原有 D/E 输出映射。`PLAN.json` 保存源文件身份、梗概输入覆盖、活动与校准；日常的覆盖指完整梗概文本输入，不代表听过整场视频。`SONGS.json` 是每场格式化歌单，包含场次、房间、开播时间、歌曲名或空值、每次演唱起止与时长、完整/片段类型、证据 ID、待核项和 P 序号，并引用粗定位梗概及成本数据。`status: failed` 与一个成功检查且 `songs: []` 的歌单含义不同。`LIVE_CONTENT.json.content.songs` 继续作为梗概；统计应使用歌单以保留重复、未知歌名和时间区间。

视频和两个投稿元数据位于计划签名命名的子目录。`songs.json`/`watch.json` 各自引用所有分 P，`UPLOAD_MANIFEST.json` 每类只有一条投稿记录，`REVIEW.md` 列出本地视频、合集和审核命令。重跑复用源文件和参数完全一致的检测缓存及已完成视频，保留审核结果；已审核视频变化时不能直接覆盖。活动处理失败或仍有待审核投稿时，后台流程保留原录播，供检查完整边界、修订及源文件身份校验。

```powershell
$env:NODE_ENV = 'production'
npm run activity:clips -- plan --media 'D:\录播.flv' --srt 'D:\录播.srt' --xml 'D:\录播.xml'
npm run activity:clips -- run --media 'D:\录播.flv' --srt 'D:\录播.srt' --xml 'D:\录播.xml'
npm run activity:clips -- stats --root 'D:\files\videos\DDTV录播\25788785_岁己SUI'
```

可选 `--summary 'D:\..._LIVE_CONTENT.json'` 与 `--full-context 'D:\..._FULL_LIVE_CONTEXT.json'` 指定同源梗概和共享输入。自动下播会等待该场梗概完成再启动歌切，避免多个进程重复补请求。梗概保留原有公开内容字段，内部新增 `activityTimeline`；后者绑定 SRT/XML 摘要及共享输入摘要，改过源文件后不能复用旧时间线。

统计输出按歌名汇总音画已确认的演唱次数、片段次数和涉及场次；未知歌名、未确认演唱候选 `unverifiedPerformances`、失败/未完成场次单独计数。歌单逐项保留 `verificationStatus`，未确认候选不计入已确认歌数，不伪装成已识别或没有演唱。

## 审核、投稿与合集

自动制作只注册待核投稿短 ID。检查实际演唱/观看、完整起止、P 标题和文案后批准具体投稿包，可显式加入现有上传队列：

```powershell
npm run activity:clips -- approve --metadata 'D:\...\songs.json' --note '已核对实际演唱者、前奏尾奏及所有歌曲标题' --enqueue
npm run activity:clips -- approve --metadata 'D:\...\watch.json' --note '已核对完整观看起止、作品标题与连续分P' --enqueue
```

省略 `--enqueue` 只保存审核结果并刷新 ID。队列计数、90 次/24 小时额度、137022 冷却、查重和 406 恢复都按**投稿包**计算；不会把各 P 拆成独立投稿。活动包上传允许至少四小时 subprocess 时间，适合长素材。所有 P、顺序、区间、封面、文案和合集路由都绑定审核摘要；修改或丢失任何一个 P 均拒绝上传。投稿成功后只把该 BV 加入对应专用合集一次；合集失败记录错误，不重复投稿视频。

真实上传前查询官方视频投稿页实际使用的 `archive/white` 与 `archive/pre`，取得当前**网页投稿渠道**的权限和文件限制。不要用创作中心通用的 `white` 替代 `archive/white`：两者的 `have_permission_of_p` 可以不同。`have_permission_of_p` 控制网页新增分 P，`new_web_edit.max_count` 与 `single_max_count` 分别给出稿件 P 数及网页单次添加数量；本项目活动包仍保留最多 100 P 的本地限制。`season` 与 `season_add_multip` 分别确认合集和多 P 入合集权限，不能把“可建合集”当成“多 P 可入合集”。未开通时返回 `capability_blocked` 并保留同一个完整投稿包，不自动拆成独立投稿。这些网页能力不代表所有客户端渠道的资格，也不能推导出粉丝数或等级门槛。

`approve --enqueue` 在入队前也检查当前权限；失败时保留本地批准和原短 ID，直接报 `[BLOCKED]`，不创建反复失败的上传任务。权限恢复后可把同一个已批准 ID 加入现有投稿队列，实际上传仍会再检查。

生产合集在 `streamActivityClips.songs.collection` 与 `watch.collection` 中独立配置，`seasonId` 是展示用合集 ID，`sectionId` 是创作中心实际加入小节的 ID。不使用按房间匹配的通用合集路由，避免把原有趣味切片也改投歌切/视听合集。

`npm run activity:collections` 只查询；`npm run activity:collections -- --apply` 创建缺少的“岁己歌切”和“岁己同步视听”，按精确名称复用已有合集，使用岁己自动切片合集封面。输出的 ID 写入生产配置，不能把 season ID 当作 section ID。遇到“合集编辑过于频繁”先重新查询部分成功结果，稍后仅创建仍缺少的一类；不盲目重复创建。
