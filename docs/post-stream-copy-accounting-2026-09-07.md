## 已落地修复

排查失败时确认，Node原先只把失败原因写入attempt，丢掉空输出、过短、截断等被拒绝响应已有的usage。选材诊断只记录成功返回；Python漫画日志又只打印最后一次成功。这会漏算失败和重试，影响优化判断。

- 新 `text_attempt_diagnostics.js` 保存每次失败可用的HTTP状态、请求/响应ID、已知用量和未知标记。有效别名、数字字符串和真实0保留；空白、布尔、负数及非法值不转换为0。
- 本地截止时间在调用fetch前触发时，明确记0次请求和0用量；fetch已启动但未返回用量时记未知。`requestStarted`只表示HTTP客户端调用已开始，不证明上游实际完成或计费。
- 空最终答案、过短或截断仍拒绝，但已报告的用量不丢。修复tuZi Responses漏判 `max_output_tokens`，并拒绝明确失败、未完成及非终态输出；有final_answer时，结束状态不再错误取自较早进度消息。
- 明确queued/in_progress时，保留响应ID与已报告的阶段性用量，设置 `outcomeUnknown`、`usageFinal=false`，不继续切换模型或供应商重复提交。它不是已完成稿件或完整账单。
- API兼容切换的前一请求也单独记录。选材阶段同时记录失败，完整总量未知时保持null，已知部分放在 `knownUsage`，不把它冒充完整总量。
- 同进程多个消费者等待同一请求失败时，仅owner累计本次用量，其他消费者本次为0，原尝试放在 `reusedGeneration`。不会修改原始错误对象，也不会缓存失败。
- Python漫画入口逐次记录Node报告的全部尝试，保留状态和请求ID，不只打印最后成功一次；不启动第二条Python重试链。不同日志标签若指向同一请求，仍须按ID去重，不重复加总。
- 已知未完成结果不写入或复用阶段缓存。漫画缓存要求成功状态，拒绝明确截断的最后成功attempt；元数据损坏或读取异常时不再误复用已读出的脚本文本。失败后另有完整成功结果仍可缓存。

没有全量提升请求协议或漫画脚本策略版本来清缓存，仍为5和17；正常结果与已有成品图片继续复用。缺少历史完成状态的旧记录并未因此获得语义认证，不宣称已修复所有历史成稿。

## 跨进程等待方的重复提交修复

沿完整 `requestSelectionText -> withSelectionCache -> generate` 路径检查，发现此前只验证了跨进程成功去重，以及同进程失败共享。两个进程已等待同一个请求时，如果 owner 报错并释放锁，另一个进程会取得新锁再次生成。对已经返回 `queued/in_progress` 的请求，这会绕过文本生成器内部“不继续提交”的保护。

先用两个真实 Node 子进程复现，等待进程确实读到 owner 的活动锁并进入文件监听后，才释放模拟上游结果；不是通过随意延时猜测并发。修复前生成回调执行 2 次，修复后 1 次，等待方收到相同失败、原响应 ID 及 `outcomeUnknown`。未调用远端模型，不将模拟用量算成实际消费。

- 活动锁新增每次生成唯一 ID；已加入的进程只跟随该次请求，不在失败或 owner 消失时取得新锁成为下一次生成者。
- 非缓存结果和异常通过 `.attempt-outcomes/<generationId>.json` 原子落盘，绑定阶段 key；只供已经观察到该 generation 的消费者读取。正常成功缓存路径不写此记录，已有阶段缓存 key/协议不变。
- 失败、截断和无效结果仍不作为有效阶段缓存。之后独立发起的调用不会读取旧失败记录，原有生成器内部重试规则也未改变。
- 已加入的进程遇到 owner 消失、结果损坏或结果无法落盘时，返回 `SELECTION_OUTCOME_UNKNOWN`，不臆测完成、不自动提交替代请求。保留已知尝试与用量；原记录确实不可恢复时保持未知，不伪造原请求零消耗。
- 等待方本次调用没有新增模型请求，用量为 0，原用量保留在 `reusedGeneration`；跨进程失败诊断额外保留 `joinedGenerationId`。原始 error 不被修改。
- 临时记录只序列化明确的错误诊断字段，不复制错误对象中任意配置或凭据属性。发布新记录时清理超过 24 小时的旧 journal；不修改字幕、录播、成功阶段缓存或其他文件。

八类真实进程回归分别覆盖成功、普通失败、进行中响应、无效文本、截断文本、成功缓存写入失败、结果记录写入失败和 owner 退出。每类均启动两个等待进程，确认整组生成回调仅执行一次；失败后另起独立调用，确认仍能生成成功。测试经过实际请求入口和用量汇总，而远端生成函数完全替换为本地模拟，不涉及发布、图片或视频外发。

## 最终弹幕引用的来源变化

继续检查实际成品复核发现，字幕有源哈希保护，但弹幕 D-ID 是数组位置编号。旧计划引用 D1 后，当前 XML 合并、排序或纠错可能让 D1 指向另一段文字；原 `revalidateClipEvidence` 会重建新的 `audience` 并仍返回 `linked`，丢失“当前不是当初引用内容”的差异。最小复现已确认同时间换文字时旧实现无任何提示，时间移动和前方插入弹幕也有相同问题。

- 最终复核现比较每条已引弹幕的原文本和精确时间。变化时写 `danmaku_source_changed:D-ID`；没有旧快照则写 `danmaku_snapshot_missing:D-ID`，不能用当前解析结果补成已验证历史。
- `audienceChanges` 同时保留原引用和当前记录。再次写成品 metadata 时仍沿用最初快照，不因上一轮更新了 `audience` 而消除告警；删除或明确重新建立引用后才不再继承旧记录。
- 未引用弹幕追加不会影响已有证据。原文、标题、简介、封面、边界、D-ID、模型及缓存请求均不改变，只有最终审核诊断增加。PLAN、单路成品、并发成品及 REVIEW 均已验证能保留差异。
