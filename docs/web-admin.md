# 本机 Web 管理工作台

工作台首页统一管理配置、视频审核、直播提醒、录播检索、任务与延迟回复。
侧栏“评论回复”（`/#comments`）展示鹿饼自动评论的排队、处理、点赞与回复记录，
每 5 秒刷新，支持历史筛选与分页。此页只读取评论消费者的原子快照，不启动消费者或修改队列。
平台成功回执与公开可见性分开展示语义，详情见 [评论回复](bilibili-comment-replies.md)。
它通过本机管理 API 调用已有工作流，不创建第二个上传 worker 或延迟回复调度器。

## B 站登录恢复

侧栏“B 站登录”（`/#login`）提供当前登录、评论服务、Cookie 刷新与录播同步状态。
页面打开或手动重新检查时执行只读校验，不周期性请求 B 站。
恢复时，从浏览器同次登录复制完整请求 Cookie 和本地存储 `ac_time_value`。
Cookie 必须包含 HttpOnly 的 SESSDATA；`document.cookie` 不足以完成恢复。

`GET/POST /api/admin/bilibili/login` 经现有本机访问校验转发到管理 API。
保存先校验机器人配置的 `botUid`（未配置时使用原 Cookie UID）及 B 站返回账号，
再通过现有 revision/备份/原子保存机制仅替换 Cookie、CSRF 和刷新凭据。
远端校验期间若配置改变，拒绝覆盖；登录凭据不回显，不写浏览器存储。
`ac_time_value` 必须来自同次登录；此处无法验证它与 Cookie 的配对关系。
评论服务通过既有 check-cookie 接口检查并热加载配置；服务暂不可用不撤销已成功保存。
录播仍由原守护同步 Cookie，可能短暂重启录播服务；页面显示同步结果，不直接重启进程。
接口只检查登录与刷新需要，不发布测试评论或主动轮换 Cookie。

## 启动与依赖

开发时在两个终端分别执行：

```powershell
npm run admin:dev
npm run dev:next
```

浏览器打开 `http://127.0.0.1:3000`。管理 API 默认只绑定 `127.0.0.1:15127`；
可用 `/?clip=<数字 ID>` 直接打开指定视频的审核内容。
延迟回复仍访问 `WEBHOOK_BASE_URL`，默认 `http://127.0.0.1:12523`。
网页和管理 API 可独立启动；服务未连接会显示明确错误。
旧 `/delayed-tasks` 页面保留兼容路径，其 HTTP adapter 同样检查本机 Host 与 Origin。
主机需有 Node 与 Python。纯配置、列表、提醒管理和字幕读取无需 GPU；
点击实际制作、精剪或上传相关操作需要原有工作流环境和对应凭据。

生产构建使用 `npm run build:next` 和已经验证、单独部署的服务产物，
以 `npm run admin:start` 启动管理 API，`npm start -- --hostname 127.0.0.1` 启动网页。
验证不启动 PM2、不部署 `dist`、不激活工作流；常驻化与升级沿用单独部署授权。

### PM2 常驻与登录恢复

「配置」的本场切片和关键词切片分组均提供「切片制作模式」：自动选择、普通、前置、精切。
选择框同步更新当前 JSON 草稿，点击保存后才写配置；自动模式不会为了凑齐种类而强行制作。
前置顺序为重点原话、鹿饼 OP、正文。它只影响后续制作，成片仍须通过原有审核和投稿策略。
后台切片 worker 在每个新录播任务开始时读取一次配置，已运行任务继续使用原快照。

获得常驻部署授权后，使用独立的 `scripts/ecosystem.admin.config.js`，只管理
`danmaku-admin-api` 和 `danmaku-admin-web`。管理 API 使用 runtime 下的独立
发布副本，后续验证覆盖 `build/service` 不影响正在运行的版本：

```powershell
npm run build:isolated
if ($LASTEXITCODE -ne 0) { throw 'Service build failed' }
New-Item -ItemType Directory -Path 'data/runtime/admin/service' -Force | Out-Null
Get-ChildItem -LiteralPath 'build/service' | Copy-Item -Destination 'data/runtime/admin/service' -Recurse -Force
npm run build:next
if ($LASTEXITCODE -ne 0) { throw 'Web build failed' }
pm2 start scripts/ecosystem.admin.config.js
./scripts/install-web-admin-task.ps1
```

升级前先停止这两个服务，重新构建并复制，成功后只启动上述独立配置。
只更新管理 API 模块时，可在操作队列空闲后单独停止 API、备份并替换已验证的
`build/service/services/admin` 对应模块，再启动 API；网页无需重建或重启。
网页使用 `.next` 生产构建；不要在常驻网页运行时执行 `dev:next` 或重建 `.next`。
PM2 在应用退出后自动重启，关闭 Codex 或浏览器不会终止服务。
Windows 任务 `Danmaku-Web-Admin` 以当前用户在登录后启动这两个服务，
不调用全局 `pm2 resurrect`。使用 `./scripts/install-web-admin-task.ps1 -Disable`
取消登录恢复；`pm2 stop danmaku-admin-api danmaku-admin-web` 停止当前服务。
任务固定安装时的 PowerShell 和 PM2 路径，升级或移动运行环境后重新安装任务。
机器休眠或关机期间网页不可用；重启后需该用户登录。查看状态和日志使用：

```powershell
pm2 status
pm2 logs danmaku-admin-api --lines 30 --nostream
pm2 logs danmaku-admin-web --lines 30 --nostream
Invoke-RestMethod http://127.0.0.1:3000/api/admin/health
```

管理 API 首次启动生成 `data/runtime/admin/access-token`，只由 Next 服务端读取；
网页不接收此令牌。两端固定本机地址，并检查网页 Host、Origin 和跨站请求。
不要把 Next 管理页绑定公网；远程访问需要另行设计认证与访问边界。

可选环境变量：

| 变量 | 用途 |
| --- | --- |
| `ADMIN_PORT` | 管理 API 端口，默认 15127 |
| `ADMIN_BASE_URL` | Next 访问的本机管理 API 地址 |
| `ADMIN_TOKEN_FILE` | Next 读取的服务令牌文件，默认仓库 runtime 下的文件 |
| `ADMIN_VOTE_CONFIG` | 管理 API 使用的直播机器人配置，默认 `data/runtime/live-vote.json` |
| `ADMIN_PYTHON` | 固定 Python 可执行程序，默认 PATH 中的 `python` |
| `WEBHOOK_BASE_URL` | 权威延迟回复服务地址 |

## 配置修改

只开放固定文件：`config/production.json`、`config/default.json`、
`data/runtime/live-vote.json`（或启动时指定的文件）、`config/secret.json`、
`config/generation-modes.json`。不存在的文件不在切换列表中。
按分组编辑 JSON，切换分组保留草稿；保存校验文件版本、已维护的配置规则，
先备份原字节，再原子替换。并发修改返回 409，必须重新加载。

凭据默认隐藏。保持完整占位字符串保留原值，填写新值可替换；
每个占位绑定具体秘密，所以数组重排不会串用另一个 provider 的密钥。
管理服务重启后旧占位失效，重新加载即可。
备份位于被忽略的 `data/runtime/admin/config-backups`，包含原文件的真实凭据，
与原配置一样只保存在本机。凭据覆盖与环境变量优先于主配置；网页编辑的
主配置不是有效配置的完整展开。常驻服务需要单独部署或重启后读取新配置，
网页保存不会自动重启；源码 CLI 在下次调用时读取配置。

## 视频与手工任务

### 芙娅之魂备选预览与投稿

侧栏“芙娅之魂”（`/#fuya`）单独展示活动每场直播的 R 重排备选和 P 发布备选，
支持按主播、直播场次、日期/话题/编号搜索及分页；按场次保留原编号并自然排序 R1、R2、R10。
“排序方式”可选场次最新、评分升序/降序、序号升序/降序，并在当前浏览器记住选择。
`GET /campaign-candidates?sort=...` 接受 `session`（默认）、`score-desc`、`score-asc`、
`number-asc`、`number-desc`；未知值回退默认排序。排序作用于全部筛选结果，再按每页 40 条
分页；切换排序回到第一页。评分排序中无评分的候选始终置后，0 分正常参与排序；
R/P 标签按自然序比较（R1、R2、R10），相同评分/序号按场次和候选身份稳定排列。
这些备选从已有 `REVIEW*_STATE.json` 的当前决策及保留历史只读合并，
浏览时不登记数字 ID，不把全部备选混入“视频审核”主列表。
选中备选后播放对应原片时间窗，支持点击源字幕逐句定位；
召回时间仅供预览，正式裁切边界仍待核对。原片离线或缺少时间时显示无法预览。

`GET /campaign-candidates` 及对应候选详情、`source-playback`、`assets/source-preview`
经原本机访问校验和真实路径校验，使用不可猜混的场次/选择身份摘要，不能用 R1 单独定位。
发现范围限于配置中芙娅之魂活动的房间、起止日期和固定录播目录，包含普通场次与
`campaign_early/<batch>/own_stream_fun_clips`；仅接受游戏标题匹配或计划绑定该活动的审核记录，
无需场次已有上传 ID。列表快照缓存 5 秒，损坏的审核文件跳过；列表不读取整场字幕。
预览沿用原片播放器的范围传输和临时转封装缓存，浏览不会修改录播、审核或投稿队列。

详情提供可选的投稿标题、修改意见和“制作并投稿”按钮。仅填标题也能提交；手填标题
优先于模型拟定文案。点击按钮即授权按意见制作及投稿；草稿按场次/候选身份在浏览器保存，
已提交标题、意见、过程和失败原因持久化为一个 `campaign-feedback-publish` 管理任务。
`POST /campaign-candidates/:id/actions` 校验当前候选、完整源字幕和原片版本后，只将所选
备选通过固定 `promoteCampaignCandidate` CLI 准备为未审核的 own-stream 元数据，再调用
原 `import-json --include-pending` 登记数字 ID。其余备选仍只在独立分类中浏览。
准备文件采用源文件及选择身份决定的固定路径；失败重试复用原 ID，不重新导入或覆盖已修改的
正式候选。登记不授予审核或上传权限；制作、文案及入队均复用普通候选反馈流程和已有 CLI。
`GET /campaign-candidates/:id/feedback` 返回原任务及对应正式候选的当前状态，刷新页面后
仍能查看制作进度、投稿队列状态和失败重试。已投稿、入队或排除的候选阻止重复提交。

### 已登记视频

列表只读现有短 ID 注册表，不运行具有状态同步写入的 `list/show` CLI。
每个列表请求只读取一次注册表快照，仅为当前页读取候选证据，避免重复解析整表阻塞审核详情。
审核详情与原片定位使用独立请求：原片转封装或时间定位尚未完成时，字幕、文案、证据与
修改意见区仍可使用；定位失败只在原片播放器中提示并提供重试，不进入整页审核加载状态。
视频、粗剪、封面和字幕只按登记 ID 读取，并校验真实路径位于已配置的
录播或归档根目录；链接不能传入任意文件路径。播放器支持字节范围，
SRT 的网页显示副本转换为 VTT，原审核字幕保持不变。

无正式文案的候选显示 `reviewPresentation.title` 内容说明、候选字幕摘录和源起点，
没有候选字幕时只读对应源 SRT 时间窗；这些选材信息不替换投稿标题。
没有成片时默认“原片定位”，直接跳到登记候选的源起点，点击源字幕可逐句定位。
MP4/WebM 直接范围播放；FLV/MKV/TS 只将候选附近原音画码流转封装为浏览器 MP4，
用首个视频包匹配原片计算实际时间偏移。加载失败可重试或使用原有粗剪流程。
转封装缓存位于 `data/runtime/admin/source-previews`，同源同时间窗复用，
同时只处理一个新窗口，下次加载时清理超过一天的缓存；不写候选元数据、审核或队列。
源字幕用于选材，改词仍切换候选字幕，沿用原数字 ID 命令，不能提交源 SRT 行号。

审核页无需填写确认语：修改意见留空时，点击“没问题，直接投稿”即可授权按当前内容投稿，
不再弹出确认框。尚无成片或存在待制作修订时，按钮显示“按当前内容制作并投稿”。
填写自然语言修改意见（最多 1000 字）后，同一个按钮切换为“按意见修改并投稿”。
空意见通过既有 `feedback-publish` 提交明确的“投”，不登记为人工逐句核听确认；
“投”仅在标题、简介和封面文字齐全时跳过修改计划；缺失文案先依据当前片内证据补齐，
再沿原数字 ID 制作并入队，直接提交的文案可用于补齐这些字段。
当前文案修改与已选标题照常随请求提交。提交成功清空本地意见草稿，保存的意见和执行进度
仍在当前视频显示；请求失败保留草稿，已提交任务不自动重放，进行中与已入队按钮禁用。
歌切/视听多 P 的反馈原文只包含每个活动前后三分钟的字幕并保留原始绝对时间与编号，
不把相隔数小时的活动之间整段聊天送入修改计划；作品名称引用仍使用各活动附近的原索引。
按钮本身明确授权修改完成后投稿，不再要求先选择制作、批准或入队按钮。
已有成片填写“核对无误”“已核对无误，无需修改”等完整确认，直接调用原
`approve-review` 保存绑定当前视频、字幕、封面、文案和来源的人工审核，再入队；
不把人工确认重新交给文本模型裁决，不因旧的自动审核待定而重制视频。
夹有改词/改窗要求、问句或未核对的表述仍走修改流程，待制作修订不能批准旧成片。
管理操作先持久保存意见、直接修改文案和当前版本，再进入工具型编辑 agent。
管理 JSON 原子替换遇到短暂文件占用（`EPERM`/`EACCES`/`EBUSY`）时最多尝试五次，
总等待不超过 300 毫秒；持续失败保留旧 JSON 并报告错误，不删除旧文件或重放投稿。
工具包括读取当前状态、查阅源字幕、结合弹幕与歌词检索歌名、独立修复活动边界、
修改并复核、最后入队。agent 每次读取真实命令结果后决定下一步，最多 16 次工具调用、
3 轮修改和 1 次活动边界修复；来源在模型思考期间变化则立即停止。
读取状态和每轮制作后的工具结果同时返回当前 `reviewDetails`：审核状态、问题码、
具体理由、带原文引用的核查点和检查结果，不附历史审核或内部路径。
编辑器根据用户意见落实称呼、文案、字幕与范围修改；保留审核理由供参考，
不因旧审核问题擅自更换用户选定标题，也不把“投”登记为已经核听或观看。
工具不能选择其他 ID、文件路径、shell 命令或授予审核权限；制作与队列写入仍由原 CLI 负责。
“按意见修改并投稿”按同一编号落实反馈后直接投稿，AI 审核意见只作参考，不再阻止投稿。
普通片通过 `rebuild`、`cut` 或 `approve-review --feedback-authorized` 记录反馈授权；
记录 `acceptanceMode: feedback` 和 `audioVisualReviewed: false`，不声称用户已核听或观看。
仅要求“投”且无需修改时复用现有成片；修改字幕或范围时仍须制作对应修订。
文件缺失、制作或时长校验失败、来源版本变化、同编号重复投稿仍按真实执行状态处理。
只有成片/封面齐备、注册表解除待审核状态、最终标题等于选定标题时才能入队。
反馈版本校验忽略注册表的 `updatedAt`：同批其他视频刷新注册时间不会使排队意见失效。
视频、字幕、文案、审核证据和投稿状态的实际变化仍会停止旧版本操作。
编辑过程保留用户指定标题与确认替换，不因旧 AI 意见擅自改写。
字幕反馈支持明确的全片统称，例如 `里面的“石手xx”都是时守星沙。`：
固定前缀至少两个汉字，尾部每个 `x` 对应一个汉字（支持 2–8 个），目标名称必须明确给出。
管理策略只从当前切片字幕展开去重后的具体原词，补齐计划中遗漏的匹配，再逐个调用原有
`correct --from ... --to ...`；不把通配符交给 CLI、不扩展到源录播上下文，最多 30 个原词。
疑问、否定、仅限某条、无固定前缀或正则写法不作全片授权；没有匹配且目标也未出现时
报告具体问题，已全部改为目标名的反馈可继续制作/投稿，不重复猜改。
文案与现有封面文字从成片 `copy` 合并读取，不以空字段覆盖已生成的封面文案。

### 可选标题与策略统计

普通切片的标题下方提供“标题方案”。不操作沿用原有默认标题；点击“生成其他标题方案”
才请求文本模型，最多提供自然口语、原话看点、有据用梗各一条。无合适证据的策略可以缺席，
生成失败不影响默认文案。完整歌切、观看与游戏包仍使用专用包装流程。
有据用梗只提供与当前片内字幕相符的房间社区参考，来源随候选展示；社区语音标签
不能当作本片原话，也不代表近期流行。目前没有自动接入实时热梗。候选引文必须出现在
当前字幕中；这只约束标题候选生成。“按意见修改并投稿”采用前述反馈直投规则。

点击候选立即保存选择；手写标题点击“保存手写标题”。选择是审核草稿，不直接改元数据、
媒体或上传队列，提交“按意见修改并投稿”、制作、准备修订或人工审核时才通过既有 CLI 应用。

## 全局投稿进度

所有工作区顶部显示全局投稿面板，每 5 秒从只读 `GET /queues/status` 同步，切换分类保留
展开状态。它展示排队任务数、执行中任务、去重后的未完成视频数、上次成功投稿、下一次
预计尝试及滚动 24 小时投稿量。展开可见完整待处理队列、各任务重试时间、等待原因、
最近已结束尝试的投稿接口/预上传频控、结果待核对，以及账号冷却截止时间。
历史任务和原有取消入口仍在“任务与队列”；全局统计读取完整队列，不受历史 200 条显示上限影响。

管理服务从 worker 的 `accountRollingUploadGuard` 和注册表成功回执合并、去重投稿记录，
保留同一稿件较晚时间；只有成功投稿计数，传输进度 100% 不算成功。它按当前 worker
规则投影滚动 24 小时 90 条保护及 5 秒边界等待，并同时考虑账号 137022 冷却和单任务
`retryAt`。未到期重试可被后续可执行任务越过；执行中任务的结束时间未知时不承诺下一次时间。
投影仅表示时间资格，不确认 worker 在线，也不创建、重试、核对或修改任何投稿。

额度图展示“无新增投稿”情况下未来 24 小时计数下降过程，明细逐条列出成功时间和退出
窗口时间。最近创作中心同步时间、同步失败及缺失状态明确显示；尚未同步的数据按已知记录
展示，页面轮询不请求 B 站。实际 worker 仍会在投稿前重新同步并决定是否执行。

## 提醒管理

网页可管理事项名称、启用状态、多版本文案、总开关及本场暂停/恢复，
并查看每日发送与企微记录。时间窗口等策略在直播机器人配置的 `reminders`
分组编辑。首次可使用“添加提醒配置”，补全绝对路径后保存、按原流程启用机器人。

网页只向 `<statePath>.commands/` 追加独立管理指令；直播机器人是唯一状态写入者，
每次 tick 接收、校验并应用，保存状态与已应用 ID 后确认指令。每日发送 receipt
保留不变，不因编辑、重启或不确定发送结果自动重发。
正在发送的提醒保留 receipt 对象；待发送的旧版本由 generation 失效取消。
错误与生效回执在页面可见；积压表示机器人尚未接收，不能报告已经生效。
dry-run 继续使用 `.dry-run` 状态与独立 inbox。

## 录播检索与延迟回复

侧栏“问鹿饼”在管理端内打开问答与证据检索，底部的问答入口也跳到同一工作区，
不再跳转到独立的 15126 页面。可收藏 `http://localhost:3000/#questions` 或
`http://127.0.0.1:3000/#questions`；刷新、前进和后退保留对应工作区。
默认选中已配置的岁己房间（未配置则选首个房间）。点击“问鹿饼”或 Enter 提问，
Shift + Enter 换行；“只查证据”使用可展开的关键词、日期和资料类型条件。

录播检索直接复用已配置房间的 `QuestionCorpus`、问题校验和 `LabGate`。
“查证据”不调用回答模型；语义检索是否请求 embedding 取决于既有配置。
“问鹿饼”显式调用固定回答 provider，展示完整答案与引用。
网页查询频控与弹幕机器人独立，取消或离开页面传播中止，底层退出前不释放名额。
不发送弹幕、不发布动态评论，不接受用户或模型指定任意路径或命令。

延迟回复经 Next HTTP adapter 转发给 Webhook 的权威 API：列出、创建、取消。

没有另一个本地 scheduler 或对生产 delayed-task 文件的直接写入。
